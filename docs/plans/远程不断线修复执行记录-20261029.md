## 修复方式

### 出口与媒体

媒体组由实际 LAX 节点（如有）加末尾 NODE-PICK 显式组成。三台本轮只有 GIA/BWG，因此媒体组成员为 `[NODE-PICK]`。不再用 include-all 试图引入其他策略组，也不会空组落到 COMPATIBLE/DIRECT。

AUTO 与 NODE-PICK 使用同一海外 HTTPS 探测目标，AUTO 设置 timeout=4000、expected-status=204、interval=120、lazy=false。三台最终为 `PROXY → AUTO → NODE-PICK → GIA`。配置热加载后有探测收敛过程；R3 曾短时回落直连，因此增加了实际出网复测，不能仅依赖 hot reload 的 204 返回码判成功。未从每个 LAN 客户端测试视频播放。

### 自愈保护

discovery 在任何失败 return 之前带起 tunnel-watchdog。看门狗以 mkdir 锁防重入，每分钟最多采样一次，连续三次五端点都失败后才尝试恢复，恢复间隔至少 600 秒。

恢复只通过已实测支持的 ubus service signal 针对 `mgmt/mgmt2/mgmt3/mgmt4/mgmt5` 的心跳实例，不触碰 `rssh/rssh2`。若信号接口不可用，不回退为整组重启。R5 的重复 `#routermgmt-tunnelwd` cron 已移除，保留有开机补回路径的 discovery 入口。WAN 模式没有改为 heal。

没有在人为阻断生产网络的情况下演练恢复；全断、重复调用、冷却和反向实例保护在隔离桩环境测试。真实端到端故障演练仍须另选窗口。

### 广州收口与监控

新增 `gz-mgmt-ingress.service`，只加一条 INPUT 非 lo、TCP dport 8443 的 REJECT；不改 SSH、不启用 UFW、不改整体防火墙策略。广州原 relay 服务文件已备份到 `/etc/systemd/system/gz-relay.service.bak-20261029-220744`。

服务文件的下次启动绑定已由 0.0.0.0 改为 127.0.0.1。当前旧进程没有重启，因此 ss 仍显示 0.0.0.0:8443，但宿主规则对外限制已生效。外部 GIA 发起 HTTPS 探测为 000，回环为 200。此前本机单纯 socket connect 的“成功”不足以证明服务器实际公网可达（可能被本地透明代理提前应答）；最终使用真实 HTTP/TLS 探测和宿主规则核实，不把初查 TCP 成功当作原公网开放的充分证据。

新增 `gz-rssh-probe.timer` 每约两分钟检查已监听排障口的 SSH 横幅，只记录状态变化，不登录、不杀连接；当前三个口均为 ssh_banner_ok。GIA 中继凭据只允许直接转发 8443，因此操作工具通过其既有 root 执行通道运行 nc 接到本机排障口，未放宽 permitopen 或更换凭据。
