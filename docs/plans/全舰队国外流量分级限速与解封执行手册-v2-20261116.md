## 需求背景与用户目标（对话整理版，执行前必读）

> 本节是用户需求的忠实整理，不是原始聊天逐字记录，也不是技术验收结论。执行 AI 可能缺少项目上下文，因此必须先理解“为什么做、做到什么程度、哪些不能动”，再阅读后续命令和验收步骤。

### A. 需求是怎么一步步形成的

1. **用户提供了 Codex 编写的执行手册、逐台实测报告和 DNS 参考脚本，要求从第0节开始执行。** 执行过程中必须坚持稳妥、逐台验证、失败即停，不能批量蛮干。P0 游戏 DNS 已按该授权完成，后续阶段不能因为手册写着“下一步”就自动推进。
2. **用户随后要求评估手册是否可行，并再次强调“一定要稳妥、不要影响使用”。** 用户特别询问限速逻辑：国内业务不能受影响，主要限制国外流量，尤其是每天超过一定流量后的下载和视频行为。
3. **用户要求把原计划修订为足够详细、可交给其他 AI 执行的版本。** 新手册必须自包含，不能依赖执行者记得此前对话；必须写清每一步的前置条件、执行顺序、验收、回退和停止条件。用户同时要求：某些设备必须可以解除限速，不能只能限不能解。
4. **用户发现流量统计明显不一致。** 用户指出：GIA 从10月26日至今供应商侧已用约820GB，而平台国外流量统计不足100GB，要求检查原因并把统计纠偏追加到计划中。由此确定：旧平台估算只能作参考，必须先建立可信计量，不能拿旧数据直接封禁。
5. **用户进一步要求限速参数可调整。** 不是把阈值和速率写死在脚本里，而是可以按设备修改“超过多少流量”和“超过后限到多少”。用户给出的需求示例是：某设备超过3G流量后，视频和下载限速到“60kb”。该例说明需要的是**可配置的阈值与动作**，不是已经批准所有设备统一使用3G/60kb。
6. **用户最后要求把需求对话也整理进手册。** 目的是让后续执行 AI 明白前因后果，避免只截取某一个数值或某一条命令而误伤业务。

### B. 用户真正希望达到的使用效果

- 日常未超阈值时，用户上网体验不发生变化。
- 国内网站、国内游戏、公司管理、医院白名单和远程控制始终不受影响。
- 普通国外网页、邮件、API、即时通信尽量保持畅通。
- 真正需要重点约束的是**持续下载、大文件、视频等高消耗行为**，不是简单封掉所有国外访问。
- 某台设备当天国外代理流量超过设定值后，先告警，再只对下载/视频采取降速或经核实后的出口迁移。
- 超限后视频可以降低清晰度、下载可以变慢，但**不能直接国外全断，更不能国内一起变慢**。
- 某些设备有临时大文件或特殊业务时，可以单台、单类、临时或长期解封；发生误伤时可以紧急解封。
- 限速参数应能按设备在线修改，并有版本、审计和回退；解封期间仍保留计量，不能靠清零流量“恢复”。

### C. 用户明确不希望发生的事情

- 不希望执行 AI 未经确认就全舰队批量下发限速或重启服务。
- 不希望把现有不准确的流量统计当成真实配额依据。
- 不希望把“tc速率限制”误当成“每天多少GiB”的流量限额。
- 不希望只限制单一 TCP443，导致 HY2、CF、机场等协议绕过。
- 不希望限速后普通国外网页也无法使用，或用 DIRECT/断网代替治理。
- 不希望国内网站、LOL、医院业务、广州管理通道受到任何影响。
- 不希望设备限速后无法解封，或解封后被旧策略自动改回。
- 不希望执行 AI 把“60kb”等含糊单位自行解释后直接落盘。

| R2 action候选 | 3GiB=3221225472B；全文只有这一个R2候选值，实际启用写入批准参数 |
| R2 warn候选 | 1GiB；须在activation_request中明确，不能说用户已逐项确认 |
| 严重暂停 | 默认关闭，hard=null；不凭“action×2”自动增加暂停权限 |
| 自动迁移 | 默认关闭；额度/路径/授权齐备后另行启用 |
| 首次desired_mode | `observe`；这不代表引擎存在，也不启用限速 |

60 kbit/s只能承诺整形参数，不承诺视频能播。网页视频同站控制页面也可能落入视频规则，必须在分类清单和现场验收中说明。不得偷偷改成60KiB/s、60000B/s或把下行确认解释为上下行全部限60。

### 2.2 速率、配额、链路预算分开

- 速率：内核对指定业务类的代理传输线速率；应用有效载荷通常低于7500B/s，不能要求加密后仍精确等于7500B/s。
- 日阈值：Asia/Shanghai自然日，设备全部代理端点上/下行字节，用于触发已批准动作。
- 提供方月预算：GIA/BWG/机场分别按其账单周期记账；切出口不清零，也不把服务器两条腿重复计入设备日用量。
- 此设计允许普通网页和未知业务继续使用，**不保证设备总流量被硬封顶**。不得宣传“超过3GiB就绝不再多用流量”。

### 2.3 允许与不允许的分类依据

| 类别 | 可用依据 | 不允许的替代 |
|---|---|---|
| exempt/direct | 国内/私网、管理依赖、医院白名单、国内游戏等明确规则 | 按同IP就顺便限SSH/医院业务 |
| video | 版本化、经批准的视频域名/规则集合 | 把所有US-MEDIA连接当视频 |
| download | 明确下载域名/规则/专用业务申请，且最终实际走代理 | 只凭持续大流量、端口443、文件看起来大就认定 |
| web/unknown | 无法可靠归类时保持原行为，仅观察/告警 | 为了“堵漏洞”把unknown全部降至60 |

当前模板有两处必须处理：

1. **US-MEDIA含非视频业务**，包括音频、代码静态资源等；分组名字不能作为准确业务分类。维护独立`classifier_version`及命中清单，受保护规则优先于分类规则。
2. **DOWNLOAD默认DIRECT**。DIRECT下载不进入本方案；不能为了好分类把它改成PROXY，再限60，造成国内或原直连业务被改道。

相同HTTPS连接/H2连接可能有多种请求；不做解密时不能承诺逐URL/逐文件精准识别。分类证据不足时保持可用并告警。大文件启发式只可产生候选报告，不直接触发降速/断连。

## 3. 架构阻断项：先证明分类，才能谈分级限速

### 3.1 当前主路线：专用通道在服务器保持类别身份

```text
受保护/国内/DIRECT规则 → 保持原路径
普通国外WEB/未知业务  → 原PROXY → 普通端口，不整形
明确代理VIDEO         → QOS-VIDEO → 设备+video专用端点 → 服务器video类
明确代理DOWNLOAD      → QOS-DOWNLOAD → 设备+download专用端点 → 服务器download类
                                                      ↓
                         可信日账＋版本化策略 → 超阈值后两类各60kbit/s
```

名称BULK不产生分类。每个受限传输只承载指定设备/类别；video/download不共用不可拆分HY2会话或一个60kbit桶。分类仍按§2.3，不能把整个US-MEDIA当纯视频或把原DIRECT下载改代理。

### 3.2 路线选择与固件限制

| 路线 | 本版结论 | 所需证据 |
|---|---|---|
| R2 WAN ingress→IFB | 当前固件停止此主路线，不反复modprobe/opkg碰运气 | 最新能力记录＋本轮文件/包只读核对；固件改变时另做适配 |
| R2 HTB上行 | 能力记录通过，初始上传仍unchanged | 不能用上行60冒充下载60 |
| 服务器专用通道下行 | 方案A实施方向，待设计/实现/部署 | §12.4—§12.12关卡全部通过 |
| 公网IP整站点60 | 否决 | 误伤网页、共享NAT/管理，不能按IP代表设备 |
| 升级/刷固件 | 本轮不做 | 不因模块缺失顺便刷新 |

其他固件若未来选设备内核mark路线，仍须区分socket/packet/ct mark、zone、NAT和tc ingress时序。PREROUTING恢复不等于ingress可见，必须独立验证；服务器主路线不以R2支持IFB为前提。

### 3.5 下行整形不等于供应商已停止计费

路由器WAN ingress/IFB处理的是**已经到达路由器的包**。这些包通常已消耗国外服务器/提供方流量；不能拿IFB出队只有60kbit/s就宣布GIA也只消耗60kbit/s。

- TCP及正确响应拥塞的QUIC/HY2通常会在反馈后降低发送速率，但需要验证稳定后的代理端点收包量、重传和提供方对账；不保证加密隧道开销也等于应用速率。
- 对不响应拥塞的发送者，路由器侧排队/丢包可能只让用户变慢，国外线路仍持续耗流量。不能用增加DROP来假装节省额度。
- C0/C3同时记录整形前的端点wire计数与整形后的类计数；“分类限速通过”与“国外计费消耗下降”分开验收。后者未证明时必须标NOT_TESTED，不能据此推算月预算足够。
- 本版服务器主路线见§12；也须区分客户端回复腿与访问网站的另一腿，并核对提供方计费方向。只见某qdisc出队60不能证明月账单硬封顶。

## 4. 可信计量：先把统计口径做对

### 4.1 三本账与唯一强制来源

| 账 | 用途 | 不能做什么 |
|---|---|---|
| 供应商面板/API | 套餐额度、周期、计费方向 | 不与未对齐自然月数据直接相减定责 |
| GIA vnstat / GIA nft | 服务器总量/直接客户端腿对账、共享/unknown观察 | 不能把rx+tx直接当设备负载，也不能与路由器同一条腿再相加 |
| router_meter | 指定设备代理端点收+发、各业务类子账 | 没有覆盖/连续性验证时不能驱动自动动作 |

R2日阈值权威源只选`router_meter`。`gia_nft`用于对账，**不能双源相加**。旧估算展示为`estimated_proxy_bytes`，新账为`metered_proxy_wire_bytes`，不覆盖旧字段、不伪造历史回填。

旧活跃连接求和通常明显漏计，但在混合覆盖/类别变化/重放/历史算法下，不能把`E≤U`当作每个样本、每个账单窗口都成立的硬数学约束。标记`estimated/incomplete/not_for_enforcement`，不要乘固定倍数“校正”。

对“供应商约820GB、平台不足100GB”的差异，必须填以下对账表，不直接用其中一个值减另一个值：

| 对账项 | 接手者要记录什么 | 不能推导什么 |
|---|---|---|
| 窗口 | 供应商周期起止/时区、vnstat起止、平台查询起止；统一为同一半开区间 | 10-26至今、11月、最近30天不是同一窗口 |
| 单位 | 各来源原始单位与整数B；GB=10^9B，GiB=2^30B | 820GB约763.68GiB，单位差不能独自解释不足100GB |
| 计费方向 | 供应商只出/双向/倍率、vnstat rx/tx及代理客户端腿/互联网腿 | 服务器rx+tx不等于路由器应用下载量；不能无条件除2 |
| 覆盖 | CF回源、管理/健康检查、非舰队客户端、IPv6和机场是否包含 | 提供方总量不自动等于这批路由器的合计 |
| 采样 | 活跃连接关闭、进程重启、采样断点、重放/正差算法 | 已关闭但未采到的历史连接不能精确补回 |
| 节点归因 | 实际连接叶子和当时端点，而非当前current_node_id | BWG普通出口不代表视频未走GIA；CF仍可能消耗GIA |
| 开销 | 加密、重传、健康探测、源站/边缘腿的口径 | 不用固定倍率把平台旧值“修正”为供应商账单 |

现有历史证据不足以精确恢复每台设备从10-26起的真实消耗。可以给出带口径/窗口的估算排序及unknown，不能按连接数或统一倍数分摊后据此处罚设备。新计量只从真实部署时间起建立可信账。

### 4.2 端点与豁免范围

| 提供方 | 历史已知元组，执行时重查 | 记账 |
|---|---|---|
| GIA | 154.36.139.155 TCP443、UDP34568 | GIA |
| CF | 104.18.32.7、162.159.135.42 TCP2053；EDGE按实际 | 依据**当时实际源站**记账，源站未知标unknown |
| BWG | 74.82.193.113 TCP443、UDP34567 | BWG |
| AIRPORT | 受控读取有效provider及实际连接解析后的端点 | 机场，动态更新 |

端点账按IP+协议+端口统计一次；同元组被多个类别别名引用，**不能复制三条总计数规则再相加**。分类子账用互斥标签，不能与总账重复累计。

管理SSH22/28722、管理-L/-R、实际WireGuard端点、医院10.1.2.18及公司管理等豁免必须先列实际依赖。不能因与代理同IP就把管理算入；不能按132xx这类反向服务端口猜路由器出站端口。国内DIRECT及原DOWNLOAD/DIRECT不进入代理账。

受保护业务若确实合法经代理，提供方物理消耗仍应计入总账并单独标为受保护类别，不能为“豁免限速”隐藏真实用量。它永远不进受限类；如需从动作阈值中扣除，须另定义并预览quota.scope及独立eligible账，不得把总账和扣除后用量混用。R2本草稿scope明确为全部已计量代理收发；雅典娜仍默认不自动动作。

计量对象可以放路由器本机INPUT/OUTPUT hook；它们不是名为“WAN OUTPUT”的网卡链。实际iif/oif、socket路径、硬件/软件offload是否经过规则必须证明。没有命中证据就不报`metered`。

### 4.3 最小字段、去重和守恒关系

```text
sample_id, device_id, meter_id, source, provider,
endpoint_ip, protocol, endpoint_port, traffic_class,
direction, counter_total_bytes, sampled_at_utc,
boot_id, continuity_id, sample_sequence,
period_id, window_start, window_end, timezone,
coverage_status, discontinuity, unknown_proxy_bytes
```

- 原始累计以整数B保存；GiB只用于输入/展示，精确换算为字节。方向以路由器为准：rx=从代理接收，tx=发往代理。
- 相同sample_id去重；乱序sample_sequence不得改写当前基线；连续区间不能重复累加。
- 同一continuity内取非负差；计数下降/表重建/boot变化记录断点与新基线，缺失部分unknown，不能当0或补历史估算。
- 守恒校验：已覆盖总代理账=互斥类别子账+已识别代理但未分类部分，允许明确记录协议/采样边界差异；不能用WAN国内流量当分母稀释unknown。
- `unknown_ratio`分母是同期可比较的代理候选字节；没有可信分母时返回`null/unavailable`，不擅填0%。
- 阈值自动动作要求coverage验证通过、样本新鲜、时钟可信、连续性状态合格。任何缺口转`degraded_observe`，保留业务可用，继续采集并告警。
- CF/source NAT共享、多个设备共公网、链式代理、IPv6、动态节点均需明确覆盖。没有覆盖的设备/协议单列NOT_TESTED，不借一台结果外推。

自动处置已开启后发生持续计量/分类失效时，保存`automatic_suspended=true`与原因，撤除本方案配额触发的限制并观察告警；不能只停新动作却把无法解释的旧限制留住。恢复采样不等于清除暂停锁，须按status/preview/resume重新验证，避免抖动反复安装限制。紧急/人工解封锁始终优先。

`traffic_class=unknown`与“计量覆盖缺失”不是同一个概念：前者可以是**已知代理、已准确计数、但业务未归类**，继续记总账且不整形；后者是无法证明字节是否被纳入，不能驱动配额动作。不得为了让unknown比例变低，把未归类业务硬塞进video/download。

实现中必须版本化meter_health_policy。当前R2记录每300秒、GIA每60秒；不能套旧30秒/90秒候选谎报健康，也不能只放宽时限掩盖日账缺失。开发时按性能/存储预算选周期、新鲜度和缺样判据，经测试由status返回。D阶段前必须明确这些值。

### 4.4 自然日、重启与半天上线

- 日键=`device_id + Asia/Shanghai + YYYY-MM-DD`，底层时间用UTC。时钟偏差>60秒冻结自动动作；不要为本方案擅改NTP。
- 原始计数器不在午夜清零；由日聚合建立新窗口。日界跨采样区间不能伪造精确按日分摊，记录边界不确定量。
- 首日中午部署只覆盖部署后，`period_complete=false`；不把上午未测部分当0。自动启用需按批准的coverage条件通过，不直接把3GiB历史估算塞进新账。
- 重启保留已落盘日账、解封/紧急锁和版本。新内核计数从新基线继续，不因WAN换IP/换提供方/重建表清空日已用。
- 先观察24–48小时；记录完整起止时间、缺样和覆盖，不是简单等一个计时器就算通过。

### 4.5 GIA纯计量的独立边界

可按原手册§6.2在GIA建立自有命名counter表：只有INPUT/OUTPUT计数、无DROP/REJECT、不改root qdisc、不reload现有防火墙。先查表归属并`nft -c -f`，再按授权加载。

该计量从部署时刻起有效，CF/共享IP只建共享账，unknown必须保留。它是可独立交付的小阶段，不应因尚未有业务分类引擎就阻止纯计量，也不能宣称部署GIA计数后就完成了R2全提供方日阈值。

| 规则失败被吞 | 建链/查规则错误大量忽略，读不到计数默认0，最终exit0 | 每命令检查、区分不存在/权限/锁/模块；失败不生成健康样本或推进基线 |
| 重建断点漏计 | 新计数小于旧值时负差直接归0，无boot/continuity_id | 记录完整boot_id/表代次/每规则基线，断点unknown；不能把丢失区间当0 |
| 日账未实现 | state只存上一累计，日志只写正增量，无持久自然日聚合 | 完整整数样本/去重/窗口/period_complete与持久日账，跨日/重启/换端点测试 |
| 无并发保护 | cron和手动运行可能共享state.tmp、覆盖基线 | 单实例锁、唯一临时文件与原子提交；并发/中断/重放不重复累计 |
| 样本语义不足 | 只写有正增量的项；没有全量样本、seq、覆盖与健康字段 | 每周期完整样本，0字节与失败可区分，缺样可发现 |
| 归属未充分核对 | 同名自链存在就复用，不能证明对象完全属于此计量器 | manifest与规则集指纹；遇外来对象停止，不先flush |
| 留存/闪存 | 每周期写持久state/log，轮转只限制单文件大小，无总保留上限 | 写入预算、保留天数/总量上限、上传确认与满盘健康检查；不先清旧日志 |

R2本次config ipv6=false只说明该代理配置关闭IPv6，不能据此宣布整台设备没有任何IPv6漏路径。机场仍为AUTO后备，因此机场不覆盖不是可忽略小项。

### 4.7 已部署GIA表与采样器：不能把unknown当代理剩余量

本轮07:39实测：表有36条规则；日志38行均为可解析JSON，起止07:03:08—07:39:01，**仅约36分钟**，还没有完整自然日。采样脚本哈希与本地一致（`05dd215e908516dda0598af3c44c6df173f434d2ba851fad0916b4d958435118`）。这证明部署/读取，不证明可信归因。

1. unknown规则仅是“IPv4源/目的地址不在固定站点集合”，**没有限定代理协议端口**。输入方向会混SSH等，输出方向还会混代理服务器访问互联网网站的另一腿。不能用它计算“未知设备代理流量比例”。
2. CF规则只按TCP2053计数，随后仍进入unknown规则，CF与unknown可以重复；也没有单凭此规则验证连接确实来自获批CF地址段。计数器相加不是互斥总账。
3. 固定集合只有部分站点，缺GL/雅典娜独立可信身份；公网漂移/共享NAT不是脚本已能自动处理的事实。**发现unknown≠已实现漂移监控或告警**。
4. 采样器共用`samples.jsonl.tmp`，用追加暂存再cat入主日志；并发或崩溃残留可能重放。追加失败后使用`> "$LOG"`回退有覆盖原日志风险。
5. nft失败写error后exit0，不等于可监控健康；完整boot_id、sequence、去重、缺样与受控留存也需补齐。

修正设计：仅把客户端侧获批服务端口送进独立**计数专用regular chain**；先匹配可确认直接站点，再CF共享，再代理端口内unknown，各桶互斥。计数后若用return，只在该计数子链返回，**不在原业务过滤链新增ACCEPT/DROP来“去重”**。服务器另一腿与管理另记，不混设备账。旧表作为历史口径保留快照，不原地改标签伪造历史一致性。

### 4.8 计量修正M阶段：从试点迁移到可信账

1. 只读导出自有规则、脚本哈希、cron对应行、样本窗口/错误数、当前计数和state；受控备份，不运行当前采样脚本“顺便读一下”。
2. 本地开发修正版及隔离测试：正常/零流量/读失败/表重建/重启/重复/乱序/跨日/端点更新/并发/满盘。不得用生产数据库测试。
3. 获批部署时新meter_id/continuity起始基线，并保留旧样本和切换时刻。观察两套时只能指定一套权威源，不能双加；不能回填切换前丢失量。
4. 新规则必须计数专用、归属精确、无丢弃/路由/队列变更。脚本迁移与计数清理分步；失败恢复原采集，不清现有计数或旧日账。
5. 从**覆盖与连续性均合格**的时刻建立24–48h观察；部分首日period_complete=false。修复前的07:03/07:04起点不能直接算合格观察已完成。
6. 与供应商、GIA和路由器按相同窗口对账；R2目前主要走BWG，GIA R2桶低/不增长本身不证明路由器计量坏，也不代表BWG已被服务器计量。
7. 只有可信router_meter驱动R2日阈值。BULK服务器计数只统计子类、缺普通代理，不能取代全部代理配额源，更不能与路由器重复相加。
8. 提交meter_health_policy、覆盖表、未决/缺样与观察报告。判据未通过则继续观察告警，禁止自动限速。

## 5. 策略契约：参数、版本与运行态不混用

### 5.1 两组状态必须分开

- **desired_mode**：`observe`（仅观察）、`enforce`（准许按阈值动作）、`exempt`（设备长期豁免）。这是用户持久意图。
- **runtime_state**：`normal / warned / limited / download_paused / released / released_pending_review / degraded_observe / emergency_latched`。这是设备实测执行状态。

status还必须返回`class_effective.video`与`class_effective.download`各自的状态、effective版本、端点和override。设备级runtime_state只是汇总：一类已release、另一类仍limited时，不能把整台写成normal/released。服务器部分提交时分别报告，不能借一个task ok抹平两端差异。

不能把desired_mode=observe同时解释为“等超3GiB自动开始限速”；observe永远不执行阈值限速。也不能把desired_mode=limited直接等价为“尚未达阈值的正常设备”。

### 5.3 参数校验

- 拒绝未知schema、未知字段、未知类别、字符串表达式、NaN/Infinity、负数、零速率、错误设备ID。
- 允许明确单位`kbps/Mbps/KiB/s/MiB/s`，底层整数bit/s；用十进制精确运算，不能把二进制float误差带入审计。规范值必须是正整数。
- 配额以GiB精确换算为整数B；非整数B结果向上取整并在preview显示。初始3GiB严格等于3221225472B。
- 阈值要求`0 < warn < action`；hard=null表示未启用严重暂停；非null时必须`hard > action`，且独立hard_pause授权有效。
- `60kb`这种新输入拒绝并提示具体单位；对本次已确认的`60kbps`不再次询问、不自行提高为60KiB/s。
- 上下行可以独立unchanged；“解除限速”不使用0数值表达，避免与旧API的0=不限混淆。
- 一次只更新该device_id和明确scope；全局模板默认值变更不得自动改变已有设备override。

### 5.4 不可变版本、预览绑定与回退

1. 分开`config_version`（mihomo签名YAML）、`qos_policy_version`、`classifier_version`、`endpoint_revision`、`release_generation`。不能复用或降低设备highest_accepted_version。
2. QoS策略修订单调递增、不可覆盖。preview返回短期revision和规范化diff，绑定device/expected_policy_version/分类版本/端点覆盖/能力/计量窗口/解封代次。
3. apply做版本CAS与设备锁；旧revision、旧release_generation、超期任务全部拒绝。相同幂等键+相同请求返回原结果，不重复动作；同键不同内容409。
4. 内核事务失败可恢复原有效对象和原effective_policy_version，失败目标修订保持failed；不能把数据库或最高版本水位倒写旧值。
5. 已提交后想恢复旧内容，创建**更高版本的恢复修订**，content可与历史相同，注明restored_from；禁止“恢复exact policy_version=旧版本”的倒退操作。
6. 参数调整不清账、不清连接、不重启mihomo/隧道；纯速率调整不应每次重发YAML。首次增加分类出站需要单独的、已授权的模板部署。
7. apply成功只代表内核提交，吞吐/现场验收独立报告；返回desired/effective分歧，不得假装即时一致。

## 6. 接口与实现契约（以下全部是拟建，不是当前可执行命令）

### 6.1 最小受鉴权接口集合

```text
GET  /api/v1/devices/:id/proxy-qos-v2/status
POST /api/v1/devices/:id/proxy-qos-v2/preview
POST /api/v1/devices/:id/proxy-qos-v2/apply
POST /api/v1/devices/:id/proxy-qos-v2/release
POST /api/v1/devices/:id/proxy-qos-v2/emergency-release
```

执行者必须先在本地源码确认路由注册、agent白名单、结构体/迁移、可用CLI和能力上报，再在隔离环境验证。当前不存在时报告NOT_IMPLEMENTED并进入开发，**不能向生产试发写请求探测是否支持**，更不能改用旧set_ratelimit。

- status：返回设备/agent能力、desired/effective版本、运行态、逐scope解封、meter新鲜度/完整性、当日used_bytes、endpoint/classifier版本、自有对象清单及实际内核计数。
- preview：返回规范单位与原单位、作用域、old/new、当前用量、是否立即触发、是否会改YAML、未覆盖协议、有效期；不返回秘密配置。
- apply：提交`preview_revision + expected_policy_version + Idempotency-Key`，返回task_id和新desired版本，等待真实effective确认。
- release：提交scope、kind、原因、审批身份、expected版本、到期/恢复模式、Idempotency-Key；是独立的高优先级版本事务。
- emergency-release：专用权限与持久紧急锁，任何普通限速/阈值任务不能覆盖；成功必须有实际对象撤除和独立管理验证。

后端不得信任客户端随便填的approved_by当授权证据；从鉴权身份/授权记录生成审计，原因可以用户提供。

### 6.2 在线修改操作顺序

```text
status → 核对当前scope/版本/解封/当日用量
       → preview完整差异和立即动作提示
       → apply（新幂等键、版本CAS、绑定preview）
       → 等task终态和effective确认
       → 独立verify（内核分类、管理、国内、测试流）
       → 记录；失败走第10节
```

降低阈值到当前用量之下：没有`allow_immediate_action=true`就拒绝激活；保留草稿，不自动把设备从enforce改observe或偷偷覆盖已生效策略。提高阈值不自动解除当前limited，需显式release/恢复事务。

有release/emergency/exempt时，参数更新只能写未来草稿，不能通过普通apply绕过锁。恢复需要显式resume意图、当前release_generation与新preview。

`resume`是上述preview/apply契约中的显式操作意图，不代表当前有一个未列出的可执行resume API。开发者必须在请求结构中定义它，列出允许解除的override_id及所需权限；未实现时只允许保持解封，不用普通apply凑出恢复动作。

### 6.3 必须具备本地紧急解封

- 广州不可用时，设备与每个承载BULK的服务器均须有已部署、已演练、可用--help/机器可读status的独立紧急入口。只在设备删规则不能撤远端限速。
- 本文不捏造当前不存在的CLI名字。实现交付时登记它的绝对路径、签名/哈希、输入schema、返回码和离线运行方式。
- 各端先持久写emergency latch，服务器撤指定类整形、设备必要时恢复原已知可用路径，随后合并较高release_generation。旧心跳/queued task不得重装；广州失联也可独立操作。
- latch在重启和WAN重连后保持；服务端恢复后合并这次高优先级事件，再允许经批准的resume。
- 本地入口缺失、依赖故障中的API、或无法区分对象归属时，C阶段不得生产启用限制。

紧急时若持久化本身失败，不能因“写锁失败”放任误限继续：仍优先撤本方案限制，同时设置进程内紧急锁并停止**本方案自己的**自动重装器，明确返回`released_but_latch_not_durable`和重启风险，停批交人工修复存储。不得停整个管理agent、隧道或self-heal来代替；不得把非持久结果报告为完整解封成功。

## 7. 内核事务与解封：谁先写、谁优先、怎样验真

### 7.1 统一优先级（从高到低）

```text
受保护流量豁免（永远不进受限类）
> emergency_latch
> 设备/类别长期豁免
> 人工release（按scope）
> 明确的resume新事务
> desired enforce + 合格计量的阈值动作
> observe默认
```

只解封video不能把整个设备改observe，否则download限制也被解除。为每个scope保存override，并单独返回effective状态；all解封才覆盖两类。

resume不是可随意压过高优先级锁的常驻状态；它必须由对应权限验证并明确撤销指定override，随后创建更高版本重新评估。普通apply不能隐式清除紧急锁或长期豁免。

### 7.2 四种解封

| 类型 | 状态与动作 | 不能做什么 |
|---|---|---|
| 单类 | 只移除指定video/download动作，保留另一类状态 | 不能移除共享计量或让另一类不小心无限速 |
| 单台临时 | 两类解除，继续计量告警；记录scope与expires_at | 不清日/月账、不因到期自动恢复旧限制 |
| 单台长期 | desired_mode=exempt，持续计量，不自动迁移/降速 | 不把预算或账单历史删除 |
| 紧急 | 先持久紧急锁，撤本方案动作，阻止自动重装，人工复核 | 不等待额度判断，不全删防火墙/qdisc |

默认临时release为60分钟建议值，实际用授权时长。默认`restore_mode=manual`：到期转`released_pending_review`并通知，仍保持解除；不能删除release记录后让旧enforce自动触发。

如未来需要到期自动恢复，必须额外明确批准`restore_mode=reevaluate_if_authorized`，到期重新验证当前策略版本、计量、业务和所有锁；不能仅拿解封前旧策略回放。未实现这一路径就只支持manual。

### 7.3 内核对象清单（没有清单不允许apply）

每台manifest至少包含：owner_id/device_id、创建时间、策略/分类版本、mark及mask、ct zone、qdisc/IFB/filter/table/chain精确ID、原对象快照、各对象作用域与依赖、验证结果、备份哈希。

- 预检自有handle/IFB不存在或归属一致；遇到别人的SQM/HTB/mq/clsact对象，不覆盖。
- SN的noqueue、GL的mq、GIA的fq不是相同环境。以ip route/ubus识别实际L3路径，不写死eth0，也不凭qdisc存在就证明能命中。
- 服务器主路线验证端点/设备/类别和回复腿；只有另选IFB路线时才要求对应恢复实验。缺R2 IFB不等于服务器路线已通过或永远不可做。
- 不用远端IP+443作为唯一受限条件；不要为让计数变化全局关offload。确需offload变化，另行评估授权和业务影响。
- 带mask操作不得清掉其他网络策略的mark；异构机型不复用SN规则。

### 7.4 apply事务顺序

1. 校验设备/能力/版本/无并发，采集真实现网manifest与必要备份，准备独立SSH入口。
2. 开启有时间上限的自动回退保护；保护不能通过reboot实现。
3. 先server-ready再设备导流；跨主机不是单机原子事务。协调器保存每端prepared/committed/failed和补偿结果，一端失败不宣告limited，不无保护删旧再装新。
4. 验证分类计数、scope、管理豁免、无全WAN导流、policy与classifier匹配。
5. 提交effective记录后解除本次回退保护。task ok必须含实际effective与kernel验证摘要；失败上报failed/rolled_back/rollback_failed，不能只因为写文件成功就ok。
6. 外部测试器另做吞吐与业务验证，不让一个同步agent任务阻塞几分钟。

包括watchdog在内的任何回退，都要先重读最新release_generation/emergency状态。若事务期间已经发生更高优先级解封，旧watchdog只能清理自己尚未提交的对象，不能回放会复活旧限制的快照；用设备锁、generation校验和对象owner防止迟到回退覆盖新状态。这一竞态必须纳入T15/T20测试。

解封按相反依赖顺序撤整形/暂停：先建立持久override防复活，再解除受限过滤和队列，保留计量及必要标记基础设施。共享基础对象仍被另一类引用时不得删除。

## 8. 分阶段实施卡（不能跳步）

| 阶段 | 允许动作 | 出口证据 | 失败时停在哪 |

## 9. 60 kbit/s的验收方法：避免超时、突发误判和误伤

### 9.1 低速数学与测试窗口

| 应用数据大小 | 仅按60000bit/s计算的最低理论时间，不含TLS/开销 |
|---|---:|
| 64KiB | 8.74s |
| 128KiB | 17.48s |
| 2MiB | 279.62s |
| 4MiB | 559.24s |

旧配置发布任务deadline=120s、agent配置事务watchdog默认约100s。**不得在其中同步做2–4MiB的60kbit/s测速**；会把正常低速误判为故障或拖过回退窗口。

- C3用获批的64–128KiB可控数据源；`APPROVED_TEST_URL`必须由执行者确认确能返回指定大小、无敏感业务正文，不能复制一个不存在URL。
- 控制面apply完成与外部吞吐验证分离；每次测试有明确字节/总时长上限，例如30–60秒，不能无限curl重试刷额度。
- 至少观察稳定窗口并扣除初始突发：T秒内允许字节上界应明确为`rate_bps*T/8 + burst_bytes + 已解释误差`。不能要求每100ms都恰好750B。
- 60kbit/s下64KiB突发桶就相当于约8.74s的预算，会掩盖短测。burst需至少容纳实际MTU，并按固件/调度验证；可从2–4KiB候选开始实验，**不是未经测试的生产固定值**。
- TBF/HTB是排队并仍可能因队列满/延迟发生丢包，不能承诺“绝不丢包”。记录实际burst、队列、延迟与重传，不通过大DROP制造假限速。

## 10. 失败回退、紧急解封和恢复限速

### 10.1 正常失败

1. 停止当前设备和当前批，保持原SSH；不要盲杀广州132xx会话。
2. 根据manifest恢复本次新增/改动对象，验证旧有效内容与必要qdisc/filter；不删除别人的对象，不回放整套旧防火墙。
3. QoS提交前失败：effective仍旧版本，失败desired修订保留失败记录；已经提交需回退内容时创建新修订，不版本倒退。
4. 回退校验P0 DNS、国内/管理、旧受保护文件；失败则ROLLBACK_FAILED，启用已经核实的备用管理入口并交人工。

### 10.2 紧急情况

国内、管理、游戏异常，WEB被误限，或WEB/VIDEO无法分离：立刻通过已演练本地/远端紧急解除，先持久latch、再撤自有限制。业务恢复优先，不等额度或冷却计数。

不把`set_ratelimit kbps=0`、`PUT PROXY=AUTO`、`DELETE /connections`、`tc qdisc del root`或reboot当作完整紧急解封。它们要么只管旧功能，要么改出口/清业务/删除非自有对象。

### 10.3 从解封恢复

status确认当前版本/范围/当日量/锁 → 新preview声明resume及release_generation → 审核是否立即超过阈值 → 明确提交 → 验证scope与业务。

不能`apply(original_policy_id)`盲回放旧策略；必须基于当前状态创建新修订。过期、旧版本、被紧急锁覆盖的自动任务都不允许恢复限制。

## 11. 日阈值、跨日恢复与推广建议

### 11.1 候选阈值：只有R2的action统一3GiB，不给其他台自动照搬

| 设备 | warn候选GiB | action候选GiB | hard/自动暂停 |
|---|---:|---:|---|
| R2试点 | 1 | 3 | 默认关闭；不是旧表的2GiB |
| R1、R6 | 2 | 3 | 未批准前关闭 |
| R8 | 1.5 | 2.5 | 未批准前关闭 |
| R4、R5、R9 | 1 | 2 | 未批准前关闭 |
| R3、GL | 0.5 | 1 | 未批准前关闭 |
| R7/R10/R11回线 | 0.5 | 1 | 重新现场评估 |
| 雅典娜 | 3，仅通知 | 不自动动作 | 不启用 |

初始60kbit/s只落R2已通过验收的video/download下行；其他台速率必须在其activation_request中明确，不从旧1000/2000默认值自行套用。

### 11.2 自动状态转换

仅当desired_mode=enforce、自动动作已批准、计量/分类合格时逐scope评估。设备级emergency/exempt覆盖所有类；单类release只阻止该类自动动作，不能停掉另一类的正常独立状态转换：

- 本日used<warn：normal；warn≤used<action：warned，仅通知。
- used≥action连续两个合格样本：video/download进入limited，采用各自批准速率；同一scope本日幂等，不每次采样重新装规则。
- hard_pause未启用或hard=null：再高也不自动新增暂停权限。批准后达到hard，才仅暂停已可靠识别的非关键download新业务；不得切断共享传输、WEB、国内或医院上传。
- 稳定到新自然日：只有策略明确批准`daily_reset_action=restore_normal_if_no_release_latch`时，才撤昨日**quota来源**的限制回normal。manual/release/emergency/exempt锁和历史记录不被日切删除。
- 释放期间继续计量，迁移自动动作暂停。日切不自动拿昨天的limited状态重放，也不清原始计数器。

### 11.3 迁移和月预算

- 自动迁移默认关闭，只有提供方余量/到期/实际可用性/类别路径都验过且获批才启用。
- 限制对象和计量总量是两件事：迁移单类不能只改PROXY全设备出口；新旧类别传输必须仍有标签、累计账不清零。
- 每设备自动迁移最多2次/日、900秒冷却；这不是限制紧急解封次数，也不能阻挡人工解除。
- GIA/BWG/机场账单周期各自核实。70%/90%只能是获批预算的预警/分流建议，不能在额度或计费单位未知时自动硬切。
- 只因日历到11-30/12-01不恢复GIA；需要真实重置证据、实际数据请求健康、人工窗口和备份。

推广：R2稳定48h且全部关卡合格 → R3/R4/R5 → R8 → R6 → R1 → R9；GL单独机型适配；雅典娜默认只观察。不得将单台通过外推全舰队。

- R2候选可从video=2054、download=2055评估，**端口仅候选，不是已开放，也不强制TCP**。先查占用、安全组/主机防火墙、真实路由可达及协议兼容。
- 端点必须唯一映射device_id+class。初期优先每设备每类独立监听元组与认证范围；只用“公网IP+所有设备共用2054”会把共享NAT设备合并。
- 若复用端口，必须另有经过验证的认证身份→独立内核类映射；UUID名字本身不能被tc读取，不能声称按UUID就能过滤加密包。
- 相同设备的video/download独立类。不能把二者同送一个BULK端点后承诺单类解封；如果未来改为两类合计60，须明确变更需求，不能由执行AI暗改。
- 首期每设备每类只启用一个承载提供方。后备需同类专用端点及独立验收，不能把普通机场/CF当作已限速后备。

### 12.6 模板与规则必须开发：不是“节点名含LAX”即可（K2）

本轮源码确认：`template.go:Render`循环对**每个**绑定节点加入groupProxy和groupAuto；名字含LAX只是额外加入mediaMembers。因此旧“加两个BULK-LAX节点、NODE-PICK仍只有8/4、proxies=4、零代码改动”验收条件无法同时成立。

实现要求：

1. 显式加入node purpose或等价可靠用途字段：ordinary / qos_video / qos_download；绑定、渲染、preview和审计都能看到用途。不能仅靠子串LAX或节点ID区间作安全边界。
2. 非R2设备feature flag关闭，输出不受试点影响。不能只修改共用golden.yaml一行，就宣称仅R2会受影响；后续所有发布都会读新模板。
3. 普通PROXY/NODE-PICK/AUTO、旧US-MEDIA及airport provider下载路径只引用ordinary。BULK节点不能借AUTO成为网页兜底或订阅下载出口。
4. R2新增独立QOS-VIDEO/QOS-DOWNLOAD；组只含本类获批专用端点。受保护规则优先；类别规则从原US-MEDIA细分，代码静态资源/音频等未明确授权的留原普通路径。
5. DOWNLOAD原为DIRECT时继续DIRECT；只有原来明确要代理的download才进QOS-DOWNLOAD。不能为了测出60而改变国内下载路径。
6. **不要求全局US-MEDIA fallback→select**。需要人工选择时在新类别selector外加同类fallback，成员/默认选择/缓存写穿均须验证；旧US-MEDIA可保持原类型。
7. 名称需符合现有最长32字符校验；字段、版本迁移及动态provider扩展都是真实代码变更，不伪称平台已支持。发布版本从当前最大/accepted水位生成，不固定v34。
8. preview必须展示完整组成员与规则差异。隔离测试既验证R2新行为，也验证普通设备不含任何BULK成员。

### 12.7 服务器服务与协议选择（K3）

**部署前**：核对在位sing-box版本、二进制/配置路径、systemd管理方式、监听元组、共享账号、现有服务依赖与回退入口。本轮GIA未见BULK监听或s-box-bulk服务；BWG未取得SSH实测，不能填“模块/端口已通过”。

- 选择实际能从R2握手并取数据的协议。原HY2 UDP34567好用，不证明新TCP2054可用；本机LISTEN、自连或广州可达也不等于R2跨境可达。候选VLESS/TCP、HY2/UDP分别验证，未选协议标NOT_TESTED。
- 独立新服务与受控配置目录，不修改由厂商脚本管理的原s-box主配置，不复用已有unit名称覆盖他人服务。
- REALITY服务器需要**private_key**、服务端handshake、users/flow、short_id等完整字段；pbk是客户端公钥，不能充当服务器私钥。按在位版本执行配置检查，不能直接照最新网页schema套旧二进制。
- 原有密钥/账号不旋转。新BULK凭据来源和范围入注册表；如合法复用服务端密钥对，仍从受控服务器配置读取私钥并只校验对应关系，禁止打印/入库私钥。不能从只有UUID/pbk/sid的客户端档案拼出不存在的服务端配置。
- 配置先暂存并以实际二进制校验，文件权限受控，再按已确认防火墙栈精确开放获批端口。检查安全组和链顺序，不把末尾追加ACCEPT视为必然生效；不全局reload/flush。
- 不通过PUT全设备PROXY去新节点做试验。先隔离测试客户端/本地显式测试代理或受控类别测试规则，避免整个站点普通浏览一起改道。
- 服务启动/防火墙/节点发布是分开的检查点；任何一步失败，只撤本次自有对象，不动原服务/管理密钥。

### 12.8 服务器整形拓扑与共享root边界（K4）

**默认禁止照旧附录把GIA eth0的fq直接replace成HTB，BWG“同款”。** 本轮GIA实际root为fq；BWG未核验。给HTB加个“默认全速类”不能证明无延迟/丢包/公平性变化，也没有可凭空填写的无限线路速率。

优先在隔离实验设计**专用BULK网络路径上的队列**，例如独立network namespace/veth：只把新端口导向专用服务，在该专用路径对回复设备的传输腿整形，普通端口与共享WAN root保持原状。这是待验证设计，不是现在已有拓扑或可直接执行的一行命令。

隔离拓扑必须证明：端口映射/DNAT/SNAT、服务器访问目标网站与回复设备两腿、DNS/MTU/路由、mark保留、conntrack、IPv6与重启恢复；只匹配正确回复腿，不能把BULK进程访问网站的源端口误当客户端服务端口。不得顺便改全局转发策略、默认路由或iptables/nft整套规则。

如隔离拓扑不可行且确需改共享root：停在设计检查点，单列共享服务器变更范围和窗口，完整保存所有qdisc/class/filter/action/参数及可重放恢复脚本，先隔离演练再获批实施；仅`tc qdisc show`或“恢复fq”不足以恢复原队列配置。不能把本次“仔细核查计划/只读核对”当成这种写入授权。

不论采用哪种拓扑，都须实现：

- 每device_id+class聚合预算、独立类/归属；只命中注册表的类别服务回复，不碰普通代理、SSH22/28722、广州管理、医院/公司依赖。
- 初始受限下行HTB类必须规范化`rate=ceil=60000bit/s`（或等价严格最大值）；只改rate留下高ceil可能借到更多带宽。burst/cburst/quantum按实际MTU与低速实验确定，不能把服务器默认大突发原样当验收标准。
- 同类多连接共享一个预算。不同提供方若同时各给60，合计会120；首期单承载，迁移须处理旧连接排空/同意中断或分配总和≤60的跨端预算后再报告严格限速通过。
- 服务器本地manifest、持久锁、独立status/release与重启恢复先于测试。不要通过降低普通默认类速率“顺便优化”服务器。
- 普通网页并发基准、延迟/重传与管理新SSH会话验收；不能仅用规则计数变化宣布无误伤。

### 12.9 正常期、超阈值与既有连接（K5）

推荐从C2观察阶段就让**明确可代理的类别**走各自已验证的专用通道，服务器此时没有60限制；WEB始终原通道。这样D阶段只改类别服务器有效策略，已在专用端点的长连接也能随类调速，不需要每次阈值触发PUT US-MEDIA。

这是为修复旧方案的“切组只影响新连接”漏洞而细化的实现方式，不扩大用户要限制的业务范围。首次分类导流是有影响的维护动作，须独立获批、验证基础业务，不能宣称observe就零影响。

若选择“只有超阈值才切BULK”的变体：必须记录旧普通端点连接并明确自然排空或获批按连接ID处理；旧连接未迁移期间返回`transitioning`/覆盖范围，不报告所有视频下载已限。禁止全量DELETE连接或重启代理解决。

日动作依据仍为可信router_meter所有代理收+发；服务器BULK子账不能取代全部日配额。两次合格样本达阈值后幂等提交类策略；普通参数调整不重发整份YAML。不把“每日2次/15分钟”迁移冷却误套解封或必要安全补偿。

### 12.10 双端解封、故障可用性与协调器（K6）

服务器受限后仅把设备组名改回去、仅在设备清tc，均不算完整持久解封。广州协调器要管理两端版本/锁/对象和真实effective状态：

1. 限速：预览当前router_meter/端点/分类/服务能力和release_generation；锁定设备事务；服务端准备/提交，再确认类别路径实际命中。不在一端失败时伪报limited。
2. 单类release：先持久高优先级事件，撤对应服务器类cap；保留另一类cap及总计量。不能删共享父类或把全设备observe。
3. 紧急：广州失联时服务器独立撤自有限制，设备可独立恢复之前已验证普通路径；两端各持久latch，恢复控制面后合并，旧任务不得复限。先演练这两个入口，再做60试验。
4. 解封不能把rate写“猜测的线路全速”代替。恢复实际未限速对象/已知正常路径，并验证；共享root恢复若涉及他人对象按另案范围处理。
5. 服务器全不可达、类别链路全死或计量失效时，按**提前批准的安全回退策略**恢复原可用路径、解除配额限制、锁定degraded并告警。不得为了“防绕过”默认REJECT黑洞；也不偷偷落普通端口继续声称受60限制。
6. 正常同类后备只允许已计量、同等限速能力与预算验证的专用端点。机场/CF普通节点不算已验证后备；若无安全可用后备，在启用前明确失败恢复行为。
7. 暂时release默认manual到期，仍遵守§7；任务乱序/过期、服务器重启、设备换公网、提供方切换均不清锁或账。

### 12.11 BULK工作包K1—K8（与阶段A—E分开）

| 包 | 动作/前置 | 交付证据 | 失败处理 |
|---|---|---|---|
| K1 | 只读能力/访问/协议/预算/身份核对 | BWG有效管理入口、候选元组、现场路径、未覆盖项；GIA不自动加回 | 不开端口，不默认换GIA |

| K4 | 隔离整形拓扑及可信计量联动 | 不碰共享root的设计或另案审批；M阶段通过；回复腿计数 | 不在生产试replace root |
| K5 | 协调器/版本/日阈值与长连接 | preview/CAS/幂等/部分提交补偿/持久账；先隔离故障注入 | 保持observe |

### 12.12 回退顺序：先让仍在用BULK的连接有出口

1. 持久release/emergency事件并停止本方案自动重装，核对最新generation；保留管理SSH。
2. 先解除对应cap、恢复已验证可用普通路径或保持专用通道未限速；验证国内/网页/游戏/管理。旧BULK长连接与回退新流分别记录。
3. 对仍引用BULK的设备/连接先排空或在获批窗口精确处理；**不得先停BULK服务再改设备**，否则原附录E7顺序会直接断现有连接。
4. 如需移除分类配置，通过平台新preview、发布更高config_version，不降低accepted高水位；不能全局恢复模板后未经逐台验收就算回退完成。
5. 依manifest撤精确类/filter、新服务/端口转发/放行；保留被其他类引用的基础对象和计量历史。自有namespace/veth也要确认无引用后再撤。
6. 成功必须实证；服务器不可达时设备侧先恢复可用路径并锁定，报告远端清理待办，不能写“完整回退通过”。
