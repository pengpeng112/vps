## 4. N02：分流修复与 DNS 根因补证

### 4.1 推荐最小修复

公司场景优先给已证实受影响资源域增加明确的 PROXY 规则，放在 `GEOSITE,google-cn,DIRECT` **之前**，保留内网及节点 IP 豁免在最前面：

```yaml
# 合并到 rules 中的候选片段，不是可直接覆盖整文件的配置
- DOMAIN-SUFFIX,gstatic.com,PROXY
```

它覆盖 `www/fonts/ssl.gstatic.com`，不等于覆盖全部 Google 业务。根据用户页面的脱敏失败域名及连接规则，再逐项决定 `googleapis.com`、`googleusercontent.com` 等是否加入；不要从一个 204 URL 推导所有资源均修复。Google 主站本来可代理，不要用“全局模式”替代精准规则。

**关键限制：** 现有 AUTO 允许全节点失败后落 DIRECT，因此 `gstatic→PROXY` 仍可能降级直连。N02 验收必须记录最终节点链，不能只看到命中 PROXY；若业务要求国外资源不回落直连，在公司策略中设计仅含两个代理节点的组，并同步调整相应测试。公共家宽默认策略是否变更单独决策，不静默改变所有发货设备。

### 4.2 环境策略与发布

1. 查清现有管理系统是否支持设备/环境覆盖项。若支持，用公司策略仅绑定目标设备；若不支持，先为当前设备生成受控候选配置，登记维护窗口内避免并发下发覆盖，明确如何纳入后续渲染。
2. 若需扩展渲染器，采用显式 profile（如 office/home，名称按项目风格），默认行为保留现有家宽兼容；不要在通用模板里硬编码设备 ID 或当前 WAN 租约。没有现成接口就先交付本地实现和相关测试，不直接编造 API 请求。
3. 先在 SN-R1 单机验证故障修复；若即将直接迁到雅典娜且 SN-R1 不再承担上网，可把 SN-R1 作为诊断对照，优先完成雅典娜目标配置，避免两台无意义批量发布。执行记录必须写采用哪条路径。
4. 使用相同核心版本对候选配置做语法校验，`mihomo -t` 也应在受控临时 home/隔离环境执行：可能读取或补下载规则库，不默认认为它在生产 home 上零写入。
5. 仅运行相关测试：渲染改动用 `go test ./internal/clash/`（工作目录 `mgmt/backend`）；Shell 改动做相应语法/BusyBox 兼容验证。测试夹具使用虚构节点，不接生产数据库。
6. 模板由 Go embed 编入后端，持久修复涉及 API 构建时，先核对基础 compose + prod overlay 合并结果；不得照抄开发命令，禁止公开 API/DB。先准备可审查的产物与部署 diff，再按已授权范围发布。
7. 复用现有签名应用/回滚链路，禁止为了省事直接永久覆盖运行 YAML。若应急本地覆盖有明确授权，记录版本、来源、后续管理台覆盖风险和收敛步骤。
8. 加载后校验运行 `/rules` 中规则次序、实测连接链、DNS 行为、出口。`reload_effective()` 当前主要校验组名存在，无法证明“组名未改但规则/DNS改了”的重载真实生效。雅典娜 home/path 不一致曾导致热加载失败；只在证据表明失败时使用已审查的正确服务重启。

### 4.3 根因细分的只读/隔离实验

推荐采样矩阵：两设备 × `www.gstatic.com / fonts.gstatic.com / www.baidu.com` × 系统 DNS / mihomo `/dns/query` / 明确指定的 DoH 查询，记录 A/AAAA、TTL、响应状态、命中规则、最终真实目的地。实际 DoH 请求须有效，不能用空请求的 HTTP 400 判断 DNS 正常。只保存指定公共测试域，不采用户完整浏览记录。

逐项比较两机核心版本、规则库文件哈希/日期、缓存答案。先保留缓存证据，若需要清缓存，只在授权的单机实验窗口做；不要双机同时清空导致丢失基线。用少量 `--resolve` 保留 SNI/证书校验的实验区分 DNS 与传输，禁止 `-k` 绕过 TLS。

候选措施的取舍：

| 方案 | 采用条件 | 风险与结论 |
|---|---|---|
| gstatic 精确 PROXY | 公司场景最小修复首选 | 需要可用代理节点，验证不能落 DIRECT |
| 为 DIRECT 指定 direct-nameserver / 有针对性的 nameserver-policy | 隔离实验证明能稳定获得可直连答案 | 不保证所有 Google 域可直连；避免覆盖医院 split-DNS；按 core 版本验证 |
| 把 nameserver 改成国内 DoH | 当前已经这样配置 | 不构成有效 diff，不应当修复执行 |
| 更换 fake-ip 地址池 | 只有证明映射碰撞导致具体错误时 | 不能修复当前真实目标不可达，且会影响客户端缓存 |
| 上游豁免 SN-R1 全部流量 | 仅继续串联的受控临时方案 | 必须同时保证 SN-R1 的 DNS/bootstrap 独立；只 RETURN 会把上游 fake-ip 当路由目标或失去上游补偿，不能盲用 |
| 升级核心 / 关闭 IPv6 / 改 MTU | 有对应版本缺陷或路径证据时 | 本轮没有支持直接实施的证据，独立变更批次 |

**验收与回退：** 每个设备 7890、电脑透明路径各做 20 次 gstatic/Google/百度请求，间隔 1—2 秒，连接超时 4 秒、总超时 8 秒，保存退出码。gstatic 与 Google 必须 20/20 成功、P95 总时长 <2 秒且无 >5 秒长尾；国内控制也应 20/20，目标 P95 <0.5 秒。阈值是本项目候选验收线，非普适标准；若因目标服务限流或时段因素需调整，记录原因，不将失败样本丢弃。百度仍失败则 N02 只能标“gstatic 子项通过”，继续定位 PC DNS/映射与上游拦截。任何管理/医院回归，或连续两轮业务失败，恢复该批原配置和组选择并停止扩大范围。

2. 保存 PC IP/DNS/默认路由/接口 metric，记录原网线端口。雅典娜上本地验证 N02 公共目标及内部依赖；不能只根据 08:09 快照直接改线。
3. 在现场可恢复条件下，将电脑网线从 SN-R1 LAN 移到雅典娜 LAN。先保留原配置与 SN-R1 通电；不同时改服务器或路由器 LAN 网段。
4. PC 若原为 DHCP，重新获取租约后应得到 `192.168.2.x/24`、网关/DNS `192.168.2.1`。若原为静态，先选经检查无冲突的地址；不要覆盖其他接口。无新租约/出现 169.254/双默认路由则暂停验收，恢复原连接。
5. 测试到新网关、国内、双节点、三类 HTTP；再测医院授权端口及 PC 反向 SSH。原跳板进程可能在改线后需要其重连逻辑生效，读回 DO 18322/18422 及端到端握手，不只看 PC 任务状态。
6. 确认用户流量不再经 SN-R1：PC 路由、雅典娜指定测试连接 sourceIP、SN-R1 指定测试流量计数联合核验；traceroute 隐藏代理跳数，不能单凭它认定完整路径。
7. 连续观察 30 分钟后取消该批回退计时器；N06 通过前不擦除 SN-R1。最终从用户网络拔除 SN-R1 后，如需停用管理记录/告警，作为明确授权的收尾任务处理。

**立即回退条件：** 2 分钟内没有正确租约；管理、医院新出现故障；国内或国外控制连续两轮失败；出现地址冲突。把 PC 网线接回记录的原端口，恢复原 IP/DNS/metric（若曾改），验证旧网关与原业务，保留两边证据；不要通过修改公司交换机或白名单“临时救火”。

### 5.3 如果还需要 SN-R1 提供 Wi-Fi

可另做纯 AP/交换机模式，只有雅典娜负责 DHCP/DNS/NAT/代理。但这仍是两台物理设备，须符合用户意图。LAN-LAN 桥接必须先停 SN-R1 DHCP/代理并给管理地址防冲突，防环路；这些会影响现有身份及反向隧道目标，单列变更，不能当作默认迁移步骤。本计划默认直接移出 SN-R1。

## 6. N04：先得到稳定出口，再谈复杂自动化

### 6.1 短期策略

基于历史晚高峰数据，候选为**公司用户数据腾讯主用、DO 备用；DO 继续承担现有管理面**。这不是把所有 DO 流量改走腾讯，也不修改 DO 公网 IP。先用同窗口逐节点 HTTPS/小文件性能证明腾讯确有优势，再实施。

可采用两种明确的运行方式，选定一种写入记录：

- 最小运行时验证：维护窗口手动将 PROXY 指向 `VPS-TX-SG-02`，观察 30 分钟；这是固定选择，腾讯故障时不一定自动切换，不能宣称容灾已完成。测试后按目标恢复/持久化，读回选择。
- 简单长期策略：公司专属“有序 fallback”组先腾讯后 DO，内置健康检查使用一个已验证的 HTTPS 小响应 URL，另一个独立目标由外部观测交叉验证；不要假设内置组支持两个 URL。主要检测不可用，不能解决所有“可用但慢”的状态。Google 业务组不要把 DIRECT 当作等效健康后备。旧通用 AUTO 测试约束如需修改，应显式区分 office/home 并更新相关测试。

如果两条 VPS 都坏，国内/医院的 DIRECT 规则继续工作；境外显示降级/失败，不把 Apple HTTP 200 当“境外已恢复”。是否允许海外业务自动直连要在实际实施范围中明确，不能静默放宽。

### 6.2 逐节点探测与防止误测

普通 `curl -x 127.0.0.1:7890` 只测当前所选链路，不能区分两个节点。mihomo 支持命名节点 delay API，但会更新探测历史，可能影响 url-test 的选择；读 HTTP GET 不等于完全不影响状态。先按对应版本核实 API 语义。[官方 API 文档](https://wiki.metacubex.one/api/)

优先在 N05 中用绑定指定 outbound 的独立回环监听或隔离探测实例做每节点 HTTP。listener 语法按核心版本校验，不能凭空给出未验证 YAML；只绑定 127.0.0.1，关闭该实例的透明代理/DNS劫持、不改默认路由、不自动下载大规则库。不得每分钟 PUT 用户 PROXY 组来“轮流测速”。

同窗口记录两个节点：TCP 443 建连、指定节点 HTTPS 成功率/TLS/TTFB/总时长、1 MiB 小文件限速下载完成时间；端口打开本身不代表 VLESS+Reality 可用。测试文件用自有或已验证稳定的小文件，核对状态/长度，避免误把错误页当吞吐；不要发布新公网测试服务或开压力测试。

### 6.3 如果串联拓扑暂时继续

雅典娜 nft 和 SN-R1 iptables 的节点豁免清单都要覆盖真实的 DO/腾讯节点 IP，且位于广泛 TCP 捕获之前。仅对实际节点目的地址豁免，保留私网、UDP443兼容和医院规则；服务重启也必须保持。两机脚本分别生成、分别验收，不相互复制。

雅典娜本轮只豁免 DO，腾讯 TCP 可能被上层二次接入 DIRECT。先补证/修复这个一致性问题，再把串联下的测速当作直连腾讯性能；不能以 YAML 的 DIRECT 规则替代防火墙豁免检查。最终单雅典娜时，下游 SN-R1 节点连接消失，该项优先级下降，但仍应修正通用节点清单生成，避免未来复用重犯。

## 7. N05：低成本观测和可选质量切换

### 7.1 先修探针数据质量

现有 v2 每 5 分钟 ICMP 三目标 + HTTP 两目标，共 1440 行/天；9000/8500 滚动阈值只保留约 5.90—6.25 天。新增字段前先定义格式，不靠无限加行。

每条至少包含：UTC 时间与本地时区、device、boot_id/uptime、probe_run_id、target_alias、path（LAN/direct/node-DO/node-TX/selected）、config_hash、节点选择、curl_exit、http_status、DNS/TCP/TLS/TTFB/total、sample_duration。日志不写完整 URL 查询串、Cookie、认证头、UUID 或用户访问域名。

1. ICMP 记录 sent/received/loss/min/avg/max；缺 ping 命令或解析失败记 unknown，不用 `loss=100` 假装真实测量。采样空洞显式 missing，不补 0。
2. HTTP 保留 curl exit：6 DNS、7 连接、28 超时、35 TLS、60 证书校验等；记录失败阶段，不再把所有 000 写成 timeout。规则变更后 `http_gstatic` 标签不能仍被当成直连，附最终链路。
3. 每分钟小响应检查，每 5 分钟链路统计；每 15 分钟可选 1 MiB/节点、限速且串行。两节点全天约 192 MiB/设备/日的文件载荷，双设备再翻倍，先核对预算和探测价值；目标拓扑只在主路由常驻。
4. 每 5 分钟取接口错误/丢弃增量、conntrack 占比、可用内存、CPU；VPS 用同窗口 TCP 重传/发送增量，不用开机累计比例代替实时质量。采样读失败记 unknown。
5. 加互斥锁/进程存活判断，探针总超时必须小于间隔；cron 标记行局部更新，保留其他任务，禁止 `crontab 新单行文件` 覆盖整表。两个设备错峰，避免探针同步放大负载。
6. 时间/大小双限制保留：保证完整 7 天及字节上限，满限后轮转且记录丢弃范围。优先内存日志 + 有界汇总/批量持久化，考虑路由器 flash 写放大；不要每次请求同步刷盘。
7. 新旧格式解析都支持；首日计算预期样本与实际样本、重复率、最长空窗。已知雅典娜 07:55 附近有重复探测，要用 run_id 避免把手工首跑当独立定时样本。

本机低成本补充：用户卡顿时记录网关 RTT、指定公开网页耗时、当前链路、浏览器失败域名与时间。不导出完整 HAR 原件（可能有业务正文和登录态），仅导出白名单诊断字段。

### 7.2 自动切换候选状态机（先影子模式）

这是实施建议，不是已经上线的功能。每 60 秒对两个节点分别探测两个独立 HTTPS 目标，总超时 8 秒；用最近 10 轮窗口及当前有效样本数。先运行 24 小时只算分不切换，至少覆盖一个晚高峰，与用户体验比对后再允许写选择。

| 情况 | 候选判定 | 动作 |
|---|---|---|
| 硬失败 | 当前节点两个目标连续 3 轮都失败；备用最近 3 轮至少 5/6 成功 | 切到备用，目标发现时间约 3—4 分钟 |
| 持续劣化 | 最近 10 轮至少 16 个有效样本，成功率 <90%，或成功样本 P95 >2s 且备用快至少 30%；连续 3 次评估成立 | 备用成功率 ≥95%、P95 <2s 才切换 |
| 仅 ICMP 丢包高 | ICMP >10% 但业务 HTTPS 正常 | 记告警证据，不单凭 ICMP 切换 |
| 单一目标两节点都坏 | 另一目标正常 | 判目标故障，抑制切换，不能把目标故障当线路故障 |
| 两节点都坏 | 均无合格候选 | 保持/标记降级，国内仍 DIRECT，不循环切换 |
| 数据缺失、时钟跳变 | 样本不足或采样器故障 | unknown，不做质量切换，独立提示采样异常 |
| 恢复/回切 | 候选连续 15 分钟合格，P95 优于当前 ≥30% 且至少 100ms | 满足冷却后才回切；默认稳定优先，不必因 DO 恢复即抢回 |
| 人工固定/发布中 | 存在锁定或维护标记 | 自动控制只记录，不写选择 |

控制约束：切换后至少 15 分钟冷却；普通质量切换每小时不超过 2 次，超限冻结并提示。硬失败可越过普通冷却但仍受防来回振荡保护；备用不健康绝不盲切。启动先读当前组，不自动重置。切换失败后读回实际选择，记录部分完成并恢复已知有效选择，不连发多次 API。只由一个控制者写 PROXY，避免与 NODE-PICK url-test、管理台、Agent 并发争用；可让控制者选明确节点，并在退出时恢复预定策略。

新连接才使用新选择；已有 TCP/流式会话可能继续旧节点，不能承诺无缝。不得删除所有 connections 强制切换。记录切换原因、前后节点、评分窗口、人工锁、实际执行结果。

离线验证案例必须包含：DO 高丢包但小 HTTP 正常；DO TLS 超时；TX 全断；单测试站挂；双节点挂；采样缺失；时钟回拨；人工固定；管理台并发发布；进程重启；冷却内反复抖动。生产先一台，先观察后启用；不主动断生产链路制造故障。

## 8. N06：验收、观察与回退

### 8.1 当批验收矩阵

| 层次 | 必须记录的检查 | 候选通过标准 |
|---|---|---|
| PC/LAN | 唯一默认路由、DNS、网关 100 包、有线链路及错误增量 | 无新错误；有线网关 0% 丢包，P95 <5ms |
| 单层拓扑 | DHCP 所属、透明代理处理设备、指定测试 sourceIP | 用户流量只经目标路由器；无双 DHCP/地址冲突 |
| 国内 | 百度及第二个可用国内公共目标各 20 次 | 100% 成功，P95 目标 <0.5s；异常须解释而非丢样本 |
| 国外 | Google 204、gstatic 204、用户受影响页面静态资源 | 各 20 次成功，P95 <2s，无 >5s；浏览器无资源长时间悬挂 |
| 双 VPS | 明确节点的 HTTPS 和小文件对照 | 记录性能而非只比 ping；腾讯主用达到业务线 |
| 医院 | 10.1.2.18 次地址、SNAT 计数、授权 TCP、PC 反向通道 | 保留原依赖；端到端实测，无业务正文访问 |
| 管理 | 心跳时间、DO SSH、保留设备反向 SSH | 基于实际配置周期判断新鲜度；不新增公网 API/DB |
| 兼容 | SN-R1 仍承载流量时的 UDP443 DROP | 保持存在及顺序，不用删规则来消除报错 |
| 持久性 | 运行组/规则与源配置一致、服务 reload 后保持 | 无管理发布回写旧配置；设备重启验证另在可恢复窗口进行 |

ICMP、TCP、DNS、HTTP、浏览器结果分列。HTTP 通过不代表医院通过，反向端口开不代表心跳通过，代理组显示健康不代表用户流量实际使用它。

### 8.2 观察窗口

连续 48 小时，覆盖两个 20:00—22:59 晚高峰；窗口长度是项目安排，必要时延长。记录成功率、失败次数/原因、P50/P95/P99、最大连续失败、采样缺口、节点切换次数、用户报告的卡顿时间。不同时间段/不同样本量不得直接比较均值。

候选最终线：已验证公共业务探测成功率 ≥99%，晚高峰 P95 总耗时 <2 秒、无反复 >5 秒卡住；无管理/医院新增回归；无质量切换振荡。小于 100 个样本时不使用 P99 制造精度。若用户重视大文件，再独立加吞吐门槛，不能用 204 请求代表下载/视频质量。

若仍有问题：

- 网关 RTT 与负载一起飙升：对比空闲/限速传输，检查排队和链路；有 bufferbloat 证据后再评估 SQM，不提前装包或降低带宽。
- 只有特定 IP/资源失败：继续 DNS/SNI/分流对照，不迁移整台 VPS。
- 只有大流量卡、小请求好：补 MTU/PMTUD、重传、接收窗口、限速证据；不盲设 MTU 1400。
- 两节点同窗都差：查公司上联/共享路径/服务器负载，不认为双新加坡节点是真正完全独立容灾。
- DO 只有跨境方向差：收集路由器与 VPS 双端同时间 TCP 证据、必要的低频 TCP traceroute/MTR（工具现存才用），保留中间跳 ICMP 限速的解释；形成工单草稿，未经明确要求不代发工单/消息、不换 IP。

### 8.3 关闭任务

输出实施前后对比、修改文件/版本/哈希、每个门槛结果、仍未验证项、回退记录、设备角色和下一精确动作。状态只更新 `docs/current/当前状态.md`；本计划任务状态与执行报告同步，历史原文不重写。

不得把“完成本地代码”“服务重载成功”“上午能访问”写成“长期稳定性验收完成”。N06 未跨足窗口就写待观察并给出下一次采集时间。

## 9. N07 可选：必须保留 SN-R1 为唯一主路由时

仅在用户选择 SN-R1 终态时执行，本轮不默认走这条影响更大的路线。

1. 先确认公司网接入方式、地址约束/MAC 限制、WAN 网段与 LAN 不冲突；不能把 SN-R1 当前 `192.168.2.x` 配置直接搬到公司口。
2. 设计医院 `10.1.2.18` 次地址/SNAT 从雅典娜 nft 到 SN-R1 iptables 的等效实现，来源网段变为 `192.168.132.0/24`；核对回程与过滤。迁移期间两机不能同时在同广播域拥有 10.1.2.18。
3. 先保存雅典娜可回退状态，再按窗口交接地址/上联；验证无 ARP 冲突、医院实际出口源地址符合白名单，而不只是“配置文件存在”。
4. SN-R1 系统 DNS/bootstrap 不再依赖 192.168.2.1，保证新上联下国内 DoH 和代理节点解析可启动；保留 UDP443 DROP 与 dropbear 192.168.132.1:22。
5. 验证 PC 跳板及所有管理隧道，再移除雅典娜。失败时先撤 SN-R1 新增白名单地址，再恢复雅典娜，避免双占地址。
6. 执行 N02/N04/N06 相同业务验收。此分支不顺带固件升级、主机键体系迁移、密钥轮换或 VPS 迁移。

### 12.3 第二上联实施边界

如要求接入容灾，先用已有手机热点/独立接入做受控同目标 A/B，切换时保留本地管理；手机若只是连公司 Wi-Fi 共享，不是独立上联。真正部署时做单路由主备 WAN，先采用主备而非同时分摊。

医院目标及白名单依赖强制走公司 WAN，不能失败后自动送往移动公网；公司内网不可用应明确报错，公网通了不代表医院恢复。公共上网和恢复管理通道才可按已验证策略用备用 WAN。上联探测必须绑定对应接口/路由，否则探针可能经仍正常的另一 WAN，误报故障线路正常；避免节点选择器与 WAN 选择器同时切换，先稳定 WAN 再重新评估节点。

多 WAN 需要专门核对 fwmark、策略路由与 mihomo 透明代理的兼容性。官方 mwan3 文档说明其多线分配按连接工作，并非把一个连接带宽合并；换 WAN/IP 不保证现有 TCP 会话不中断。[OpenWrt multi-WAN 文档](https://openwrt.org/docs/guide-user/network/wan/multiwan/mwan3)

雅典娜现网 nftables，不能直接安装或照搬 SN-R1 的 iptables/mwan3 配方；先核实固件支持与隔离验证，再决定具体实现。备用移动接入设置流量预算、计量提示和大下载限制；切回公司 WAN 设置恢复观察时间，避免上下线反复震荡。

### 12.4 在原计划上进一步完善上网策略

建议以明确业务需求增加少量策略，初期可复用同一物理出口，不为每类都造一个自动控制器：

| 类别 | 建议策略 | 验收重点 |
|---|---|---|
| 医院/公司内网 | 内部 DNS 按域/网段定向、公司 WAN 专用、原白名单 SNAT | 不能被公共 DoH、境外代理或移动备用吞掉 |
| 节点与管理传输 | 节点目的 IP 的防火墙旁路；独立 TCP 管理入口 | 用户数据换节点不破坏恢复通道，主链路失败能用已验备用 |
| 国内常规服务 | DIRECT，匹配可用的真实解析结果 | 域名及其静态资源都通，不用 GEOIP 标签替代访问实测 |
| 境外普通网页 | 稳定主节点 + 明确备用；HTTPS 成功率优先 | 页面主文档、字体、脚本、登录域名规则一致 |
| 登录/工作服务、长连接 | 固定一个已验证节点，人工锁定或更保守的故障切换 | 避免仅因几十毫秒差异切出口；故障时允许重连并记录原因 |
| 下载、更新、同步 | 按目的地正确分流，单独限速/错峰；移动备用时限制 | 不能因一律 DIRECT 造成境外下载不通，也不能占满交互通道 |

重要补充：

- **网页相关资源一致性**：按实际失败域名维护小型业务域集合；无需把整个全球 CDN 平台或超大 IP 段粗暴强制代理。一次修 gstatic 不代表登录验证码、字体、API 全部通过。
- **解析可启动性**：路由器系统解析、mihomo bootstrap、节点域名解析、DIRECT 解析和客户端 fake-ip 分开验证；冷启动/上游 DNS 暂不可用时仍能恢复。内网域名不得泄漏给公共解析器；浏览器安全 DNS 设置也需纳入路径核对，未经验证不全局强制开关。
- **出口稳定性**：不建议当前使用 round-robin。mihomo 的 consistent-hashing/sticky-sessions 提供地址维度的分配，不能保证跨多个不同域名的一整个登录业务始终使用同一出口，也不能让既有连接跨节点无缝迁移。[mihomo 负载均衡文档](https://wiki.metacubex.one/config/proxy-groups/load-balance/)
- **主备语义**：内置 fallback 按顺序选择可用节点；恢复后可能重新选择前面的节点。原计划 N05 的“15 分钟冷却、业务质量评分、不急回切”不能声称由简单 fallback 自动实现；若采用简单方案，明确其限制，若确需完整防抖再实现外部单一控制者。[mihomo fallback 文档](https://wiki.metacubex.one/config/proxy-groups/fallback/)
- **排队治理**：只有限速上传/下载时交互 RTT 明显升高，才进入 SQM 试验。先测实际可控瓶颈与吞吐，核对硬件加速/流量卸载兼容性，再单机评估整形值；公司共享出口的拥塞不一定能由这台路由器解决。SQM 用于控制排队延迟，不修复跨境路由丢包。[OpenWrt SQM 文档](https://openwrt.org/docs/guide-user/network/traffic-shaping/sqm_configuration)
- **协议选择**：公司场景先保留已验证的 TCP 代理和 UDP443 兼容规则。不要仅为“抗丢包”全局改用 UDP/QUIC 方案；其他接入若需要另做 profile 和端到端 UDP 实测，不取消现有管理 TCP。
- **配置持久性**：策略、DNS、节点防火墙旁路、探针目标应从同一份经验证的节点/环境清单生成，逐机应用。名单不一致是当前腾讯未提前旁路的风险来源之一；规则库更新也需要哈希、灰度和可回退。

### 12.5 对后续执行的增补要求

N01 加入“腾讯恢复入口现状与 DO 故障恢复能力”盘点，不重新安装已有隧道。N02 加入网页依赖域、内网 DNS、冷启动解析验收。N04 明确每类业务是否允许自动切换、回切及 DIRECT 降级。N05 将备用上联与第三节点评估标为可选，不自动采购、安装多 WAN 或启用负载均衡。

- 6个终端平均每个约6.67GB/天，10个约4GB/天，尚未留备用余量；双向计量时有效业务载荷预算近似减半，具体以商家记账口径为准。
- 假设10人每人每天2小时、平均5Mbps视频、22个工作日，仅载荷就约990GB/月；双向计量可约1980GB，未计协议、重传、其他流量。网页/文档/轻量交互与视频/模型下载差异很大。
- 建议月度预估不超过套餐70%—80%；用至少一周各站点“真正走代理的流量”外推，加20%—30%余量，再选1.2TB/2TB或更大套餐。不要将国内直连流量也算进VPS预算。

### 13.5 试用验收：电信、联通分开过关

1. 采购前记录机房、产品ID、供应商线路文字承诺、测试IP/Looking Glass、两方向路由、带宽计量、退款截止、续费价和流量超额措施。以上应形成询问清单交用户，未经明确指示不代发工单。
2. 官方网关测试IP只能初筛线路，不能代表分配实例吞吐/负载。先安排测试时段再开通；退款时限若不足72小时，先在截止前完成首个晚高峰 go/no-go，再决定保留后继续观察。
3. 经采购授权才开一台月付或最短周期候选，使用独立凭据；作为隔离数据出口先测，不迁移现有MASTER_KEY、DB或路由器身份。
4. 从实际电信、联通各至少一个点做同窗对照，每天20:00—22:59重点采样，覆盖至少两个晚高峰。若只有本工位联通点，只能验收该点，电信明确待验证，不拿外部公共测点替代全部验收。
5. 对照 DO/TX/新节点的实际代理 HTTPS 成功率、P95、长连接断开/重连、小文件吞吐，结合双向路由和终点TCP证据。中间跳ICMP丢包不直接作为失败；不运行未审查的一键测速脚本，不向外发真实出口或业务数据。
6. 通过N06业务线且晚高峰收益明确，再按站点逐个灰度（1→少量→全部），每站保留TX回退。若电信佳而联通差，可按站点运营商分别设置主节点，不强迫全部使用一个“统一最优”出口。
7. 若精品候选不优于现有TX或晚高峰仍严重劣化，按具体退款条件退出，不为了线路标签强行保留。若通过，改为“精品主用、TX备用、DO管理”，观察7天再讨论现有节点续费与角色收敛。

### 13.6 中转建议的判断

中转只有在“客户端→中转”和“中转→出口”组合路径确实更好时才有价值；单纯增加一跳不改善拥塞，还增加时延、故障点和计费。当前更值得先测精品出口直连，不默认叠加国内公网云中转。

关于“国内云检测到代理就封禁”：本轮没有证据支持对阿里/腾讯所有产品一概作此保证性判断。须区分云厂商账号/实例限制、网络端口/IP阻断、目的站风控和公司网策略；处理条件也不同。按具体地域产品的现行服务条款/AUP及用途确认，不宣称必封或绝不会封，也不把海外精品线路等同于免受网络干扰。

最终推荐：**修复现有分流问题，同时准备一台电信/联通精品出口的短期试用；不增加国内中转、不立即迁移整个DO、不因宣传线路而跳过晚高峰实测。** 第12节的普遍采购门槛继续适用，本节将精品线路试用提前为明确候选。
