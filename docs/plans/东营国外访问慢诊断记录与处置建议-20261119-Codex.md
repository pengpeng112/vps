# 东营国外访问慢：诊断记录与处置建议

2026-11-19 16:26—16:36，Codex。本轮用户先反馈“国外无法访问”，随后明确为“国内没问题，国外很卡”，终端应是连Wi-Fi的电脑，尚未提供具体网站或现场可复现操作。

**结论：不是本轮观察中的完全断网。R9当前经BWG-HY2能访问国外，但国外下载样本吞吐偏低；对照更支持东营到境外节点的传输段是瓶颈。香港CF路径的数据段更快，但小样本、传输方式和握手开销有边界，不能据此称已修复全部网站。**

本轮没有改生产配置、节点选择/绑定/认证，没有发布、重启或切换全舰队。新增本地只读诊断工具，完整测试只通过SSH TCP通道在内存里建立独立TLS/WS/VLESS连接，不在路由器启动临时核心或写入文件。

## 1. 设备与配置现状

- 设备：SN-R9-AX3000东营经开区网安，rtr-101be0，广州排障13231。
- 16:27心跳约6秒；配置7/7/7；许可enabled且到期2027-11-11；proxy_mode=rule、access_mode=all、vps_limit_kbps=0。
- 运行PROXY=AUTO→NODE-PICK→BWG-HY2-JPTY-01，实际出口74.82.193.113/JP/NRT。此前拟迁香港的全舰队计划尚未实施。
- 正式配置SHA仍`1eb54b96092fd96f449d4360a7c805418d468275b8c6ec897f2bffd83a101ebb`，核心PID4086；整个独立探测前后相同。
- 发布处理器SHA71a5045e…；DNS/隧道文件与上午已知基线相同；WAN noqueue。不是此前3GiB/60kbit自动限速触发，本计划限速尚未上线。
- MIHOMO与DNS透明链及PREROUTING跳转存在、有计数；192.168.132.182/.216客户端TCP Redir连接实际进入BWG，也有正常国内DIRECT。没有发现透明代理链整体丢失。
- DNS为fake-ip模式；Google/YouTube返回198.18.x是该机制的正常表现，不可仅凭假地址就重做游戏DNS修复。实际Web TCP成功已单独验证。

## 2. 访问和节点探测

R9正式7890代理访问：Google200/约0.59秒、YouTube200/1.32秒、GitHub200/0.79秒、Microsoft200/0.57秒、gstatic204/0.83秒；百度200/0.17秒。这些主要是HEAD或小响应，不代表视频播放、下载或用户账号业务无卡顿。

指定节点HTTPS延迟：BWG-HY2约119ms、GIA-HY2约204ms、新香港CF约392ms、新BWG-CF约399ms。**低延迟和alive不等于高吞吐。**

## 3. 速度证据：不能只看网页能打开

### 3.1 路由器原生curl，经正式BWG-HY2

同时间、同目标speed.cloudflare.com小文件，成功长度/HTTP均核验：

| 来源 | 256KiB总耗时/平均速率 | 512KiB总耗时/平均速率 |
|---|---|---|
| 东营R9 | 5.85s / 44782B/s | 9.42s / 55629B/s |
| R2对照 | 2.11s / 124221B/s | 4.57s / 114719B/s |

东营路由器自身已测到慢，所以不能把全部原因归到电脑Wi-Fi；但这仍是一个下载目标、短时样本，不当作所有业务的固定带宽。

R9国内阿里镜像Range测试：HTTP206、262144B完整、0.271秒，约967724B/s。支持“国内路径比此时国外样本明显快”的反馈。

### 3.2 三种路径共同回传方式的独立对照

为避免影响现有客户端，所有路径均从R9发起、通过相同SSH回传方式测512KiB；两条CF路径为内存独立客户端，完整校验外层TLS/WS/VLESS及目标HTTPS。数据不经过改动后的正式组选择。时钟边界仍有差异：正式PROXY的数据段从收到响应头后计时，CF从发HTTP请求前计时；不能将数据段速率直接当严格同条件的长期带宽比。总耗时可用于本轮单次完成时间比较。

| 路径 | 数据段耗时 | 数据段速率 | 含建立连接的总耗时 |
|---|---:|---:|---:|
| 正式PROXY→BWG-HY2 | 4.36s | 120146B/s | 5.22s |
| 香港CF2D-HK-01 | 2.06s | 254348B/s | 4.50s |
| BWG-CF2D-BWG-01 | 2.60s | 201548B/s | 5.43s |

该组香港数据段约为BWG-HY2的2.12倍，但握手更慢，512KiB整次总耗时仅约缩短14%。SSH回传本身也会限制速率，因此不把它与原生curl或服务器本机测试混为同一测量方法，不承诺切香港后所有页面快一倍。

第一次256KiB独立路径样本也全部成功，HK/BWG-CF数据段约119/127KB/s，说明短时吞吐有波动；不能只挑最佳样本。

### 3.3 两个境外服务器自身对照

HK和BWG分别直接下载同目标512KiB：

- 香港约0.056秒、9.02MiB/s量级（curl输出约9.39MB/s），无资源吃紧。
- 搬瓦工约0.143秒、3678800B/s，约3.68MB/s，load约0.04；当时队列为fq，未见本方案HTB。

以保存的原始curl字段为准；香港当次是`524288/0.058030≈9.39MB/s`，不能拿14:13的64KiB速度冒充此时容量。单文件不能排除特定站点/线路的其它问题。

第二个Hetzner测速目标在两台服务器均异常（HK TLS EOF、BWG空回复），该目标不作有效带宽证据，也不把它判为R9故障。

补充服务器侧对照：同一Cloudflare512KiB文件，HK约9034775B/s（9.03MB/s），BWG约3678800B/s（3.68MB/s），分别约0.058/0.143秒完成。服务器负载低；不能据此证明所有国外目标都快，但支持当前慢速不主要发生于这两台服务器到该目标的出站段。另一个Hetzner目标两处失败，保留失败证据、不参与性能结论。

## 4. 本地链路、资源与Wi-Fi边界

- R9到上级网关192.168.3.1：8/8回应、0%丢包、平均约0.923ms；只证明该短时小包样本正常，不证明运营商全程无丢包。
- 内存可用约776MiB；观察CPU idle约33%—95%，没有持续CPU打满证据。load约1并不等于CPU满载。
- wan rx/tx errors为0；存在累计dropped，不直接当即时丢包率或根因。
- Wi-Fi ra0有累计rx_errors，最后12秒采样没有继续增长；驱动iwinfo assoclist返回No information available。没有拿到真实关联终端RSSI/重传率，不能断言Wi-Fi完全健康，也不依据旧累计CRC率调信道。
- 当前实际客户端访问样本有限，且没给出具体卡的网站。未做现场Wi-Fi到网关测速或真实网页/视频复现。

## 5. 判断与建议

**支持的判断：** R9能出国，当前跨境代理传输吞吐偏低，低于服务器自身出国能力及国内样本；BWG-HY2路径不如香港CF数据段表现。授权停用、设备配额限速、DNS整体失效、透明链全丢或服务器持续满载，均不是本轮证据支持的首要解释。

**尚未确认：** 是运营商跨境拥塞、路径丢包、UDP/QUIC传输差异、特定时段或站点限制中的哪一项；Wi-Fi是否另有叠加影响。不能写成“确定被封/确定服务器限速/确定无线坏”。

后续最小处置：

1. 用户现场提供实际卡的网站/客户端，再对该目标和同一电脑做测试，避免拿测试站替代真实业务。
2. 可仅对东营进行有回退的香港临时路径体验对比，保留66云/BWG备用，不整机重启、不改DNS/信道/全舰队。明确临时选择与正式香港主用发布是两件事，CF不得直接设primary的现有门禁仍适用。
3. 现场体验确有改善才决定保持/转正式策略；若无改善先恢复原选择，继续查目标站点与客户端，而不是不停重启。
4. 正式长期香港主用，仍按既有“入口/预期出口分离”能力、R2先行或独立维护批次落实，不因本次诊断绕过签名/校验或丢弃备用。

本轮用户要求为检查情况，本轮保持只读。没有将测试改善写作已修复/已切香港。
