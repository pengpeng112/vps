## 执行方式

每轮选一个任务包；长包拆成 45～90 分钟的工作批次，时间是安排参考，不是做到一半就停止的理由。每批必须留下可复核交付物。观察窗口不需要 AI 一直占用会话，可保存检查点后交接。上一包验收通过后再执行依赖包；发现高影响问题先登记，不能在只读任务中顺手修复。

## P00：先建立可信现状

输入：current、阶段 0/1、09-25 变更、mgmt 部署文件。

1. 只读采集服务器服务状态、容器状态、端口绑定、磁盘内存、待重启标记；不运行 compose up/build 或部署脚本。
2. 分别核对两台路由器 Agent 版本、配置版本、心跳时间、SSH 探测、NTP、wan-watch、当前出口。将“进程运行”和“端到端有效”分开。
3. 用最小必要数据核对电脑默认网关、SN-R1 上联、医院通道依赖；不改网卡、DHCP、路由或白名单。
4. 记录账号侧付款、2FA、恢复码保存是否已确认。仅用户/账号授权渠道能证实，不能从 VPS 存活推断；不把历史价格和赠金预测当当前事实。
5. 输出 `P00-日期/基线.md`、差异表与下一任务建议。不可访问项记“未验证”，不得用旧结果冒充实测。

## P01：凭据治理与会话导出修订

本次已发现：工具包带私钥；脚本、引导包、WG 配置、备份和旧文档可能含秘密；导出脚本内置已知敏感值，不能算秘密库。

1. 扫描只输出文件、行号、规则名，报告不回显值；将活跃凭据、过期令牌、历史证据分开登记。
2. 建立脚本→凭据→设备/服务的消费者映射，再选择受控存储；先改一个低影响脚本验证缺凭据立即失败。
3. 修订 `export_zcode_sessions.py`：项目路径精确或目录边界匹配（现为前缀 LIKE，可能误含相邻项目）；标题、元数据、工具入参输出都需脱敏；先按日期/会话选择，避免大库 fetchall；明确截断和解析失败数量。
4. 脱敏默认开启，显式危险导出选项不能成为普通使用流程；移除脚本中的真实秘密清单，使用运行时规则/受控替换源。用虚构秘密样本验证遗漏场景，不在测试夹具写真实值。
5. 在完成清点后制定必要的轮换顺序，单独执行和验收；不要因文件挪位置就认为秘密已失效。
6. 产物：脱敏风险清单、脚本修订、虚构样本测试、迁移清单、仍需轮换事项。恢复依赖未核实的凭据不得删除。

## P02：隧道最小权限

参考旧阶段 2，不重复阶段 1 的双实例改造。先核实现有用户/密钥权限与受限 jump 账户是否仍能执行命令。为每台设备设计独立身份、端口白名单和恢复通道；验证 ssh -N 与禁 shell 的兼容性。

先雅典娜、观察至少 30 分钟再 SN-R1；保留可用旧通道直至新通道验收。验收包含管理心跳、反向 SSH、越权端口拒绝、命令执行拒绝、数据面和跨项目通道。失败退回该设备的已知良好配置，不扩展到另一台。产物是脱敏配置差异、负向验证证据和回退记录。

## P03：监控与告警

按三个小包执行：A 修 WAN/握手/时钟语义；B 告警 active/resolved/acked 生命周期；C 真实出口探测与双线切换口径。

先由 D3 核对缺字段、空值和时间分布；再看 Agent→数据库→DTO→页面全链。不可简单放宽 HMAC 时间窗掩盖 NTP 故障。已有端口探针、自动修复上限、wan-watch 不重复部署。schema 变更另出迁移和回滚兼容说明，在隔离库测试。

验收：指标未知、失败、正常可以区分；历史故障恢复与人工确认可以区分；正常切节点不产生长期无法解释的告警；假数据和两机实测覆盖对应口径。真实 webhook 发送测试属于对外动作，任务范围明确包含时再做。

## P04：证明备份能恢复

盘点 backup.sh v3 是否覆盖 DB、密钥依赖、证书、Agent 包、DO/TX 配置。先核对最近成功时间与包清单，再在隔离目标恢复；不得覆盖生产卷、生产库或原始备份。

恢复演练是单独的写入任务，不包含在数据库只读探索授权内。记录包哈希、恢复命令、测试库标识、实际耗时、失败点、RPO/RTO。确认远程副本与加密密钥分离后，再实现专用拉取账户、自动落地、失败告警及保留策略。未证明恢复成功前不清理旧备份。

## P05：拓扑、配置和路径

整理设备 ID、机型、固件、LAN/WAN、上级、管理传输、反向端口、DNS/NTP、医院依赖及脚本调用者，制作脱敏 inventory 示例和受控真实配置。

区分本地源码名与线上部署名，尤其 mihomo 防火墙脚本、生产 overlay 和打包路径。将硬编码改配置前先列影响面。先做到从同一清单校验差异，再考虑自动生成。域名方案依赖用户已有域名或购买决定，不预设已拥有。

## P06～P08：维护、发布与扩展

- P06：确认可用恢复通道及备份后安排单机维护窗；SN-R1 host key 问题先做客户端兼容性实验，不能直接刷固件。系统升级与路由固件升级分批。验收心跳、时间、SSH、国内/境外、跨项目依赖。

## 对“一次性全部完成”的具体建议

从现有资料看，你的问题主要是**把不同完成标准的工作放在同一句目标里**：整理资料、分析生产、修改网络、升级软件和验证恢复，需要的证据与风险完全不同。目标写得越大，AI 越容易用“做了很多”替代“每项已验收”。

第二个不足是缺少唯一状态表：旧计划仍未勾选，后续报告又写已完成，下一位 AI 很容易重做。第三个不足是把“在线”“能启动”“有备份”当成整体可靠，尚缺权限、负向测试和恢复结果。第四个不足是把原始会话和凭证当交接资料，会扩大泄露范围，也增加阅读噪声。

可以一次性交代完整目标，但把执行拆成可交付批次：**一个总计划、一个当前任务、一个验收结果、一个下一步**。无需每一步都确认；提前明确允许的读写范围、可接受中断、验收标准和停止条件。建议先 P00 + D0～D2，再按实际发现排 P01/P02；不要在同一轮同时动密码、隧道、数据库结构和固件。
