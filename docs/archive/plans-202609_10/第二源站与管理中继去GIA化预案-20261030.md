# 第二源站热备与管理中继去 GIA 化预案（2026-10-30）

> 依据：round-cf-1030 多方评审结论 + 2026-10-30 全天实测。**当晚更新：方案 A 已实施部署完成；方案 D 已实测否决。**

## ⭐ 方案 A 实施记录（2026-10-30 晚，已完成待切换验证）

- BWG（74.82.193.113）已部署 `s-box-ws.service`（/usr/bin/sing-box，:2053 VLESS+WS+自签TLS，**UUID/path 与 GIA 主源站完全一致**——切换时设备零改动）+ `cf2053-guard.service`（2053 限 CF 段+回环，持久化）。
- 验证：本机 TLS=404 / WS 升级=101（与 GIA 主源站同行为）；部署链 PC→GIA→DMIT(txbackup key)→BWG 全程可用。
- **切换程序（66云源站故障时执行，预计 2-5 分钟）**：Cloudflare 控制台 → DNS → `cf` A 记录 `154.36.139.155` 改为 `74.82.193.113` → 保存即生效（橙云下 CF 内部生效快）。验证：设备侧 CF 节点 delay 测试恢复数值；`curl -k https://cf.k3x9m2.top:2053/`（经 CF）=404。回切同理改回。
- 注意：BWG 自身 TCP 被 GFW 封不影响此方案（CF 从境外回源）；但 BWG 机器/账号失效则备源同死（与主源同级的机器风险，两台不同供应商互备已大幅降低）。

## 方案 D 实测否决（2026-10-30 晚）

`GZ→BWG:22 TCP = FAIL`（8 秒超时；GIA→BWG 与 DMIT→BWG 均 OK）——GFW 对 BWG 是 **IP 级 TCP 封锁**（非仅 443），国内任何 TCP 都到不了 BWG，管理中继备份走 BWG 不可行。**剩余路径：F（新购香港/国内轻量中转，¥30-60/月）或 E（广州 API 副本，终极解）**。建议直接规划 E。


## 一、现状与风险（实测）

**出海面**：66云 GIA（154.36.139.155）同时承载 REALITY 主用 + HY2 备份 + CF 回源源站——服务器级故障（停机/欠费/封号）三条同死。
**今日新证据**：
- CF 中转链路已平台转正（节点 id=10，v22 发布验证），66云 IP 被 GFW 封时 CF 链预期存活（回源不跨墙）；
- **BWG-HY2（UDP 34567）实测可用**（演练中真实流量 103-143ms）——"BWG 被封"实为仅 TCP 443 被封，UDP 通路活着，链上已天然存在第二跳；
- 受控演练证实：主用被断 ≤30-60 秒自动切换、恢复后自动回切、全程流量不断。

**管理面（关键单点）**：设备心跳链 = 设备 → 广州(8443) → GIA(s-relay) → DMIT(API/DB)。**GIA 同时是出海主力、CF 源站、管理中继三重角色**——它一死：出海降级 BWG-HY2/CF（可用），但全舰队心跳/配置下发断（今日 15:21 事故实证），只剩设备 SSH 排障口（广州）独立存活。

## 二、方案选项（出海源站冗余）

| 方案 | 内容 | 成本 | 见效 |
|---|---|---|---|
| **A. BWG 复用为 CF 第二源站**（推荐首选） | BWG 东京已通（UDP 活着）、已装 sing-box：加 s-box-ws :2053（同一部署脚本重放，参数见 backups/.cf-node-params.json 的 rollback 旁注）；平时不接流量，66云源站故障时 CF 控制台把 A 记录 cf.k3x9m2.top 改指 BWG IP（或做 DNS Failover） | 0 元，半小时 | 66云服务器级故障时 CF 链 5 分钟内换源恢复；设备零改动 |
| B. 新购第二台 CN2 GIA 类 VPS | 独立于 66云 账号；同样部署 REALITY+HY2+s-box-ws 三件套 | ¥50-100/月 | 出海+CF 源站全套冗余 |
| C. 域名双记录轮询 | cf1/cf2 两条 A 记录分别指两源站，设备配两个 CF 节点 | 0 元 | 源站故障自动减一路，不需人工切 DNS；但两节点都过 CF、需两份节点绑定 |

注意：CF 免费版无健康检查 DNS Failover（付费才有），方案 A 的人工切换预计 5-10 分钟（演练前须先做一次 DNS 切换演练）。

## 三、方案选项（管理中继去 GIA 化）

| 方案 | 内容 | 成本 | 见效 |
|---|---|---|---|
| **D. BWG 中继备份**（推荐与 A 同步做） | BWG 上加 s-relay 同款（-L 8443→DMIT:8443）；广州侧加 gz-relay-bwg 备份服务（主 GIA 断时手动/脚本启用） | 0 元 | GIA 被封时管理面有第二路径；但 BWG TCP 443 被封说明 GZ→BWG 的 TCP 可达性需先实测（UDP 活≠TCP 活，部署前必须验证 GZ→BWG:22 SSH 可达） |
| E. 广州本地 API 副本 | 把 Go API+PG 主从复制搬到广州（用户 10-29 曾问"广州做管理后端"）；广州为主或 DMIT 为主均可 | 0 元（复用广州机）但工程量大：DB 迁移/双写/证书/入口切换 | 管理面彻底国内闭环，不再依赖任何境外中继；是最强解 |
| F. 新购国内中转 VPS | 轻量只跑 s-relay | ¥30-60/月 | 同 D 但不依赖 BWG 可达性 |

**推荐路线**：先做 A+D（零成本、半小时级、覆盖"66云被封"最可能场景）→ 观察 BWG TCP 可达性 → 中期做 E（广州 API 副本）彻底消除境外依赖。做 E 前须先解决：DMIT 管理库与广州副本的数据同步策略（每日 03:30 backup.sh 已推三端，可作基础）。

## 四、执行前置条件（届时逐项核对）

1. A：CF 控制台访问凭证可用的书面确认；BWG s-box-ws 部署后须复跑 WS 101 握手验证 + GIA 同款 2053 限源。

4. 全程红线不变：不动管理面现有通道、不重启在用服务、每步可回退。
