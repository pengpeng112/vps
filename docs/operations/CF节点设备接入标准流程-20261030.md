# CF 节点设备接入标准流程（SOP）— 以 R4 为原型，2026-10-30

> 适用：向任意 SN-R 设备接入 CF-CDN-GIA-01（平台节点 id=10，vless-ws）。
> 前置：平台 api 已支持 vless-ws（2026-10-30 部署验证）；GIA 源站 s-box-ws :2053 运行中且已限源 CF 段。
> 红线：CF 节点**不得设为 primary**（switch_node 的 expect_exit_ip 校验会失败——出口实为源站 IP 而非 CF 边缘 IP）。

## R4 全流程实录（可复制）

### 第 1 步：设备预检（只读，全部通过才继续）

```
心跳：logread | grep routermgmt | tail -1        → heartbeat ok
API：  curl http://127.0.0.1:9090/version          → 200
版本： 平台 DB desired_config_version = current_config_version（无待发布积压）
链路： NODE-PICK now=<主用> alive=true；US-MEDIA 非空
```

### 第 2 步：平台绑定（failover_priority=2 → 链尾）

```
POST /api/v1/assignments/batch
  {"device_ids":["<设备ID>"],"node_id":10,"is_primary":false,"apply":false}
SQL  update node_assignments set failover_priority=2
      where device_id='<设备ID>' and node_id=10
核对 select ... order by is_primary desc, failover_priority, priority desc  → CF 在末位
```

### 第 3 步：发布（batch apply=true，用该设备现有 primary 的 node_id）

```
POST /api/v1/assignments/batch
  {"device_ids":["<设备ID>"],"node_id":<主用节点ID>,"is_primary":true,"apply":true}
→ 响应含 task_id + version；轮询 tasks.status=ok、devices.current=desired
```
切换窗口：agent 下载校验→备份→替换→mihomo 重启（含 geodata 加载约 30-60 秒，该设备外网瞬断）。

### 第 4 步：设备侧验收

```
grep -c $'\r' config.yaml == 0        # 无 CRLF
grep -c '^- name:' == 0               # 无顶格节点（v21 事故防线）
9090 /proxies/NODE-PICK all 含 CF-CDN-GIA-01 且在末位
9090 /proxies/US-MEDIA all 非空（新模板=[NODE-PICK] 或含 LAX）
路由实测：US-MEDIA delay(gstatic/youtube) 有数值；NODE-PICK delay 正常
logread 心跳恢复 ok；平台 metrics exit_ip=<主用出口>
```

### 第 5 步：回退（如需）

设备侧恢复备份 + PUT /configs 热重载；平台侧删绑定（node_id=10）+ 重发布。
CF 链路整体回退：GIA `systemctl stop s-box-ws` + CF 删 A 记录（设备节点仍在但不可达，NODE-PICK 探测自动跳过）。

## 已知行为与限制

- 发布会覆盖设备侧一切手工改动（DMIT-HY2 等手工节点会消失——平台节点表为准，属预期）。
- CF 节点质量依赖 联通→CF 国际段：延迟 300ms-5s 波动、偶发超时；NODE-PICK 探测自动规避（不健康即跳过）。
- 每站点最优 CF 边缘 IP 可能不同：当前统一钉 104.18.32.7（坊子实测最优）；其他站点若实测差，可另建节点（换 host IP）分别绑定。
- US-MEDIA 空组问题随本流程一并修复（新模板显式成员渲染）。
