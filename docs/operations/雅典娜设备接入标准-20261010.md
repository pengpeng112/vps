# 雅典娜类设备接入标准（异构 OpenWrt 设备接入 DMIT 管理面）— 2026-10-10

> 依据 2026-10-10 雅典娜（JDCloud RE-CS-02 AX6600 / LibWrt）v3 迁移实战沉淀。
> 与《新SN-R1刷机录入SOP-自动化》互为补充：SN-R 系走 flash-snr.py 全自动；**本标准适用于非 SN-R 系异构设备**（已有系统在跑、不能重刷、只做管理面接入/升级）。
> 执行前必读：`AGENTS.md` 红线段、`docs/current/当前状态.md` 顶部。口令只从 `backups/SN-R系列凭证总览.md` 读取。

## 1. 设备画像（识别特征）

| 项 | 雅典娜实况 | 对接入的影响 |
|---|---|---|
| 硬件/系统 | JDCloud RE-CS-02 AX6600，LibWrt（OpenWrt 系，busybox 1.37） | procd/rc.common 可用，v3 init 可直接套 |
| 防火墙 | **nftables**（fw4） | **禁一切 iptables 脚本**（红线） |
| SSH 服务端 | dropbear 2025.89 | ed25519 密钥可用 |
| SSH 客户端 | /usr/bin/ssh（dropbear 客户端） | 支持 -o ExitOnForwardFailure（R2-R5 同款验证过） |
| 工具缺口 | **无 base64、无 coreutils install** | 用 `openssl base64 -d`、`cp+chmod` 替代 |
| 工具冗余 | **有 sftp-server**、curl 8.15、openssl 3.5 | 文件传输走两跳 scp 最稳 |
| 业务依赖 | mihomo(openclash 版)+医院/公司转发+borrow18 SNAT | 动手前逐条记录 nft 表清单与 mihomo PID |

## 2. 与 SN-R 标准流程的差异对照

| 环节 | SN-R 系（flash-snr.py） | 雅典娜类（本标准） |
|---|---|---|
| v3 隧道 | 四端点（DMIT+TX+BWG+DO） | **三端点**（DMIT+TX+BWG；DO 端点不加，避免向将退役机增条目） |
| 密钥 | 新刷生成 RSA | 沿用设备现有 `/etc/routermgmt/id_dropbear_mgmt`（ed25519） |
| onboot-hooks | cron 恢复+QUIC iptables | **仅 cron 恢复**（模板见 §4 文件清单） |
| 每日 00:00 重启 | 加 | **不加**（家庭/医院依赖设备，重启须用户明示） |
| 密码 | 全舰队统一 | **不统一**，异构设备保持自有口令，台账单列 |
| handlers/switch_node | 部署 | **不动**（代理发布体系不同；平台侧绑定为 0 前不会推送） |
| mihomo/代理 | 部署+发布 | **完全不动**（代理迁移属计划 D2b，单独授权单独做） |
| 录入方式 | flash-snr 全自动 | `scripts/athena-enroll.py`（平台录入+enroll 引导包） |

## 3. 标准流程（七步）

### 第 1 步：只读侦察（红线检查）

经现有路径进设备，记录：`cat /tmp/sysinfo/model`、`nft list tables`（**逐表名记录**）、mihomo PID、`/etc/routermgmt/` 现有文件清单、tunnel.conf 键名（v1 是 `VPS_SSH_PORT`，v3 是 `VPS_PORT`——**沿用旧键名会静默降级**）、出站连通（`ssh -o BatchMode=yes` 探测三个 VPS:28722，"Didn't validate host key"=TCP 通）。

### 第 2 步：VPS 侧 authorized_keys 预置

- 取设备 `/etc/routermgmt/id_dropbear_mgmt.pub`。
- DMIT：舰队格式，排障口用空闲 1322x（先 `grep permitlisten /root/.ssh/authorized_keys` 核占用）：
  `no-agent-forwarding,no-X11-forwarding,no-pty,permitopen="127.0.0.1:8443",permitlisten="127.0.0.1:132XX" <pubkey> <注释>`
  改前备份 authorized_keys，改后 `sshd -t && systemctl reload sshd`。
- TX/BWG：仅 -L 备用条目（`permitopen="127.0.0.1:8443"`，无 permitlisten），镜像该机上现有路由器条目格式。DMIT 上有 txbackup 密钥可代登 TX(ubuntu)+BWG(root)。
- **注意**：9 月实验可能已预置过旧条目（permitlisten 18222 等）——先 grep 设备公钥指纹再决定改写还是新增。

### 第 3 步：平台录入

本机开 `-L 8444:127.0.0.1:8443` 到 DMIT，`MGMT_API_BASE=https://127.0.0.1:8444 python scripts/athena-enroll.py`（口令/TOTP 自动从台账读）。产出 `backups/.athena-enroll.json`（600，gitignored）。录入后 PATCH `traffic_alert_hourly_mb=2048`。

### 第 4 步：文件清单（md5 门禁基准）

仓库源+生成件，全部比对 md5 后落盘（本次实测 md5 前缀）：

| 文件 | 源 | 权限 | 本次 md5 |
|---|---|---|---|
| /etc/init.d/mgmt-tunnel | mgmt/agent/init/mgmt-tunnel-v3 | 755 | 3fcb54af… |
| /etc/routermgmt/tunnel.conf | 生成（三端点，RSSH=132XX） | 600 | — |
| /etc/routermgmt/routermgmt-agent.sh | mgmt/agent/ | 700 | 86db9c41…+多端口补丁 |
| /etc/routermgmt/agent.conf | enroll 包生成（DEVICE_ID/HMAC_KEY/MGMT_URL/SIGN_PUB） | 600 | — |
| /etc/routermgmt/sign_pub.pem | enroll 包 sign_public_key | 644 | — |
| /etc/routermgmt/mgmt-port-discovery.sh | mgmt/agent/ | 755 | 373c8dc8… |
| /etc/routermgmt/connlog.sh | mgmt/agent/ | 755 | 86d97188… |
| /etc/routermgmt/netprobe.sh | mgmt/agent/ | 755 | 9fbb150a… |
| /etc/routermgmt/onboot-hooks.sh | **雅典娜变体**（仅 cron 恢复，无 iptables 无每日重启） | 755 | — |
| /etc/init.d/routermgmt | mgmt/agent/init/ | 755 | aac14bf2… |

tunnel.conf 关键差异：`VPS_PORT=28722`（非 v1 的 VPS_SSH_PORT）；`MGMT_TARGET=127.0.0.1:8443`；`RSSH_TARGET=127.0.0.1:22`。

### 第 5 步：传输（两跳 scp，唯一可靠路径）

本机→DO(28722,密钥)→设备(1822X,sshpass)。设备有 sftp-server 时 scp 直接走 sftp 协议：
`scp -P 28722 -i DO密钥 staging/* root@DO:/tmp/` 然后 DO 上 `sshpass -f pw scp -P 1822X /tmp/* root@127.0.0.1:/tmp/`。
落盘后逐文件 `md5sum` 与本地清单对拍，**不一致不得装机**。

### 第 6 步：安装+重启（crond 触发，唯一可靠方式）

安装脚本要点：先备份（`*.bak-athena-$TS` 全套）→ `cp+chmod` 落位（无 install 命令）→ agent 打多端口补丁（flash-snr 同款 awk/sed，`sh -n` 门禁）→ cron 三行+rc.local 钩子+respawn 归一 `3600 0 0` → init enable → 预检（tunnel.conf 键数 8、agent.conf 键数 4、onboot 无 iptables 命令）。

**重启必须 crond 触发**（sshpass 双跳链上 nohup 后台任务会随会话死亡，实测翻车）：
临时 cron 行 `* * * * * sh /tmp/r3.sh` + r3.sh 自删该行后执行 `pkill 旧隧道 → mgmt-tunnel restart → routermgmt restart`。

### 第 7 步：验收（15 项，全过才算完）

1. 新排障口在 DMIT 监听；2. 经新口回连 DEVICE_ID 正确；3. 隧道实例数=4（-L/-R/TX/BWG）；
4. 18443 健康 200；5. /tmp/mgmt_active_port=18443（分钟间隙读到缺失属正常，agent 回落 conf 固定值）；
6. agent 进程 1+多端口补丁存在；7. 心跳新库秒级刷新且持续≥3 个周期；
8. **旧库心跳冻结**（记录冻结时刻=切换前最后一拍）；9. cron 三行+rc.local 钩子；
10. netprobe 日志新鲜；11. connlog 基线建立（采样器，日志待流量≥1MB 才有行，空文件非故障）；
12. **mihomo PID 与迁移前一致**（代理零扰动铁证）；13. **nft 表清单与迁移前逐表一致**（医院/公司依赖表 borrow18 必须在）；
14. respawn=3600 0 0 + rc.d 自启链接；15. 平台 approved+告警阈值生效。

## 4. 已知坑（全部实测踩过）

1. **sshpass 双跳链上 nohup/后台任务随会话死**——重启类操作必须 crond 触发（§6）。
2. **无 base64**——命令包装用 `openssl base64 -d -A`；且 dropbear 命令串过长会截断（>4KB 实测丢字），命令内嵌大 payload 不可靠，**两跳 scp+md5 是正解**。
3. **无 coreutils install**——cp+chmod 替代。
4. **嵌套引号地狱**——经 DO 中转的命令若本体含单引号，必须整体 base64 后 `echo B64 | openssl base64 -d -A | sh`，杜绝双层引号拼接。
5. **v1→v3 conf 键名差异**（VPS_SSH_PORT vs VPS_PORT）——沿用旧键名不报错但降级，装机后必须核对键数。
6. **/tmp/mgmt_active_port 分钟级缺失**——discovery 每分钟重写，读到缺失等 60 秒再判，勿当故障。
7. **未持久化 nft 规则会被系统刷新清掉**（hosp_fwd 实证：10-09 部署的运行时规则于 10-10 被外部刷新清空，与本接入无关——connlog/discovery 源码级无 nft 交互）。**任何 nft 业务规则验收通过后立即写入 /etc/nftables.d/ 持久化**。

## 5. 回退（已验证路径存在即生效）

设备侧：`cp /etc/routermgmt/{tunnel.conf,agent.conf,sign_pub.pem,routermgmt-agent.sh}.bak-athena-$TS 原位 + cp /etc/init.d/{mgmt-tunnel,routermgmt}.bak-athena-$TS 原位`，crond 触发重启两服务 → 心跳回 DO 旧库（旧设备记录未删）。VPS 侧：authorized_keys 有带时间戳备份，恢复即删新条目。平台侧：新设备记录保留无害（不再有心跳即自动离线）。
