## 3. 已确认的问题与原因

### 3.1 P0：雅典娜反向 SSH 端口假健康

现象：

- 雅典娜 `mgmt-tunnel` procd 实例显示 running。
- 同一 SSH 会话提供的本地管理转发 `127.0.0.1:18443 -> VPS:8443` 可用，所以 Agent 心跳正常。
- 该会话配置的远程转发 `-R 127.0.0.1:18222:127.0.0.1:22` 没有在 VPS 产生监听端口。

根因判断：

- 当前隧道把 `-L` 和 `-R` 放在同一个 Dropbear SSH 会话中。
- 远端 `-R` 绑定失败时，进程没有退出；procd 只检查进程存活，不检查每个 forward 是否建立。
- 源码模板 `mgmt/agent/init/mgmt-tunnel` 甚至只包含 `-L`，线上雅典娜和 SN-R1 使用了各自临时定制版，源码与生产漂移。
- 没有对 VPS `18222/13222` 的定时探测、告警和自动修复。

风险：管理台显示在线，但雅典娜无法经 VPS SSH 进入；故障时才暴露问题。

### 3.2 P0：路由器隧道密钥仍使用 VPS root 身份

VPS root `authorized_keys` 对两台路由器密钥设置了 `no-pty`、`permitopen`、`permitlisten`，比无限制密钥好，但仍不理想：

- 隧道设备私钥一旦泄漏，攻击面直接落在 root 登录身份。
- `no-pty` 不等于禁止非交互命令执行。
- SSHD 的 root 匹配规则为转发场景开放了 TCP forwarding，配置容易因后续改动扩大权限。

目标：每台路由器使用独立、无特权、无 shell 的 tunnel 用户，按设备限制 `permitopen` 和 `permitlisten`。

### 3.3 P0：敏感材料散落在工作目录

已发现但未读取/传播其具体内容的敏感材料类型：

- `mgmt/deploy/.env`
- `backups/.mgmt-token`
- `docs/wg-*.conf`、手机 WG 二维码
- `docs/设备引导包-雅典娜.json`
- `scripts/ubus_token.txt`、`scripts/login_acl.json`
- 多个 Python 脚本中的路由器管理口令
- 含 VLESS UUID/Reality 参数及设备后台 UUID 的交接文档和模板

风险：误发目录、同步网盘、提交公共仓库或让不可信 AI 扫描时会扩大泄漏面。

### 3.4 P1：监控指标语义错误或缺失

- `wg_alive` 当前只检查 `/sys/class/net/wg0` 是否存在，不检查最近握手；雅典娜显示 true，但 VPS 上该 peer 的最近有效握手已是约 4 天前。
- `wan_ip` 两台均为空。Agent 在设置 `RM_WAN_IF/WAN_IF` 后不会再从 ubus 读取 `_wanip`，属于采集逻辑缺陷。
- 节点健康只有管理员手动 TCP probe，当前一直 `unknown`；TCP connect 也不能代表 VLESS/Reality 鉴权和真实出口可用。
- 反向 SSH 端口没有指标。
- 旧离线告警不会在心跳恢复时自动 resolved，只能人工确认，告警页容易积累噪声。
- 代理流量为 `partial` 是设计上的轮询估算，界面虽有提示，但不适合作为计费数据。

### 3.5 P1：备份仍有单点与人工步骤

- VPS 本机每日备份正常。
- 最新 v2 备份已包含数据库、环境密钥、证书、WG、sing-box、SSH、UFW 和源码，内容较完整。
- 异地副本仍依赖人工双击脚本；当前本地最新副本比 VPS 最新副本旧一轮。
- 备份包包含高价值密钥，若不加密直接落到普通磁盘，泄漏影响很大。
- 当前仅验证过数据库恢复，没有按 v2 包做“新机完整恢复 + 路由器重新上线”的演练。

### 3.6 P1：VPS 待更新且需要重启

- 系统提示需要重启。
- 有 Kerberos/netplan 等更新待安装。
- 单 VPS 架构没有热备，直接重启会同时中断代理、管理台和跳板；必须放在维护窗执行并做重启后全链路验收。

### 3.7 P1：文档、源码和生产配置发生漂移

- `mgmt/docs/开发进度.md` 仍写“Session 2 未开始”，但 WireGuard、真机联调、生产 TLS、备份等实际已做。
- `mgmt/docs/验收记录.md` 仍把多项生产能力写为未验证。
- 工位当前默认网关为 SN-R1，而文档中存在电脑有线走雅典娜的旧拓扑。
- 通用 `mgmt-tunnel` 源码未包含两台生产机的远程 SSH forward。
- 部分本地脚本绑定旧的本机源 IP `192.168.2.105`，当前电脑地址为 `192.168.132.105`。
- SN-R1 WAN 地址通过 DHCP 变化过，尚未确认已在雅典娜设置静态租约。

### 3.8 P2：扩容前必须补的能力

- 每设备独立 VLESS UUID 尚未落地，当前共享凭据会扩大单设备泄漏影响。
- 自动故障转移、真实 webhook 通知、50 设备压测尚未完成。
- IP 地址在多处硬编码，VPS 换 IP 会产生大面积人工修改。
- 前端存在中危依赖公告和 bundle 过大问题。
- 当前目录不是 Git 仓库，无法审查差异、打版本标签、可靠回滚。

## 阶段 2：把路由隧道从 root 身份迁走（P0）

### 目标

设备密钥泄漏时，攻击者最多建立被允许的端口转发，不能获得 VPS root 命令执行能力。

### 操作顺序

- [ ] 为每台路由器创建独立账户，例如 `tunnel-athena`、`tunnel-snr1`，不得共用账户和密钥。
- [ ] 账户无 sudo、无密码、无可用交互 shell；先在测试账户验证 `ssh -N` 转发可工作。
- [ ] 每个账户的 `authorized_keys` 使用 `restrict,port-forwarding`，并分别限制：

  - `permitopen="10.10.0.1:8443"`
  - `permitlisten="127.0.0.1:18222"` 或 `13222`

- [ ] SSHD `Match User` 只为 tunnel 账户开启 TCP forwarding，关闭 agent/X11/TTY，并限制源行为。
- [ ] 执行 `sshd -t`；保留旧 root 隧道，先用新账户建立并验收一台。
- [ ] 雅典娜迁移成功 30 分钟后再迁 SN-R1。
- [ ] 两台均稳定后，从 root `authorized_keys` 移除对应设备公钥。
- [ ] 用设备私钥做负向测试：

  - 不能执行 `id`、`sh` 或任意远程命令。
  - 不能监听未授权端口。
  - 不能连接未授权目标。
  - 能建立规定的 `-L`/`-R`。

### 验收

- root `authorized_keys` 不再包含路由器隧道密钥。
- 两台路由心跳、18222/13222 与代理均连续稳定至少 30 分钟。
- 非交互命令执行负向测试失败。

### 回滚

- 在保留旧 root key 的迁移窗口内切回旧用户。
- 新账户失败时不要删除旧 key；只有新链路完整验收后才清理。

## 阶段 4：修复监控口径和告警闭环（P1）

### 4A. WAN 指标

- [ ] 将 `wg_alive` 拆成：`wg_interface_present`、`wg_latest_handshake_at`、`wg_handshake_fresh`。

### 4C. 节点健康

- [ ] 后台定时做 TCP 探测，但 UI 明确标记为“端口可达”。
- [ ] 增加至少一个真实代理合成探测：完成 VLESS/Reality 握手并访问独立探测地址，验证出口 IP。

- [ ] alerts 表增加 `resolved_at`/`resolved_reason`，区分 active、resolved、acked。
- [ ] 设备恢复心跳时自动 resolve 对应 offline 告警。
- [ ] rollback 后续成功时将旧告警标为已恢复，但保留历史。
- [ ] 配置真实 webhook（Bark/Telegram/企业微信任选其一）并做失败重试与死信展示。
- [ ] 告警内容不得包含配置正文、UUID、IP 私钥或 token。

### 验收

- UI 不再把“接口存在”当成“WG 正常”。
- 节点状态不再长期 unknown。
- 制造一次短离线后能触发并自动恢复告警。

## 6. 不应执行的“优化”

- 不要为了让 `wg_alive=true` 而反复重启公司网下的 WG；TCP 隧道是当前有意的降级方案。
- 不要删除 `10.1.2.18`，除非医院白名单已迁移并完成外网 Claude 全链路复验。
- 不要关闭 SN-R1 的 QUIC/UDP 443 丢弃规则；它是当前公司网兼容性修复。
- 不要启用硬件 NAT 后只看带宽；它可能绕过透明代理与限速规则。
- 不要把雅典娜和 SN-R1 的防火墙脚本互换，两者分别是 nftables 与 iptables。
- 不要把 SN-R1 的 `-R` 目标改成 `127.0.0.1:22`，其 Dropbear 当前只监听 LAN 地址。
- 不要通过公开 DNS 暴露管理台 8443；管理面应继续只绑定 WG 地址/SSH 转发。
- 不要为了方便把 UFW 关闭或把管理台绑定到 `0.0.0.0`。
- 不要把自签管理证书改成 `curl -k` 之外的“永久忽略一切证书”方案；最终应部署受控 CA/证书 pinning。
- 不要直接改 `MASTER_KEY`；先设计密文重加密迁移。

## 7. 每批变更后的统一验收清单

按顺序执行，任一失败即停止：

### 7.1 VPS

```bash
systemctl is-active ssh sing-box wg-quick@wg0 fail2ban docker cron
cd /opt/mgmt/deploy && docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
curl -skf https://10.10.0.1:8443/api/v1/health
ss -lntup
ufw status numbered
df -h /
free -h
```

通过标准：服务 active、容器 healthy、API 200、只开放设计端口、磁盘低于 80%。

### 7.2 反向通道

```bash
for p in 18422 18322 18222 13222; do
  timeout 3 nc 127.0.0.1 "$p" | head -1
done
```

通过标准：四个端口都存在并返回预期 SSH banner；监听地址只能是 VPS loopback。

### 7.3 路由器控制面

- 两台最后心跳小于 90 秒。
- `clash_alive=true`。
- WAN IP 非空。
- 管理传输模式显示为实际使用的 TCP SSH 或 WG。
- 配置版本未意外回退。
- 没有新增 failed/rolled_back 任务。

### 7.4 数据面

- 国内站点至少测试两个，确认可访问并记录是否直连。
- 境外站点至少测试两个，确认出口为预期 VPS。
- DNS、TCP、HTTPS 都要测，不能只 ping。
- 浏览器验证一次 HTTP/3 被阻断后可正常回落 TCP。
- 两台路由器分别测试，不用一台的结果代替另一台。

### 7.5 医院跳板

- 工位到 `10.10.8.84:40022`、`10.10.8.83:22`、`10.20.1.153:22` 均可连。

- 用受限 jump key 做实际握手，确认不能访问白名单外端口。

### 7.6 负向安全测试

- 公网 22、8443 不可访问。
- tunnel 设备 key 不能执行远程命令。
- jump key 不能获取 shell，不能访问许可外目标。
- 管理台错误密码/TOTP 仍被拒绝。
- 日志与 API 响应不回显秘密。

## 10. 最终完成标准

以下条件全部满足后，系统才可从“基本可用”提升为“可稳定运营/可扩容”：

- 两台路由器的心跳、代理、远程 SSH 均有独立健康状态，不再出现半通假健康。
- 路由器密钥不再以 VPS root 身份登录。
- 源码目录不含生产秘密，并由私有 Git 管理。
- WAN、WG、节点健康指标语义准确，告警能自动恢复闭环。
- 最新备份自动异地加密保存，并完成过新机完整恢复演练。
- VPS 更新后完成全链路复验，重启不依赖人工临时修补。
- 生产配置由单一 inventory/模板生成，源码与线上没有未解释漂移。
- CI 覆盖 Go、前端、Agent BusyBox e2e、secret scan、依赖与镜像扫描。
- 每设备独立代理凭据、故障转移、灰度发布和批量设备并发预算完成。
