> 审查范围：BWG 东京服务端、TX 腾讯服务端、R2/R3 客户端（mihomo）配置 + 自身暴露面。

> 用户关切：①不被识别（防封）②加密强度。结论先行：**主用链路为现役顶配方案，配置

## 1. 主用链路（R2/R3 → BWG 东京）：vless + REALITY + Vision — 现役最强抗识别组合

实测配置（服务端 sing-box + 客户端 mihomo 双侧核对一致）：

| 防线 | 配置 | 作用 |
|---|---|---|
| REALITY | 启用，SNI 借用 `www.microsoft.com`，握手转发真微软 | **抗主动探测**：GFW 探针打到 443 收到的是真微软证书与指纹，没有自签/域名等代理特征 |
| 流控 | `xtls-rprx-vision`（双侧一致） | 消除 TLS-in-TLS 的包长/时序特征（旧版 vless 的经典识别点） |
| TLS 指纹 | 客户端 `client-fingerprint: chrome`（uTLS） | ClientHello 模拟 Chrome——Go 程序默认 TLS 指纹是被识别的经典特征，此项配置正确 |
| 传输 | 纯 TCP 443，无 ws/grpc/域名 | 无额外协议特征，与正常 HTTPS 长连接同类 |
| 加密 | TLS 1.3（X25519 + AEAD） | 与现代浏览器同级，内层流量全部在这层加密内 |

**防线在工作的实战证据**：BWG sing-box 日志持续出现
`REALITY: processed invalid connection`（来自 212.102.x/87.236.x 等扫描器）——
探针被正确拒绝，正是 REALITY 的设计行为。

TX 腾讯的 vless 入站（VPS-TX-SG-02，备用）同为 REALITY+Vision+微软 SNI
（short_id 16 个），配置同样规范。

## 2. 风险认知（按用户关切排序）

### 2.1 "封 IP"与"封号"要分清——真正的封号风险在腾讯侧

- **BWG 东京（IT7，海外厂商）**：代理用途长期默许，最坏结果是 **IP 被墙**
  （CN2 GIA 段属重点监测对象）→ 换 IP 约 $8 即恢复，**不封账号**。REALITY 就是
  针对这个威胁的主防线。
- **TX 腾讯（国内厂商海外轻量）**：国内厂商对代理用途存在**厂商侧风控/封号先例**。
  当前腾讯仅承载备用+体检测试流量（量小），风险低；但**若将来启用"视频分流走腾讯"，
  该机流量大增会放大厂商侧风险**——分流落地决策时应把此因素计入，落地后观察。

### 2.2 hy2 是当前配置里的相对弱链（建议调整备用序）

- hy2/QUIC 协议族 2024—2025 年起被针对性封锁（大量先例），UDP 特征显著；
  且 R3 客户端该节点 `skip-cert-verify: true`。
- 当前 R3 备用序：BWG → TX-HY2 → TX-VLESS。**从隐蔽性看 TX-VLESS（REALITY）比
  TX-HY2 高一个量级，建议调为 BWG → TX-VLESS → TX-HY2**（node_assignmissions
  failover_priority 一行变更，等用户确认）。

### 2.3 无法靠配置消除的部分（如实告知）

长流大流量（看视频）的**流量行为统计特征**（时长/吞吐曲线）任何协议都有，
DPI 侧统计分析理论可见。CN2 GIA 商用线路对这类宽容度高——这是选它的理由之一。

## 3. 加密强度清单

| 通道 | 加密 | 评级 |
|---|---|---|
| 代理主链（vless+REALITY） | TLS 1.3（X25519+AEAD） | 顶配 |
| 管理隧道（路由器↔VPS SSH） | SSH（Ed25519 密钥，现代套件） | 良好 |
| 管理台 API/UI | HTTPS 自签，仅 WG 内网+127.0.0.1（不暴露公网） | 良好 |
| 数据库敏感字段 | MASTER_KEY 加密（AES-GCM） | 良好 |
| 温备每日同步 | SSH/SCP 加密通道+密钥认证 | 良好 |
| hy2 备用 | QUIC TLS1.3，但 skip-cert-verify（跳过证书验证） | 弱（建议降为末位备用） |

## 4. 自身暴露面（与"被识别"无关，但属安全审查应报项）

- **R3 的 WiFi 仍是出厂默认（WIFI-7880 / 12345678）**：进入 WiFi 者可用路由器开放
  代理端口 7890（LAN 设计使然）与 LuCI。**这是当前体系里最真实的一个弱点**；
  变更方案已在案（等客户时间窗，见当日"密码三类统一"条目）。
- mihomo API（9090）已绑 127.0.0.1，无公网暴露 ✅。
- **BWG sshd**：`PermitRootLogin yes` + `PasswordAuthentication yes` + 无 fail2ban，
  近 3 天 25 次爆破尝试（量小）。建议：改密钥登录或至少部署 fail2ban。
- DO 管理面不碰代理流量、sshd 有 99-hardening（白名单/密钥），面最小 ✅。

## 5. 待用户确认的两个动作

1. **备用序调整**：R3（及后续设备）failover 改为 BWG → TX-VLESS → TX-HY2（提升
   故障切换后的隐蔽性）。
2. **BWG sshd 加固**：fail2ban（或密钥-only，保留一条应急通道）。
