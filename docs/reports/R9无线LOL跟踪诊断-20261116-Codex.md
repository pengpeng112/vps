# R9 无线 LOL 现场跟踪诊断（2026-11-16，Codex）

> 范围：用户通过 WiFi 复现，远程只读跟踪 R9；不改无线、mihomo 配置、代理选择、路由、防火墙、隧道或定时任务，不重启服务。仅启动有时间上限的诊断采集和轻量 ICMP 探测。
> 本文区分运行实测、用户反馈与原因推断。纯读会话，无生产配置变更。

## 结论

**发现一项确定的网络配置故障：LOL 域名对应的 fake-ip UDP 没有被代理接管，直接从 WAN 发往上级网关，持续无响应。它是本次黑屏、无法连接服务器的主要嫌疑；最终因果需要修复后按相同流程复测确认。**

本轮不能继续沿用此前“只有一个无关 UDP 包”“网络层全绿”“全部由无线引起”的结论。

## 确定故障的证据链

1. 从运行设备 `/etc/mihomo/cache.db` 读取副本，在本机临时目录通过 bbolt 精确查询 fakeip 桶的二进制 IP 键。没有依据字符串邻接猜测映射，没有修改设备缓存；临时数据库副本使用后删除。

   | 假 IP | 精确映射域名 | 本轮观察 |
   |---|---|---|
   | 198.18.2.74 | gpp-tj100-1.lol.qq.com | UDP 13671 持续发送，无回包 |
   | 198.18.2.8 | tqos.gamesafe.qq.com | UDP 8080/8081 无回包 |
   | 198.18.1.79 | tqos.anticheatexpert.com | UDP 8081 无回包 |
   | 198.18.2.40 | open-data-router-api.wyjsq.com | 少量 UDP，不能据域名判断具体进程 |

2. 11:44:41.584450—11:47:56.141532 的同步抓包：电脑向 `198.18.2.74:13671` 发送 **1770 个 UDP 包、918630 字节 UDP 负载**。LAN 和 WAN 两侧数量、长度及时间对应；没有观察到该目标返回 UDP。后续仍持续重试，1770 只是这个统计截点的数量。

3. 11:47:57 的内核连接跟踪：

   ```text
   src=192.168.132.182 dst=198.18.2.74 sport=56246 dport=13671
   packets=1788 bytes=978036 [UNREPLIED]
   reply: packets=0 bytes=0
   ```

   conntrack 字节包含 IP/UDP 头，不能直接与上述 UDP 负载字节数比较；采样截点也不同。

4. 同时查询真实路由：

   ```text
   198.18.2.74 via 192.168.3.1 dev wan src 192.168.3.19
   ```

   说明设备将 fake-ip 当作普通目的地址发给上级，未在本机还原域名并连接真实服务器。

5. 实际运行配置仅见 `redir-port: 7892`；现场 MIHOMO 链只有 TCP REDIRECT，mangle 表未见 UDP TPROXY 接管。官方文档也明确 redir-port 只处理 TCP：<https://wiki.metacubex.one/en/config/inbound/port/>。

6. 通过设备直接向 223.5.5.5 查询该 LOL 域名，A 记录本轮返回 `42.81.179.215`，与发往 WAN 的 `198.18.2.74` 不同。没有向真实服务器端口发送额外 UDP 探测。

**推断边界**：可确定该 LOL 域名的 UDP 路径失效，不能仅凭域名断言它承担哪一个游戏内部阶段，也不能宣称已经排除所有客户端或服务器问题。修复后的复测是最终闭环。

## 为什么此前的“UDP 正常”不足以排除故障

另一条真实地址连接 `123.233.249.133:55457` 确实存在双向流量。在 11:43:53—11:47:56 的统计窗口，WAN/LAN 两侧分别均观察到：

- 电脑发出 37698 个 UDP 包；
- 服务器返回 10831 个 UDP 包。

这些是不同方向的包数，不能互相相减来计算丢包率。LAN/WAN 数量吻合，支持该条连接在 R9 转发过程中没有明显的包数缺口；它**不能证明另一条 gpp 域名连接也正常**，也不能证明无线已把所有下行包交付到电脑或应用。

## 无线、上级网关和资源对照

- 同时进行 25 次、1 秒间隔的 ICMP 探测：
  - R9 → 电脑：25/25，0% 丢包，min/avg/max = **0.909/1.543/3.526ms**。
  - R9 → 上级网关 192.168.3.1：25/25，0% 丢包，**0.635/0.871/1.040ms**。
- 这是短时、小包对照，不能证明全时段或大包无线质量，但本轮没有发现这一窗口的持续无线断连。
- 整个 ra0 的增量 CRC 统计存在明显错误增长，多个约 10 秒窗口的比值在 11%—33% 左右，发送失败计数也增长。这些是整个无线接口的驱动计数，可能包含其他接收帧和统计口径因素，**不可直接当作这台电脑的 IP 丢包率**。
- `stainfo` 能读到目标电脑，RSSI 约 -17/-12dBm、HE/40MHz；表格列布局不齐，不用尾部字段作精确逐站点失败率结论。`get_mac_table` 用户态工具报段错误，未再使用；未据此判断无线驱动崩溃。
- CPU 单次采样约 90% idle；API health 200，未发现明显资源耗尽证据。
- UCI 配置 `RADIO2G.channel=1`，但 `iwconfig ra0` 实测 **Channel:3**，dat 为 **Channel=0;0**。配置与运行不一致已确认；本轮没有修改或重载。
- 11:41 时设备 uptime 约 11h41，表明本日零点后持续运行。因此先前文档“上午改完后，当晚零点重启已回滚”的时间叙述不能采信。dat 何时、由谁写回仍未查清。

## 最小修复方向（仅方案，尚未实施）

优先考虑通过广州平台渲染并发布 R9 的配置，在 DNS fake-ip-filter 中对已确认涉及的 LOL 域名返回真实 IP，使本来不经 UDP 代理的国内游戏流量能直接到达真实地址。fake-ip-filter 与路由 DIRECT 是两项不同设置，已有 DIRECT 规则不能代替 DNS 排除。

- 首要覆盖已实证的 `gpp-tj100-1.lol.qq.com`；考虑同服务动态主机时可评估 `+.lol.qq.com`，不应未经评估扩大为所有国内域名。
- gamesafe / anticheatexpert 已确认存在相同 UDP 路径故障，可在方案中明确范围并一并核查。
- 不手工编辑设备 config.yaml，不在当前重试现场先改全舰队 TPROXY、DNS 模式、无线或节点。
- 变更必须先检查 R9 平台 preview、发布副作用和回退版本。生效后电脑可能仍持有旧 DNS/进程内映射，需要在合适时机重启游戏客户端并更新 DNS 缓存，再抓包验证真实目的地址和回包。
- 只有“此前失败步骤成功完成 + 新会话不再将上述 UDP 发往 198.18/16 + 实际服务正常回应”，才能关闭该故障。
