# 网络稳定性只读诊断报告

采集日期：2026-09-27，约 08:01—08:09，Asia/Shanghai。对象：当前 Windows 电脑、雅典娜、SN-R1、DO、腾讯新加坡。后续方案见 [执行计划](../../plans/网络稳定性改进与单路由器迁移执行计划-20260927.md)。

本轮实际通过 SSH 连接了两台路由器和两台服务器；没有修改路由、DNS、节点选择、防火墙、服务或任务，没有部署。仅查询状态、发起少量 DNS/HTTP/ICMP 探测，并在 SN-R1 做了 8 秒、限目标且只输出 SYN 头摘要的抓取；探测会产生正常连接日志和 DNS 缓存，不等于零运行时影响。没有读取数据库或业务页面正文。

## 1. 结论

1. **gstatic 卡住已经复现。最强证据指向“真实 DNS 答案差异 + DIRECT 出口不可达”，不是已证实的 fake-ip 自环。** 两台 mihomo 配置都有国内 DoH，但内核 DNS API 对同域名分别返回 `114.250.68.34` 与 `142.251.12.94`。指定前者，两台均成功；指定后者，两台均失败。SN-R1 WAN 实际向后者发 SYN，上游雅典娜将该连接再次接入 Redir 并判定 DIRECT。
2. **DO 方向晚高峰劣化有历史原始日志支持。** 本次从设备读取的 09-25/26 日志中，雅典娜 20:00—22:59 DO 平均 ICMP 丢包约 20%—24%，腾讯不足 1%。这是历史日志复算，不是本轮现场复现晚高峰，也不足以断言具体运营商主动限速或 IP 被定向干扰。
3. **双路由串联确实增加处理层次，但双 NAT 本身不是已证实的主因。** 本机只有一个活动默认网关；本次到两个路由器各 20 个 ICMP 均无丢包。取消一层可降低复杂性，但不会自动修复错误分流和 DO 的跨境路径质量。
4. **建议最终电脑直接接雅典娜，保留双 VPS 数据出口。** 雅典娜已承载公司上联和医院白名单 SNAT，保留它比把这些依赖迁到 SN-R1 的影响小。单路由器与单 VPS 是两件事；单路由仍可择优使用 DO / 腾讯。
5. **另有独立管理通道异常需先处理。** 两次查询 DO 监听，仅见 18222，未见 13222/18322/18422；SN-R1 本地未见 18443/28443。不能沿用“所有双管理隧道正常”的历史结论。根因、心跳和端到端医院通道本轮未完整验证。

## 2. 现场拓扑与资源

```text
PC 192.168.132.105（以太网 1 Gbps；WLAN disconnected）
  → SN-R1 LAN 192.168.132.1 / WAN 192.168.2.158
  → 雅典娜 LAN 192.168.2.1 / WAN 10.1.2.105 + 次地址 10.1.2.18
  → 公司网关 10.1.2.254
  → DO 159.223.36.119 或腾讯 43.134.46.44
```

PC 唯一 IPv4 默认路由及 DNS 为 `192.168.132.1`。到 SN-R1 20/20 回包、最大 4ms；到雅典娜 20/20、最大 1ms。PC 网卡错误和丢弃计数均为 0。仅是短窗口，未覆盖负载及用户卡顿当时。

雅典娜负载约 0.11、可用内存约 465 MiB、conntrack 954/65535；SN-R1 负载约 0.20、可用约 813 MiB、conntrack 945/16384。DO 约 961 MiB 总内存、468 MiB available、约 292 MiB 已使用 swap；短采样 vmstat 未见持续换入换出，不能把历史 swap 占用判为当前内存瓶颈。腾讯约 1962 MiB 总内存、1431 MiB available。两台 sing-box 均 active。DO 已使用 bbr/fq，不能重复“优化启用 BBR”作为修复。

雅典娜有累计接口 drops，未采足够长的同窗口增量，不据此认定网线故障。SN-R1 的 BusyBox `ip -s link` 不支持，本次改用 `/proc/net/dev`，没有安装工具。

## 3. 应用与解析对照

两台均通过本机 `127.0.0.1:7890`，HTTP/1.1、连接超时 4 秒、总超时 9 秒；每 URL 三次。表中失败时间受本轮超时参数限制，与原材料 8/10 秒不能直接比较。

| 目标 | 雅典娜 | SN-R1 | PC 透明代理路径（三次） |
|---|---|---|---|
| www.gstatic.com/generate_204 | 3/3 成功，0.170—0.173s | 0/3，TLS 建立阶段超时约 4s | 0/3，约 4s 超时 |
| www.google.com/generate_204 | 3/3，0.450—1.928s | 3/3，0.522—0.948s | 3/3，0.601—1.492s |
| www.baidu.com/ | 3/3，0.113—0.122s | 1/3 成功，另两次约 4s 超时 | 1/3 成功，另两次约 4s 超时 |

显式 HTTP 代理的 curl `remote_ip=127.0.0.1`、connect 时间是连接本地代理，**不代表到 VPS 的 RTT 或服务器真实地址**。PC curl 的 198.18 地址是透明代理 fake-ip，也不是站点真实地址。

### DNS 和固定 IP 实验

| 检查 | 雅典娜 | SN-R1 |
|---|---|---|
| 系统 nslookup www.gstatic.com | 198.18.0.120 | 从上游 192.168.2.1 得到 198.18.0.120 |
| mihomo GET /dns/query 同域 A | 114.250.68.34 | 142.251.12.94 |
| mihomo GET /dns/query 百度 | 110.242.69.21 / 110.242.70.57 | 相同地址 |
| curl 保留域名/SNI，--resolve 到 114.250.68.34 | 204，0.201s | 204，0.378s |
| --resolve 到 142.251.12.94 | 连接超时 | TLS 阶段超时 |

固定 IP 实验只用于诊断，不应把该 CDN IP 写入长期 hosts；SN-R1 的 `--noproxy '*'` 只绕过本机显式代理，仍经过雅典娜透明代理，不能称为完整物理直连对照。

受控连接查询确认 SN-R1 的 gstatic 命中 `GeoSite google-cn → DIRECT`。SYN 头抓取确认 SN-R1 实际连接 `142.251.12.94:443`；返回 SYN-ACK 不能证明远端站点已握手，因为雅典娜可能代接 TCP。雅典娜连接 API 确认来自 `192.168.2.158`、目标 `142.251.12.94`、类型 Redir、最终 DIRECT；请求仍失败。

**因此当前样本否定了“这次是 SN-R1 将 198.18 当真实目标发出去”的解释。** 尚未完全解释两台相同磁盘 DNS 配置为何得到不同答案：可能涉及 fallback、nameserver-policy 匹配、缓存、规则库、不同核心版本及上游二次代理。须在隔离测试或维护窗口进一步区分；不能仅看 `/etc/resolv.conf` 推断 mihomo DIRECT 的实际解析路径。

线上 DNS 配置存在 `fallback-filter.domain: +.gstatic.com`，同时路由规则 `google-cn → DIRECT`。一个将解析引向 fallback 的设置，与一个要求直连的路由，可能组合出不可达的境外目标；本次 SN-R1 恰得到这样的地址。`direct-nameserver` 未配置。该字段、nameserver-policy 和 fallback 的语义参考 [mihomo DNS 官方文档](https://wiki.metacubex.one/config/dns/)；实际行为仍需按设备核心版本复验。

另测“普通系统 curl 请求 DoH URL”时，雅典娜超时，SN-R1 经上游 fake-ip 得到 HTTP 400。它没有发送有效 DNS 请求，400 仅说明连接到 HTTP 服务；这一实验不等于 mihomo 自身 DoH 查询故障，也不能据此判定 DNS 答案正确。

## 4. 选路与防火墙

实测两台均为：

```text
PROXY(select, now=AUTO)
  → AUTO(fallback, now=NODE-PICK, 成员 NODE-PICK / DIRECT)
  → NODE-PICK(url-test, now=VPS-SG-01, interval=300, tolerance=80)
  → DO / 腾讯
```

这与输入材料“ AUTO=url-test、NODE-PICK=select ”不符。当前最外层 AUTO 用 Apple HTTP 页面探活，不能证明 Google 业务可用。两台 core 不同：雅典娜 `alpha-ge183c58`；SN-R1 `v1.19.31`。本次未升级。

雅典娜 nft mihomo prerouting 只有 DO 的提前 RETURN，没有腾讯地址的提前 RETURN；其宽 TCP redirect 仍会捕获腾讯目的连接。YAML 两节点均有 DIRECT 规则，说明最终可能直出，但不等于没有进入第二层核心，更不等于已发生“通过另一 VPS 嵌套加密代理”。需要区分二次拦截与二次代理隧道。

SN-R1 的 iptables 有 UDP443 DROP，已保留。雅典娜 borrow18 的 SNAT 覆盖医院目标；WAN 次地址 `10.1.2.18` 实际存在。该链仅匹配 `192.168.2.0/24` 来源，若未来换路由或网段不能照抄。

## 5. 线路历史证据复算

本轮保存雅典娜最近 1800 行、SN-R1 1581 行 netprobe 日志，兼容旧 `vps=` 与新 `icmp_vps=` 格式。窗口为当地时间 20:00—22:59，每目标每窗口 36 条，每条历史探针通常 20 包；平均值是“记录中的丢包百分比算术平均”，原格式缺实际发包数，不能声称精确全包加权丢包率。

| 设备 / 日期 | DO 平均 / 最大 | 腾讯平均 | 国内平均 |
|---|---|---|---|
| 雅典娜 09-25 | 24.44% / 45% | 0.56% | 0% |
| 雅典娜 09-26 | 20.42% / 45% | 0.83% | 0% |
| SN-R1 09-24 | 29.86% / 50% | 无对应样本 | 0% |
| SN-R1 09-25 | 26.11% / 50% | 0.42% | 0.14% |

SN-R1 09-26 晚高峰缺测，不能补零。雅典娜有该窗口数据，故输入材料“09-26 只有上午数据”只能限定到 SN-R1，不能推广到全部测点。本轮早晨两台分别向三目标各发 10 包，全部 0% 丢包，DO 平均约 146ms、腾讯约 213ms、国内约 7ms。

DO TCP 累计 RetransSegs/OutSegs 约 4.08%，覆盖开机以来全部连接，不是本轮、特定出口或特定方向的 TCP 丢包率。国内 ICMP 健康只降低“全面出口故障”的可能，不能排除公司网按域名、协议、目的地实施的策略或繁忙时排队。没有足够证据定位具体 AS、区分去回程或认定主动干扰。

| 原判断 | 本次修正 |

| 双网卡同时经 SN-R1 | 当前只有以太网默认路由，WLAN 未连接 |

## 7. 证据目录与限制

- `athena-snapshot.json` / `snr1-snapshot.json`：配置白名单、代理组运行状态、防火墙、历史探针、版本。
- `http-comparison.json` / `pc-http.json`：路由器显式代理与电脑透明代理样本；小样本不能当长期 SLA。
- `dns-dependencies.json` / `forced-ip-comparison.json`：内核 DNS、真实地址对照、资源及白名单依赖。
- `gstatic-syn-only.json` / `upstream-interception.json`：受控目标的连接元数据；没有业务正文或包载荷。
- `historical-summary.json`：历史日志复算，包含每组首尾时间和样本数。
- `pc-gateway-ping.json` / `server-status.json`：本次短时连通性与服务器状态。
- `collect_readonly.py`：本次专用采集器，凭据只从本地台账在内存读取，不输出完整代理配置；已加“快照存在即拒绝重跑”保护，后续采集须审查并设置新批次输出位置及项目根目录，不能直接复制后假设相对根路径仍正确。DNS/规则只对白名单现网内容审查过，不是通用脱敏器。

服务器使用已有 known_hosts 校验。两路由器缺已登记主机键，首次本地直连记录指纹，后续采样固定该指纹；没有独立可信渠道认证，不能将这次 TOFU 视为历史 pinning 问题已解决。指纹保存在采集器中，未修改系统 known_hosts。

未验证：单路由拓扑实际效果、完整浏览器瀑布、晚高峰 TCP/下载同窗数据、长期 bufferbloat/MTU、医院业务可用性、反向隧道缺失原因、所有生产配置持久化入口。输入文件标注生成时间 08:10，而部分本次实测早于该标注；原文件时间仅作为其自述，不据此排列现场先后。
