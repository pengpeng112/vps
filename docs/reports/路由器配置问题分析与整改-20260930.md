# 2026-09-30 路由器配置问题分析与整改方案

> 范围：当日暴露的**设备/配置/管理链路问题**（线路品质问题见另册《线路情况与延迟汇总-20260930》）。
> 重点：**远程失联类问题单列 P0 防线**，所有整改遵循"先隔离验证、单台试点、可回滚、改后双通道验证"。

## 一、问题清单（按严重度）

### A 类：远程失联（P0，需专项整改）

**A1. -R 反向隧道"僵尸卡死"循环（当日三度复发）**
- 现象：客户设备反向口 13224 监听在但连接无应答/连接被拒，SSH 顶不进去。
- 根因链（三者叠加，缺一不死）：
  1. 客户家宽/CGNAT 空闲超时掐死 TCP（dbclient 已有 -K 30 客户端保活，但线路硬断时无用）；
  2. **DO sshd 无服务器端保活**（无 ClientAliveInterval）→ 死会话的监听 socket 僵尸般占用端口可达数小时；
  3. **dropbear dbclient 无 ExitOnForwardFailure** → 重连后绑定失败但进程不退出、不重试 → 永久卡死。
- 当日处置：人工"清 DO 僵尸监听 + API 下发 repair_mgmt_tunnel"恢复两次（该白名单任务生产首验成功）。下午换机后 R3 的隧道全天稳定（联通线 TCP 质量好）。
- 缺口：**VPS banner 探测只覆盖 18222/13222（雅典娜/老 SN-R1），舰队端口 13223—13226 无监控**，remote_ssh_alive=null，僵尸无自动发现，全靠人工碰上。

**A2. 线路级失联不可远程诊断（R4 案例）**
- 现象：广电线→DO 新建 TCP 全断（15 秒 0 SYN），设备 -L/-R 双亡；设备 procd 无限重连（设计正确），但该线路永不恢复 → 设备永久离线。
- 教训一：**远程修复能力的边界 = 设备至少能建立到 DO 的 TCP**。任务下发、配置下载全部依赖 -L 心跳通道；-L 一断，repair/发布/一切指令均不可达（当日多个 repair 任务 expired 实证）。
- 教训二：管理台"离线"无法区分"设备坏了/线路死了/换机了"三种情况，只能靠现场看 LuCI（192.168.132.1 → WAN 状态）。
- 教训三（正面）：设备侧 procd respawn（5 秒无限重试）+ 换线自动恢复的设计当日验证有效。

**A3. 反向端口共用导致"假 SSH 在线"（当日真实误导）**
- 现象：13224 被 R3/R4 共用；现场换机后，VPS 上 `ssh -p 13224` 有应答（实为 R3），但 rtr-cd473f 心跳离线 → 用户误判"SSH 通但设备离线，是不是被顶替"。
- 根因：09-28 刷机时 R3/R4 都配了 13224（台账有星标但未强制约束）。
- 当日处置：flash-snr.py 已改自动分配（同机复用/新机取 132xx 最大+1/占用即停，实测通过）；R4 尚未改口（待其上线执行）。

**A4. 运维通道已知陷阱（当日重复踩/差点踩）**
- DO **root 账号有 PermitOpen 限制**，不能经它转发到 1322x——必须用 jump 账号（今日一次误用 root 排查浪费一轮）。
- VPS root 直连 13224 时 **known_hosts 主机键随当前接入设备变化**，换机必先删旧条目。
- 判身份唯一可靠入口：`grep DEVICE_ID /etc/routermgmt/agent.conf`（密钥指纹/主机键可作旁证）。

### B 类：设备身份与台账（P1）

**B1. 现场设备拿混**：用户换网时插入的是 R3，但按 R4（rtr-cd473f）对待了大半天；靠 DEVICE_ID+隧道密钥指纹+主机键三重证据纠正。→ 整改：每台设备外壳贴"SN-Rn + 管理台 ID"标签；接手任何"已部署点位"先跑身份验证三件套。
**B2. R3 口令统一失败且台账失真**：台账记"R3 已统一 [REDACTED]"，实际仍是刷机随机口令（.snr3-pw 第一行），统一口令与公钥均被拒。→ 整改：unify-pw.py 增加改后强校验（用新口令真实登录），档案状态与实测强一致。
**B3. 凭证档案更新不同步**：.snr4-pw 更新为统一口令而 .snr3-pw 仍为旧值——说明 09-28 深夜批量操作中 R3 的 unify 未执行或未生效且无人发现。

### C 类：配置与发布链（P1—P2）

**C1. dl.google.com 命中 GEOSITE,google-cn → DIRECT**：在劣质线路上直连必死（当日实测 0B/s×2）。Chrome 等大文件下载会失败。→ 可选整改：golden.yaml 增 `DOMAIN-SUFFIX,dl.google.com,PROXY`（与 09-27 gstatic 修复同模式），全舰队发布。
**C2. netprobe cron 缺失**（R3/R4 确认，R2/R5/R6 待查）：当日全靠手工测量，无丢包曲线可回溯。→ 整改：批量补装 + flash-snr 末步增加"crontab 存在性校验"。
**C3. 配置发布滞留无告警**：R4 的 v2/v3 已发布在库但设备离线未送达，任务 expired 后无人跟踪；设备上线也不会自动补发。→ 整改：上线心跳时比对"设备运行版本 vs 最新已发布版本"，不一致即告警（或自动重发，需评估风险）。
**C4. 本地代码与 VPS 源码双轨**：今日 5 文件直传 VPS 重建 api（远端有 .bak），但本地尚有 mac_addr 等未提交改动混在工作区，无正式"提交→同步→重建"流程。→ 整改：git 提交规范化 + 部署脚本化（ci-local → commit → rsync → compose build → 健康检查 → 失败回滚）。
**C5.（正面记录）watchdog 发布保护实战生效**：hy2 首次发布因健康检查失败被自动回滚，设备零损伤——发布链安全性当日验证。

### D 类：测量与运维方法（P2，已记入 ops 教训）

1. tcpdump 被 timeout 强杀不刷盘 → 假阴性（当日两轮误判"UDP 不通"）；正确做法=凑包数自然退出。
2. `pkill -f "含自身命令行的模式"` 会自杀，需 `[h]xx` 写法。
3. `-x 7890` 测节点 IP 目标会命中"节点直连规则"变直连——**-x ≠ 一定走隧道**。
4. netstat/Windows 输出编码（GBK）坑、paramiko 单 channel 单会话不可复用。

## 二、整改方案

### P0：远程失联防线（建议尽快，全部低风险可回滚）

| # | 动作 | 风险 | 验收 | 回滚 |
|---|---|---|---|---|
| 0-1 | **DO sshd 加 `ClientAliveInterval 30` + `ClientAliveCountMax 3`**（reload 不断现有连接） | 低：只影响空闲死会话的清理速度 | 现有全部隧道（雅典娜/R3/PC 跳板）心跳与 banner 不中断；模拟僵尸 90 秒内自清 | 删两行配置 reload |
| 0-2 | **VPS mgmt-rssh-probe 扩端口 13223—1322N**，按台账映射设备，写入 remote_ssh_alive；连续 3 败告警（现有 tunnelhealth 机制复用） | 无业务影响（banner 探测不登录不改配置） | 人为停一台 -R 后 ≤2 分钟出告警，恢复自动 ack | 还原探测脚本（有备份） |
| 0-3 | **设备隧道脚本加固**（针对 A1-3）：绑定失败检测循环——dbclient 起 -R 前先测远端口占用？受 dropbear 能力限制，务实做法=mgmt-tunnel init 给 rssh 实例加周期性自检重启（如每小时 full restart 一次，低峰漂移） | 中：改设备隧道脚本**必须逐台试点** | 试点机 72 小时心跳/反向口零中断 + 人为制造僵尸 1 小时内自愈 | 还原 init 脚本（cp 备份），重启服务 |
| 0-4 | **"失联三态"展示**（管理台/运维手册）：心跳断+反向口在=线路抖；双断=设备或线路死；反向口应答但指纹/ID 不符=端口冲突或换机 | 纯展示层 | 三种场景各演练一次 | — |

**执行纪律（用户要求"慎重"的落地）**：① 0-1 与 0-3 **永不同天执行**；② 0-3 先拿一台**非现役备用机**（R5/R6）试点 72 小时，再推广现役客户机，雅典娜最后；③ 每次变更后 30 分钟内连续验证 -L 心跳 + -R banner 双通；④ 全部变更留 `.bak-日期` 并写入台账。

1. R4 上线当日：改独占端口 13227（设备 tunnel.conf + VPS authorized_keys + 台账三处同步）→ 0-2 探测覆盖它。

4. B2/B3：R3 unify-pw 补做+强校验；台账状态字段改为"实测日期+实测人"。

### P2（随版本迭代）

## 四、整合：后续路由器统一采用"新节点接入 SOP v1"（2026-09-30 晚追加）

《搬瓦工东京接入执行计划-20260930》与本整改文档已核对：**无冲突，仅一条排序约束**（整改 P0-1 动管理机 sshd 须避开任何发布窗口，本轮全程未动 sshd；另发现管理机已存在 99-hardening.conf，P0-1 实施前须基于现状评估避免重复配置）。计划中"不改隧道脚本/不跑 unify-pw/不动 golden"与整改 P0-3/B2/C1 的待批状态一致。

**后续路由器/新节点统一按以下流程执行**（合并计划方法论与本文执行纪律）：

1. 服务端：独立密码+独立凭据档案（只进 backups/）、自签证书、最小入站、路由拒绝私网防跳板、BBR；
2. **路径门槛=按"准备启用的协议"实测（2026-09-30 晚修正）**：UDP 协议（hy2）须证"UDP 包到达服务端"（源过滤抓包凑包数自然退出）；TCP 协议（vless）须证完整 TLS 往返（wget 非静默）。ICMP 通不算数；UDP 不到只否决 UDP 协议，不否决 TCP 接入（东京 VLESS 即此例）。UDP 丢弃的适用范围按实测点位记录，不外推到其它运营商；
3. 管理台建节点但不发布；
4. 预览六项人工核对（成员序/协议字段/掩码/gstatic/管理直连/新节点直连）；
5. 发布走 expect_exit_ip 双次校验的 watchdog 流程，**失败即停不重发**；
6. 八项验收含对照机（防绑错设备）；
7. 执行记录+当前状态短条目；凭据与秘密不入 docs/git。

**本轮新教训（SOP 第 2 条的由来）**：R3→东京 CN2 GIA 路径 ICMP/TCP 全通但 UDP 全端口丢弃（详见《搬瓦工东京接入执行记录-20260930》），与上午"腾讯平台防火墙丢 UDP"是两类不同成因的同类症状——**都必须靠"实际抓包证到达"这道门槛挡住**，这正是计划 P1.8 设计的价值：本次在发布前拦截，R3 现网零损伤。
