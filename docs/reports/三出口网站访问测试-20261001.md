## 4. 结论

1. **BWG 东京 vless 是两台共同的最优出口**：ICMP 0% 丢包（52/70ms）、网站 15/15 全通、
   中位延迟最低（~180-200ms）。两台当前主用绑定 BWG 正确。
2. **TX 备用路两台表现分化**（同省联通，线路不同结果不同）：
   - R3 现场：TX-HY2 表现好（15/15、中位 210ms）——UDP 到腾讯当前可用；
   - R2 家里：TX-HY2 3 站超时，TX-VLESS 更稳（15/15）。
   → 备用序可按点位差异化：R3 维持 TX-HY2 第一备用；R2 若切备用优先 TX-VLESS。
3. **DO 到两现场质量最差**（R3 丢 10%、API 全链路 0.9-1.4s）——只做管理面是正确取舍。
4. paypal 在两台所有出口均 500-1700ms（跨境支付站共性，非节点问题）。
5. R3 现场 TX 方向 ICMP 丢 20% 但 hy2 网站测试全通——QUIC/Hy2 抗丢包特性，长流表现
   仍需晚高峰观察（本次为下午常规时段单次测试）。

限制：单次截面测试（16:50-16:55），未覆盖晚高峰；delay 测试为建连+首响应延迟，
不代表长流吞吐。

## 5. 追加（17:2x）：R3 腾讯分流资格判定 — DENY（暂不启用）

按用户定稿的分流方案（视频/下载→腾讯、其余→东京，逐点位体检合格才启用），对 R3
补测长流吞吐并按门槛判定：

| 门槛 | 标准 | R3 实测 | 判定 |
|---|---|---|---|
| 1 通过率 | ≥14/15 且 youtube/netflix 必通 | 15/15，视频站 303/318ms | ✓ |
| 2 延迟差 | 腾讯中位−东京中位 ≤150ms | 210−180=30ms | ✓ |
| 3 丢包/吞吐 | ICMP≤5% **或** hy2 长流≥东京 60% | ICMP **20%**；三并发合计 腾讯 **3.28MB/s** vs 东京 7.89MB/s（**42%**） | **✗** |

长流测法：管理台 switch_node 试切（TX-HY2 出口 43.134.46.44 双验）→ 三并发 30MB
（cloudflare）→ 自动回切 BWG（74.82.203.175 双验，R3 配置终态 version 8）。
另注：mihomo Fallback 组手动 PUT 会被健康检查秒级覆盖（出口 IP 不变），试切必须走
管理台任务；delay API 对大文件返回 "Body invalid"，不能用于吞吐。

**结论**：R3 建连层面腾讯优秀，但长流吞吐仅东京 42%（单流 1.1MB/s≈8.8Mbps，1080p
勉强、4K 不足）且 ICMP 丢包 20%——**暂不启用分流，维持东京独扛**。hy2 表现时段性强，
建议晚高峰（21—22 点）复测再议；R2 建连层已不达标（3 站超时）无需测吞吐。
