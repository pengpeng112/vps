- **根因（路由盲区）**：该域名有公网解析（123.233.249.132，与办公室出口同段，直连 2ms/200），但小众域名不在 `geosite:cn` 名单；模板的 `GEOIP,CN,DIRECT,no-resolve` 对「域名形态」的连接不生效（no-resolve 跳过解析）→ 最终落入 `MATCH,PROXY` 从新加坡回访国内内网端口 → 超时。

## C10-2 排查中发现：SN-R1 心跳已断 26 小时（09-26 12:43 起）

- **表象**：任务 expired 送不进、hb.resp 停更；隧道进程活着但转发不通。
- **排查过程（关键取证）**：dbclient 报 host key mismatch（收到 55:e6…、期望 48:xx）→ 一度怀疑中间人 → **PC 侧 keyscan 对比证明收到的就是 VPS 真实 RSA 密钥**，且 known_hosts 里唯一条目的指纹也与真实一致 → 无 MITM，是**格式问题**。
- **根因**：09-24 写入的 pin 是脚本生成的 openssh 格式，SN-R1 的 dbclient（LibWrt 固件）解析这种格式永远报 mismatch（踩坑清单已记录过的老坑）。当时隧道长连接一直活着，掩盖了问题；09-26 12:43 连接意外断开，重启重连才第一次真正读到坏 pin → 拒连死循环。VPS 侧 mgmt-rssh-probe 的 repair 任务也送不进去（任务通道=心跳通道，鸡生蛋）。
- **修复**：清空坏格式条目 → 重启 mgmt-tunnel → init 脚本的「无条目自动 -y」兜底生效 → 隧道恢复、心跳上线（09-27 14:36）。
- **遗留（接受）**：该固件 dropbear 版本 `-y` 也不落盘，known_hosts 保持为空、每次 -y 接受（TOFU）。密钥真实性已人工核验（PC keyscan RSA=sha1 55:e6:cf… 与路由器收到的一致），且 SN-R1 每次连的都是同一 IP。logread 每次重启会打 WARN 提示「应尽快 pin-hostkey」——此固件下无法真正 pin，属已知限制。
- **经验（已入踩坑清单）**：
  1. 「pin 正确性」在长连接存续期间无法验证——**pin 写入后必须立刻断开重连验证**（当时验证过吗？该条 pin 写入流程跳过了复连验证或验证方式与实际调用不一致）。
  2. 间歇性断线 + 重启后报 host key mismatch ≠ 中击：**先从第三方视角 keyscan 对指纹再下结论**，别急着当攻击处理。
