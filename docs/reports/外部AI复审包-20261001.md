## 二、事故一（服务端）：authorized_keys 逗号格式导致全舰队认证报废

- **现象**：R3 管理面 12:41 全断（-R 与三条 -L 同时失效，客户端重连日志全是 `Connection closed by authenticating user root [preauth]`）；代理流量不受影响（独立通道）。R2 隧道侥幸存活（改动前建立的旧会话）。
- **根因**：一个并行会话为温备做准备，把三台 VPS 的 authorized_keys 里 `permitopen="10.10.0.1:8443"` 批量改成 `permitopen="10.10.0.1:8443,127.0.0.1:8443"` —— **一个 permitopen 内塞逗号列表是非法语法，sshd 解析选项失败会报废整行密钥**。R3 隧道 12:41 一次普通网络抖动重连时撞上，认证全拒。
- **定案方法**：DO 上起临时 sshd（独立端口+测试密钥文件）做对照实验：旧单值格式 ✅ / 重复选项 `permitopen="A",permitopen="B"` ✅ / 逗号列表 ❌。
- **修复**：三台 VPS 全部 sed 改为重复选项格式（各自留 .bak-commafix）。R3 秒级自愈（procd 一直在重试）。
- **验证**：R2/R3 均三路 HTTP 200；BWG 日志出现成功认证。
- **请审**：①authorized_keys 的正确多目标写法还有没有别的坑（permitlisten 双端口逗号列表是否同样非法？snR3 行有 `permitlisten="...13224",permitlisten="...13227"` 重复选项写法，理论安全）；②如何防止再次发生（格式门禁脚本？sshd 配置测试命令？）。

## 三、事故二（路由器端）：R2 代理完全不可用 = 断电闪存损坏

- **现象**：R2 新上线，无 mihomo 配置文件、7890/9090 不通；首次发布任务失败"mihomo 配置校验失败"。
- **诊断链**：`/etc/mihomo/config.yaml` 6125 字节**全 0x00**（hexdump 实锤）；`/usr/bin/mihomo`（57MB）**段错误 rc=139**（连 `-v` 都崩，ELF 魔数还在）；geo 两文件 md5 与好机不同。9-28 刷机时该配置曾通过健康检查（当时是好的）→ 期间一次异常断电打坏三个大文件。dmesg 无文件系统报错（不能靠它排除）。
- **修复**：从 R3（同批次同版本）三件套逐级 md5 校验搬运（R3→DO→R2，stdin 管道传输，R2 对 DO 方向吞吐仅 ~40KB/s，57MB 约 25 分钟）；重发布成功。
- **验证**：`mihomo -v` 正常；发布任务 ok（出口 IP 双次校验过）；此后两次重启 md5 未再变化。
- **请审**：同款固件+同款断电场景可能在 R4/R5/R6 复发。是否有系统性方案（开机自检 md5 清单+自愈拉取？JFFS2/UBIFS 层面的数据完整性？）值得做，还是接受"坏了从好机搬"？

## 四、坑组（路由器端）：mgmt-tunnel 韧性三连修

1. **respawn 5 次上限永不自愈**：`procd_set_param respawn 3600 5 0`，服务端故障期（如事故一的 27 分钟）快速失败 5 次后 procd 停止拉起——服务端修好设备也不回来。**R3 的 TX/BWG 路径和 R4 的整个隧道都栽在这**。已改 `respawn 3600 0 0`（无限重试）。
2. **-R 绑定失败 ssh 静默苟活**：无 `ExitOnForwardFailure` 时，-R 端口被 DO 侧残留会话占住则绑定失败但 ssh 不退出，procd 以为健康——端口释放后无人再申请转发=**永久半开**（R3 实发两次：TCP 在听但 banner 超时）。已加 `-o ExitOnForwardFailure=yes`，配合无限重试实现"绑定被占→退出→重试→端口释放后自动回绑"。
3. **厂商固件开机重写 crontab**：重启后 `/etc/crontabs/root` 只剩厂商 `factory checkMem`，探针 cron 条目必丢（R2 重启实测复现）。已在 rc.local 加幂等恢复钩子（sleep 10 → 缺则补条目 → 重启 cron），二次重启实证有效。

- **重要部署细节**：改 ssh 参数/respawn 后**必须 `/etc/init.d/mgmt-tunnel restart` 真重启**（procd 重读配置）；管理台的 repair_mgmt_tunnel 任务只杀进程重生（沿用旧参数），不能用于加载新参数。
- **请审**：①无限 respawn 的重试风暴风险评估（当前实测：DO ClientAliveInterval 300 导致死会话占 -R 端口至多约 5 分钟，此窗口 rssh 每 5 秒一次认证重试，是否可接受）；②三修复有没有引入新风险（如 ExitOnForwardFailure 对 -L 本地端口占用场景的行为）。
