## 发现与优先级

### 1. 高：海外媒体组实际退化为直连

证据：R3、R5 API `/proxies/US-MEDIA` 均返回 `all=[COMPATIBLE]`、`now=COMPATIBLE`；YouTube、Netflix、googlevideo 等规则仍指向 US-MEDIA。R5 的 COMPATIBLE 探测为 alive=false。

根因：`mgmt/backend/internal/clash/golden.yaml:126` 使用 `include-all: true` 和 `filter: "LAX|NODE-PICK"`，但两台只绑定 GIA/BWG，没有 LAX。当前官方文档明确 include-all 不包含其他策略组，因此不会把 NODE-PICK 自动纳入。COMPATIBLE 等效 DIRECT。

影响：主代理组正常时，视频和部分资源域仍可能无法访问。已确认错误路由，未从 LAN 终端逐项复现播放。

改进：由渲染器显式构造媒体组的真实节点和兜底成员；无 LAX 时明确接到 NODE-PICK。要考虑 fallback 的成员优先顺序，不能把兜底错误放在优先 LAX 前。发布验收必须检查运行时成员非空，不能只验 YAML 语法或组名存在。

依据：[代理组通用字段](https://wiki.metacubex.one/config/proxy-groups/)、[COMPATIBLE](https://wiki.metacubex.one/config/proxies/built-in/#compatible)。

### 2. 高：全断时自愈入口会提前退出；R5 又有重复入口

证据：`mgmt/agent/mgmt-port-discovery.sh:38` 的全失败分支 return/exit 位于第 43 行看门狗调用之前；R3/R5 的该文件 md5 均与仓库一致。R3 crontab 只有 discovery 入口，没有独立 tunnel-watchdog cron；rc.local 只补 discovery/netprobe/reboot。故在五端口都失败的情形，R3 无法通过这条执行路径带起看门狗，WAN 看门狗和后续透明代理守护也被跳过。

R5 同时有 discovery 间接调用和独立 `#routermgmt-tunnelwd` cron；两者没有锁，会共享计数文件。历史日志存在同一分钟连续计数，但不据此直接断言全部历史重启均由竞态导致。

改进：将自愈做成独立、开机可恢复的单一调度入口，发现全断仍须运行；加互斥、连续失败判定、冷却/退避，优先重建坏腿，避免无差别重启好腿。用模拟探测故障验证执行路径，再选择单台维护窗口做真实演练。

### 3. 高：广州 8443 管理转发对公网可达

证据：gz-relay.service 使用 `-L 0.0.0.0:8443:127.0.0.1:8443`；ss 确认公开监听；本机连接广州公网 8443 成功。UFW inactive。API 未登录查询返回 401，尚无认证绕过证据。

改进：设备通过 SSH 本地转发访问广州回环即可，优先将这条中继监听约束为 127.0.0.1；如有现存公网依赖，先确认使用者再收口。不要直接执行 ufw enable，以免同时误封 SSH 和设备管理入口。

### 4. 高：R1 目前仍是“有端口，无法完成 SSH 握手”

证据：广州和 GIA 均监听 13222，但广州登录 R1 两次失败；两侧分别执行限时 ssh-keyscan 都返回 1。R3/R5 同样的广州登录方式成功，故不能把本次 R1 状态当成已验收健康。

限制：尚不能区分旧会话、路由器 SSH 服务、转发目标或 LAN 地址问题；没清理会话或改 RSSH_TARGET。R1 历史目标 `192.168.132.1:22` 仍须保留，不能未经核实改 loopback。

改进：监控从 LISTEN 升级为限时 SSH 横幅/握手检测；回收旧会话前，要结合连续探测和对应 pid/设备身份，避免仅按连接年龄误杀正常长连接。

### 5. 中高：国内远程入口已分离，平台后端尚未独立

现网实际路径：`设备 → 广州 → GIA → DMIT API`。gz-relay 和 GIA s-relay 的 ExecStart 分别确认后两段 SSH 接力。

含义：设备到广州、管理员到广州的国内 SSH 可保留；但 GIA、GIA→DMIT 或 DMIT API/DB 故障仍可影响心跳与平台任务。方案中“全部国际线路断仍可完整管理”“仅国内路由故障才断”的说法过强。

改进：先把“国内 SSH 救援可用”和“平台心跳/任务可用”分开监控及承诺；为广州保留独立身份清单和受控救援流程。需要平台真正独立时，再制定国内主控迁移或有明确写入权的灾备方案，不能直接开启冻结旧库或并行写两个后端。

### 6. 中：当前抽查是主备切换，未发现真正负载均衡

R3/R5 运行时均为 Fallback；本地模板没有 load-balance。不能由用户提到“负载”就推定全舰队已部署同一种策略。

改进：先按站点实测线路、节点带宽/CPU/流量配额分配主节点并保留异构备用。确需单台分摊时，再设计独立 load-balance 组；登录敏感业务保留稳定出口，下载/媒体单独考虑分摊。consistent-hashing 按目标分配，sticky-sessions 按源与目标保持一段时间，可参考[官方说明](https://github.com/MetaCubeX/Meta-Docs/blob/main/docs/config/proxy-groups/load-balance.en.md)。不要把健康探测或 fallback 称为容量均衡。

- 现网 R3/R5 watchdog md5=`64fd492fd46f0ec2da435c7669a99613`；本地仍是只探 18443 的旧版，md5=`42d73f6ae03f689ec5eeb5cb6c29272f`。

- 架构评估仍写“计划加第六端点”，现网实际是广州替换主端点，保持五个管理端点并加第二反向口。

改进：将已验收版本回写部署源与操作文档，记录散列和适用机型；switch_node 在恢复 AUTO、读回、验证最终路径成功后再提交，失败进入既有回滚机制。不得直接重跑刷机脚本来对齐现网。

### 8. 中：控制服务器凭证与连接回收仍需完善

本地 push-via-gz.py 把服务器及设备口令硬编码且相同；本报告不记录其值。广州 sshd 实测 passwordauthentication=yes、permitrootlogin=yes、ClientAliveInterval=0；本次未找到名含 rssh/reaper 的 cron/timer，不能排除其他名称的回收机制。

改进：先建立独立管理密钥及经过验证的备用入口，再按方案逐步去掉硬编码/共享口令，设置服务端保活和基于探测的旧会话处理；不要在没有恢复路径时直接更换全舰队身份或关闭密码认证。中继服务和设备连接应使用分别受限的账号/密钥和指定转发目标。

## 建议执行次序与验收

1. 优先处理媒体组、独立看门狗入口及广州 8443 暴露；R1 单独排查，不能等同于其他两台。
2. 对齐本地升级源；增加最终 AUTO 读回验证、健康 API 身份/新鲜度检查及各腿独立监控。
3. 后续按明确窗口做单台演练：主出口失败、广州中继失败、DMIT 后端失败、全部管理健康失败、设备重启后的 cron/端口恢复。记录 SSH 可用、心跳可用和实际国外访问恢复三个独立结果。
4. 最后评估节点容量、站点分配和必要的负载均衡。当前没做带宽压测，也未人为断开任何生产连接。
