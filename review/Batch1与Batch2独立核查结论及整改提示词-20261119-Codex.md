## 2. 必须先解决的阻断

### F01 / P1：跨日仍会把旧日流量算给新日，并错误发放资格

位置：`scripts/qos-r2/proxy-meter-v3.sh:249`、`:279`、`:306`。

现在只要 boot 不变、间隔不超过 420 秒，就记 `rollover_clean`；随后却仍执行 `day_total = delta`，把整个跨午夜增量放进新日。没有午夜边界结算或可证明的日归属。

本轮用真实日期隔离复现：旧样本 **11-19 23:57**，新样本 **11-20 00:02**，同 boot、间隔 300 秒。350000−300=349700B 被全部计入 11-20，输出：

```text
day_first_at=2026-11-20 00:02:00+0800
day_total=349700
events=rollover_clean
health=ok partial=false quota_eligible=true
```

这直接违反 Q1.3“不能把跨日整段塞进新日还 partial=false”。仅修改事件名和清零历史 partial 不够。

更直接的现场阻断：**R2 仍有 `0 0 * * * /sbin/reboot #routermgmt-reboot`**。本批没有交付重启前最后结算、计数销毁顺序、恢复前装表的证据。现有代码遇到新 boot 仍记 reboot_rebaseline 并让当天 partial 持续为 true。按当前排程，每个新日都可能再次不合格；不能预告“11-20 00:00 就自然合格”。

原矩阵 T1 把 prev.day_key 写成昨天，但 prev_epoch 仍是“当前时刻减 300 秒”，晚间执行时两者不属于同一天。它不是一个真实午夜样本。必须换成确定的 23:57→00:02 等真实时间。

补修要求：先定义边界结算和计划重启协议，再实现。不能用比例猜分跨日流量；不能清空历史账或手工把 partial 改 false。没有边界证据就保持 lower-bound / quota_eligible=false。

### F02 / P1：新增计数基线的未知量仍可被当作完整日账

位置：`scripts/qos-r2/proxy-meter-v3.sh:267`、`:277`、`:309`。

`!(e in prev)` 时直接跳过该端点增量，最后只加 `new_ep` 到日志事件，不降级 health/partial。隔离夹具中，上一状态缺少新出现的 down 计数，当前 down 已有 200000B；脚本贡献 0 后仍输出 `health=ok/partial=false/quota_eligible=true`。没有证据证明这些流量都产生于正式注册之前，也没有证明基线准备早于业务。

另一现场事实：**R2 coverage 文件 generated_at 仍为 11-18 22:43:58，unresolved_record_count 仍为 40**。新生成器文件部署成功，不等于过滤后的注册表/coverage 已经生效。本次不能确认那 40 条里多少是真节点、多少是元信息，不能直接全当有效节点，也不能忽略。

补修要求：新增/删除/替换规则有代际、最后样本和基线证据；无证据时标未知并禁止配额触发。先 `--check` 对比生成器的新输出；正式重生成注册表需受控结算和锁，不能裸跑覆盖计数现场。coverage 文件须严格解析；活跃节点、实际连接及适用 IPv6/DNS 变化的覆盖边界须如实登记。

### F03 / P1：紧急锁会被热重载和普通调速撤销

位置：`mgmt/qos-gate/ctl.go:111`、`:154`；`main.go:59`；`bucket.go:97`。

`reload`、SIGHUP、`set-rate` 都调用 `Resume()`；Resume 直接把 `emergency=false`。本轮负例已复现：

```text
release -> reload: 内存 emergency=false，磁盘 emergency=true
release -> set-rate: 未经过 clear-emergency 就重新限速
```

这会造成“用户已经紧急解封，普通配置刷新又把用户限住”，违反 Q4.4。持久文件存在不能弥补运行态已经重新限速。

同一状态实现还存在：

- `ctl.go:33` 每次把 generation 初始化为 1。持久化代际 77 后模拟重启，再 release，实际写回 **2**，已复现。必须从可信持久代际恢复并单调推进。
- `config.go:78` 吞掉读取/JSON 错误，坏状态文件被默认为 emergency=false；本轮坏 JSON 负例复现启动后重新带限制。应进入明确的故障安全状态，保留损坏原件、禁止未知状态下恢复限制。
- 控制连接可并发 dispatch，但 generation 没有控制器级事务锁；SaveState 只锁文件写入，并不覆盖“读代际→修改→落盘→改桶”的事务。此项为源码检查，未在本轮声称完成竞态实测。
- release-class 只解除运行态一类，持久化却是全局 emergency=true；重启会把其它类也解除，范围不一致。需每类持久状态或明确且经过验收的全局语义。
- reload 后没有保存新 cfg 到 g.cfg，clear-emergency 会恢复旧配置速率；ElephantMB 目前没有数据路径引用，不能说置 100 就能工作。

补修要求：单一串行状态转换；普通 reload/set-rate 只能改期望参数，不能解除人工紧急锁；只有明确恢复操作才恢复，并带新代际。坏状态、旧动作、并发、单类作用范围都要有负例。

### F04 / P1：半关闭请求会导致返回数据被截断

位置：`mgmt/qos-gate/pipe.go:72`。

任一方向结束就把两侧读写 deadline 都设置为过去。客户端正常 `CloseWrite()` 表示“请求发完，继续等响应”，这里却让下行读取立即失败。

本轮用真实回环 TCP 对、无任何限速复现：客户端发 request→CloseWrite，服务器收到 EOF 后 80ms 返回 response；客户端实际收到 **空字符串**。这与限速精度无关，是代理转发的正确性问题。

补修要求：正常单向 EOF 只传播对应 CloseWrite，保留反向传输至完成；错误、取消、超时另行协调退出。握手/上游应答超时、半关闭、慢读、客户端取消及 goroutine/FD 回收均验证。当前 stallMax 只是未使用常量，不能把注释当作已实现空闲超时。

### F05 / P1：所谓 20ms 解封测试没有测到“解除阻塞”

位置：`mgmt/qos-gate/qosgate_test.go:109`。

测试用 burst=100，调用 Take(1MiB)；Take 会把一次授权截成 100B，因此约 20ms 就已经返回。测试 200ms 后才 release。**所打印的 20ms 发生在 release 之前**，不能证明解除唤醒。

本轮新增负例在 release 之前检查 done，实际已完成。原 8 项测试全通过与这个问题同时存在。

真机 release2 驱动也先等前一下载结束，才 release 并启动一条新下载；1–2ms 是控制命令响应，不是同一条已阻塞连接恢复的证据。当前脚本还保留 down_bps=2000 却称 2000B/s 的旧口径，与最终 /8 实现不一致，不可按它重跑验收。

补修要求：先确认某个真实连接已经进入令牌等待；保持连接与下载进程不变；发送解除；分别记录收到命令、桶状态改变、同一连接恢复载荷的时间。持久锁再验 reload/SIGHUP/进程重启。先通过这些，再做速度测试。

### F06 / P1：上游省流证据不足，不能改写硬停条件

原 Batch 2 卡片规定：若上游未省流，判 FAIL_SAVE_TRAFFIC 停止。执行记录却自行采用 PARTIAL_SAVE_TRAFFIC，并允许带此前置进入 Batch 3。

现有数字不能支持“承载面省流成立”的最终结论：

1. 报告记录 HK 每连接 send 满 4194304B、客户端单窗口 347894B；若对应同一连接，是约 **12.06 倍**。文中 **2.26 倍**实际来自 788072/347894（BWG 隧道与客户端），不是 HK 源站与客户端，测量层混用了。
2. `send()` 成功仅证明字节交给本机套接字，不能直接当作网卡已发出/服务商已计费；反过来，BWG→R2 单方向短窗口下降，也不能单独证明整条链或两个供应商总量降低。
3. 报告自己承认计数窗口含上一轮缓冲尾差。把不同层、不同窗口的 13KB/s 与“约1MB/s基线”相除，不能给出严格的 98.7% 总费用节省结论。
4. 单连接只收到 347894B，未完成 512KiB；2/4 并发也是超时窗口，不是完整固定数据集验收。上限受约束有证据，精度、完整性和省流全通过没有证据。
5. 当前交付的 `logs/batch2_poc_main_20261119.py` 中 curl_bytes 返回 `(elapsed, text)`，并发结果却用 `r.split()`；按现代码执行会遇到 AttributeError。`per=131072` 也未用于限制响应体。现场后续若用了其它修订驱动，必须补交真实版本和输出，不能让下一 AI 复跑这个旧驱动。

本轮不重新搭建服务器或 PoC，以免把“核查”变成未请求的生产写入。**严格验收结论：上游省流 NOT_PROVEN，发布门禁按 FAIL_SAVE_TRAFFIC/BLOCK_ENFORCE 处理。并非断言该架构在所有场景都不省流。**

补验必须：同一出口、同一专用数据集、唯一 run_id 和同步窗口，分别正常/限速/解封；客户端与 gate 两侧载荷、HK 实际网卡/连接发送、BWG 两条腿分开记；排除其它业务；记录关闭连接后残余缓冲发送，必要时加长稳态窗口。若只减少 BWG→R2 而 HK→BWG 仍预取，明确覆盖边界并继续阻断，不能自行放宽原门槛。禁止改 WAN root 或退回已废弃服务端执行器。
