## 一、评审对象：R4（坊子，山东联通）当前出海通道架构（全部为今日实测事实）

### 1.1 mihomo 节点与切换链（/etc/mihomo/config.yaml，今日 15:29 热重载生效）

```
PROXY(select，现选 AUTO)
 └ AUTO(fallback, interval 300, lazy:false)：NODE-PICK → DIRECT
    └ NODE-PICK(fallback, interval 120, lazy:false，按序取首个健康节点)：
        1. US666-CN2GIA-01   VLESS+REALITY  TCP:443   154.36.139.155（66云 CN2 GIA，✅现主用，实测 165ms）
        2. BWG-HY2-JPTY-01   Hysteria2     UDP:34567 74.82.193.113（❌ TCP/UDP 均已被封）
        3. GIA-HY2-US-01     Hysteria2     UDP:34568 154.36.139.155（同 66云服务器，TCP 被封时 UDP 兜底）
        4. BWG-VLESS-JPTY-01 VLESS+REALITY TCP:443   74.82.193.113（❌ 已被封）
        5. CF-CDN-GIA-01     VLESS+WS+TLS  2053      server=104.18.32.7(CF优选IP)，
                                                      SNI/Host=cf.k3x9m2.top → CF边缘 → 源站 154.36.139.155:2053
```

节点失效自动切换 ≤2 分钟（lazy:false + interval 120，BWG 被墙 17 小时不切换的事故复盘后固化）。

### 1.2 CF 中转链路（今日新建并验证）

```
R4 →(TLS:2053, SNI=cf.k3x9m2.top) CF边缘(104.18.32.7，橙云，边缘证书=Let's Encrypt)
   → CF回源(2053, TLS) → GIA 154.36.139.155:2053 (s-box-ws 独立进程, VLESS+WS, 自签证书) → 国外网站
```

- 域名 k3x9m2.top（NameSilo $1.88/年，CF 免费版，SSL 模式 Full 非strict）
- 源站 s-box-ws 为独立 systemd 进程，不碰 GIA 上原有 s-box(443 REALITY)/hysteria(34568)/sshd
- 今日实测：PC 侧 TLS+WS(101) 全通；R4 侧 YouTube 经 CF **可达（339/366ms 成功案例）**；不稳因素=坊子联通→CF 国际段波动（默认 CF IP 超时级，优选后 0.79s 探测、业务连接约 3-5 成成功率），GIA 源站与 CF→源站段日志实证健康

### 1.3 管理面/远程控制（与出海通道完全隔离，评审时须知其独立性）

设备反向 SSH 双通道：广州 134.175.151.213（国内，主）+ GIA（备份 rssh 口 13221-13233 段）。出海节点被封不影响远程控制；GIA IP 被封会失去 GIA 侧备份排灾口，但广州主口不受影响。

### 1.4 被封历史（关键背景，全部实际发生）

| 服务器 | IP 变更史 | 结果 |
|---|---|---|
| DMIT 美西 | 179.255.137.64 → 69.63.219.156（换过一次） | 换后仍被封（大陆方向） |
| BWG 东京 | 74.82.203.175 → 74.82.193.113（换过一次） | 换后仍被封（TCP+UDP） |
| 66云 GIA | 154.36.137.54 → 154.36.139.155（换过一次） | 现 ✅ 可用（2026-10-30 实测） |

结论性事实：**三家都换过 IP，两家换后仍被封**——GFW 按运营商 IP 段封，换 IP 治标不治本。另外 YouTube 等按 IP 信誉墙数据中心 IP（与 GFW 无关，R1 之外的设备 YouTube 长期不可用）。

## 二、待评审的三个问题

1. **R4 现通道是否可行？**（分层：REALITY 主用 / HY2 同机 UDP 备 / CF CDN 异出口兜底）
2. **能否防止被封？**（REALITY 抗协议识别 vs IP 段封锁的区别；CF 共享边缘的防封逻辑与局限）
3. **66云 IP 被封后的解决方案？**（注意一个关键待验证判断：CF 链路的源站段 CF→GIA 不跨 GFW，理论上 66云 IP 被 GFW 封不影响 CF 通路存活；另"封号"若指 66云 服务商封号/跑路，CF A 记录可 5 分钟改指向新源站）

## 三、GLM 初步立场（供对辩，见 审查_zcode.md）

- Q1 可行：现通道 = 短期靠 REALITY（可用一天算一天）+ 中期靠 CF（异出口，已验证可用但不稳）。
- Q2 部分防：防协议识别（REALITY/WS-in-TLS 都合格），不防 IP 段封——唯一真异出口是 CF；CF 自身风险=域名被针对（$2 换域即解）与联通→CF 国际段质量。
- Q3 有解且已就位一半：GFW 封 66云 IP → NODE-PICK 自动落到 CF（需确认切换顺序中 BWG 死节点不拖慢）；服务商封号 → A 记录改新源站 + s-box-ws 部署脚本重放（脚本已固化在执行记录）。
- GLM 自认的弱点：CF 国际段不稳的根治方案（优选 IP 巡检自动化/Argo Tunnel/换 ISP 线路）尚未实施；CF 节点是手工配置，平台下次发布会清除（需模板支持 vless+ws 后全舰队化）。
