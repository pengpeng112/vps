# 审查_zcode（GLM 独立初审）

## 需求覆盖度自评

用户三问均有对应分析：Q1 可行性 → §2.1；Q2 防封 → §2.2；Q3 预案 → §2.3。事实包（方案.md）中全部数据为今日实测，来源已注明。

## GLM 详细分析

### Q1：R4 现通道是否可行？—— 可行，且是当前约束下的合理形态

分层评估：
- **主用 US666-CN2GIA-01（REALITY）**：165ms 实测，CN2 GIA 线路质量好，REALITY 借 www.microsoft.com SNI 伪装，抗主动探测是目前 TCP 类里最强方案。可用性依赖 66云 IP 未进封禁段。
- **第 3 位 GIA-HY2（同机 UDP）**：仅对"TCP 选择性封锁"有效（历史实证 GFW 曾只封 TCP）；IP 段级封锁时与主用同生共死。价值有限但零成本。
- **第 5 位 CF-CDN-GIA-01**：唯一异出口。今日实证 YouTube 可达（YouTube 长期墙数据中心 IP，这是全舰队首次在其他设备可达）。缺陷：联通→CF 国际段波动（约 3-5 成连接成功率），作为兜底合格、作为主用不合格。
- 自动切换 ≤2 分钟（lazy:false）已被 BWG 事故复盘实证有效。

结论：**可行**。日常质量靠 REALITY 主用；封 IP 事件时 CF 兜底维持可用性（低质量总比断网强）；CF 稳定性优化后可升主用。

### Q2：能否防止被封？—— 分两层回答

- **防"协议识别型封锁"：能。** REALITY（TCP）与 WS-in-TLS（CF 链）对外呈现均为正常 TLS 流量。
- **防"IP 段型封锁"：只有 CF 链能防。** DMIT/BWG/66云 都换过 IP 仍被封的实证说明：只要设备直连 VPS 裸 IP，就有被封的那天。CF 链的出口是 CF 共享边缘 IP（与数百万网站共用），GFW 整体封 CF 等于自断半个国际互联网，历史上未发生过（个别 SNI/域名级封锁有发生）。
- **CF 链自身的残余风险**：① 域名 k3x9m2.top 的 SNI 若被针对 → 换 $2 新域名+改配置即解（设计上已接受）；② 联通→CF 国际段 QoS/拥塞 → 非封锁但影响可用性（优选 IP 缓解，未根治）；③ CF 免费版对 WS 长连接无 SLA，理论上有被 CF 限速/断连的可能（未见实证，值得监控）。

结论：**"防止被封"严格说做不到 100%，但 CF 链把"被封后断网"变成"被封后自动降级到低质量通道"，把"封 IP"这个不可控事件的影响降到可接受**。

### Q3：66云 IP 被封后有无解决方案？—— 有，且一半已就位

分两种"封"：

**A. GFW 封 IP（最可能）**
- 判断：CF 通路**不受影响**——设备连的是 CF 边缘（104.18.32.7），CF→GIA 源站段在国外，不过 GFW。今日拓扑已验证该段健康。
- 设备侧行为：NODE-PICK 里 US666/GIA-HY2 两个探活全死 → 自动落到下一个健康成员（BWG 两个已死）→ CF。预计 ≤2×120s 完成。**即：66云被封的那一刻，R4 自动降级到 CF 通道，无需任何人工干预。**
- 残余弱点：a) CF 段质量波动（如上）；b) GIA 上 rssh 备份排灾口同时失效（广州主口不受影响，管理面保住）；c) 若 CF 域名同时被针对（小概率联动），需人工换域名。
- 建议（未实施）：给 NODE-PICK 加一台"次优 CF 优选 IP"的 CF2 节点做双保险；self-heal 加"连续 N 分钟主用死而 CF 活"的告警上报。

**B. 66云 服务商封号/跑路（"封号"的字面义）**
- 源站没了 → CF 通路同死（源站是它）。解法：CF 控制台把 A 记录 cf.k3x9m2.top 改指向任一新 VPS（BWG/DMIT/新购）+ 在新源站重放 s-box-ws 部署（脚本与参数已固化在 backups/.cf-node-params.json 和执行记录）→ 设备侧零改动（server=CF IP 不变）。预计 5-10 分钟恢复。
- 同时需迁移：GIA 上的 rssh 备份端点（改 tunnel.conf VPS5_HOST）、HY2 服务（若有设备依赖）。
- 管理面：广州主口独立，不受影响。

## GLM 认定的主要风险排序

1. CF 国际段质量不稳（影响兜底可用性）——优化项未做
2. CF 节点为手工配置，平台发布会清除（单点人工依赖）
3. 其他 5 台在线设备尚无 CF 节点（预案只覆盖 R4）
4. CF 免费版长连接政策风险（未实证，需观察）
