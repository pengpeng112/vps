这份方案**方向基本忠实，但还没有完整满足用户需求，尤其不足以支持“在线升级一定不影响远程控制和使用”的承诺**。它已经考虑逐台处理、保留管理栈、不主动重启、不在线抹分区等边界；但存在明确的命令错误、清理遗漏、回退缺口，以及刷机失败仍可能被报告为成功的问题。

本次只读取本地文档和源码，做了不执行实际命令的解析检查；**没有修改任何文件，没有连接现网，没有登录 API 或执行清理、刷机、重启**。下面的现网状态均是文档记载，不能当成本次重新实测。

1. **【高优先级】恢复 R2 每日零点重启，与“使用不受影响”的承诺存在直接冲突。**

   方案把恢复 `0 0 * * * /sbin/reboot` 描述为“次日自然生效”，但定时重启仍然会中断代理、SSH 和正在使用的连接。用户的红线没有限定为“只在施工的五分钟内不断”。应把清理与恢复重启策略分开，明确后者的使用影响及验收窗口，不能把它归入零影响动作。

   出处：[方案：硬边界](/F:/vps/review/round-2/方案.md:42)、[R2 新增重启任务](/F:/vps/review/round-2/方案.md:66)、[次日验收](/F:/vps/review/round-2/方案.md:105)。

2. **【高优先级】`pkill -f` 可能误杀执行清理的远程 shell，破坏本次控制会话。**

   通过 SSH 执行包含 `pkill -f install_pdnterminal.sh` 的整段命令时，父级 shell 的命令行也可能包含这个字符串；此外，按字符串匹配不能证明只命中目标安装器。方案没有核对 PID、完整命令行、父子关系，也没有验证目标固件是否提供所需 `pkill` 实现。“纯休眠 bash，杀掉零影响”的结论缺少当前进程证据。

   应先识别并复核具体 PID，再终止目标进程并检查子进程，而不是直接对整个命令行做宽泛匹配。

   出处：[方案 Phase 1](/F:/vps/review/round-2/方案.md:55)、[方案所列安装器进程](/F:/vps/review/round-2/方案.md:25)。

3. **【高优先级】对厂商 init 脚本直接调用 `stop`，尚未证明不会动网络或误杀管理进程。**

   方案对五个脚本统一执行 `stop; disable; rm`，但没有给出这些脚本的实际内容和调用链。`stop` 可以执行任意 shell 操作，不能仅凭服务名称认定安全。尤其处理的是厂商管理、穿透和重启组件，必须先核对它们怎样寻找进程、是否调用网络服务、是否操作防火墙。

   出处：[方案 Phase 3](/F:/vps/review/round-2/方案.md:64)、[仓库操作边界](/F:/vps/AGENTS.md:33)。

4. **【高优先级】子挂载卸载失败后，方案没有明确禁止继续递归删除。**

   Phase 5 写“busy 则记录跳过”，紧接着仍要求删除 `docker` 目录。如果“跳过”只指跳过卸载，下一步会继续进入仍挂载的文件系统删除数据；如果它指跳过整个数据盘阶段，也没有写清楚。对于仍在运行的 Docker 或未知子挂载，这可能破坏正在使用的数据。

   必须明确：发现活动依赖、卸载失败或挂载关系不明时，停止该路径的删除，将该项记为未完成，不能继续报全绿。

   出处：[方案 Phase 5](/F:/vps/review/round-2/方案.md:73)。

5. **【明确错误】云端点删除命令只有第一个参数是绝对路径。**

   ```sh
   rm -f /www/cgi-bin/cgi-exec cgi-upload cgi-download cgi-backup
   ```

   后三个文件会从当前工作目录寻找。通常会留下真正的三个 CGI；如果当前目录恰有同名文件，还可能误删无关文件。`rm -f` 又会隐藏不存在的错误。应逐个使用完整绝对路径；现有刷机脚本已经采用这种写法。

   出处：[方案 Phase 4](/F:/vps/review/round-2/方案.md:70)、[正确的现有删除路径](/F:/vps/scripts/flash-snr.py:198)。

6. **【重要遗漏】在线清理清单遗漏了已经发现并修复过的安装器真实路径。**

   方案只删两个 `/usr/bin/install_*.sh` 文件。SOP 明确记载过安装器实际位于带字面花括号的目录，现有脚本因此额外删除：

   - `/usr/bin/{install_mbox.sh}`
   - `/usr/bin/{install_pdnterminal.sh}`
   - `/usr/bin/mbox_init.sh`
   - `/usr/bin/mboxinit.sh`

   方案既没有覆盖这些路径，也没有提供四台设备不存在这些路径的证据。只删表中两个普通文件，不能说明已达到 R7 的终态。

   出处：[方案 Phase 2](/F:/vps/review/round-2/方案.md:60)、[SOP 路径纠错](/F:/vps/docs/operations/新SN-R1刷机录入SOP-自动化-20260928.md:218)、[现有完整清理代码](/F:/vps/scripts/flash-snr.py:191)。

7. **【重要遗漏】复活链路覆盖不完整，尤其没有闭环检查 `start_autoupdate`。**

   历史记录明确列出过 `start_autoupdate` 半截禁用的问题；现有刷机清理还覆盖 netbox、zcon、jcgqos、`mbox_init` 等入口。在线方案只处理五个 init 脚本及两条 rc.local 钩子，没有要求核验其余入口及 `/etc/rc.d/S*` 自启链接。

   如果第一轮清理确实已经切断这些入口，本轮应读回证明；否则无法支撑“复活机制清干净”的结论。

   出处：[方案 Phase 3](/F:/vps/review/round-2/方案.md:64)、[历史复活链路](/F:/vps/docs/current/当前状态.md:507)、[刷机服务清单](/F:/vps/scripts/flash-snr.py:180)。

8. **【兼容性缺口】数据盘删除命令依赖花括号展开，执行 shell 没有明确。**

   `/mnt/mmcblk0p6/{docker,lost+found}` 在支持该语法的 shell 中能展开；在不支持的 shell 中，会被当成一个字面路径，配合 `rm -rf` 可能静默什么都没删。方案没有规定远端 shell 或做能力检查。

   应使用两个独立的绝对路径。现有刷机脚本的数据盘删除采用逐路径列出的形式。

   出处：[方案数据盘命令](/F:/vps/review/round-2/方案.md:75)、[现有刷机删除写法](/F:/vps/scripts/flash-snr.py:202)。

9. **【重要遗漏】数据盘清理范围比现有刷机流程明显窄。**

   在线方案只清 `docker` 和 `lost+found`，现有刷机脚本还清除 `by-agent`、`by-daemon`、`by-watcher`、`initmindevice.sh`、`data1`。如果在线设备上存在这些历史载荷，它们会被遗漏。

   应先形成逐台目录清单，识别已知载荷、隐藏项、软链接和子挂载，再限定删除范围，而不是直接假定所有弹药只有两个目录。

   出处：[方案数据盘范围](/F:/vps/review/round-2/方案.md:31)、[现有刷机清理范围](/F:/vps/scripts/flash-snr.py:202)。

10. **【结论过度】“下次开机会重格式为空”不能从 R7 的抹签名实验直接推到在线清内容流程。**

    SOP 的依据是 R7 在抹签名、调整挂载配置后出现新 UUID 和格式化日志。在线方案明确不抹签名，保留有效文件系统。现有证据不能证明它下次也会重新格式化，更不能证明四台设备的全部固件行为一致。

    在线版应依靠本次载荷清除和执行入口切断来成立，并在后续既有重启后读回验证，不应把预期的固件格式化当作保障。

    出处：[方案重格式承诺](/F:/vps/review/round-2/方案.md:75)、[SOP 实验条件](/F:/vps/docs/operations/新SN-R1刷机录入SOP-自动化-20260928.md:254)。

11. **【验收矛盾】“分区内无可执行文件”和“目录必须为空”不是同一个标准。**

    方案先采用“无可执行文件”，终验又要求 `ls /mnt/mmcblk0p6` 为空。标准 ext4 的 `lost+found`、无害元数据都可能造成误报；普通 `ls` 又会漏掉隐藏文件。仅检查执行权限也不足以识别可由解释器运行的脚本。

    应统一为明确的“已知 PCDN 载荷与可调用入口不存在”标准，并写出检查范围与允许保留项。

    出处：[方案数据盘口径](/F:/vps/review/round-2/方案.md:31)、[终验要求](/F:/vps/review/round-2/方案.md:78)。

12. **【高优先级】快照不足以支持承诺的回退。**

    Phase 0 对 init.d 和 CGI 只要求目录列表；列表无法恢复文件内容。没有明确备份文件权限、所有者、软链接、自启链接和被删除二进制，也没有备份数据盘。Phase 7 却承诺这些文件可由快照恢复，并称数据盘“无需回退”。

    应在删除前验证备份可用，并明确哪些操作可恢复、哪些不可恢复。“空分区是目标”不能代替误删后的恢复方案。

    出处：[方案快照](/F:/vps/review/round-2/方案.md:53)、[方案回退](/F:/vps/review/round-2/方案.md:82)。

13. **【回退缺口】恢复 cron 文件不等于恢复运行状态。**

    正向修改显式重启 cron，回退却只写“b64 推回即回退”。方案没有规定回退后重新加载并确认 daemon 状态，也没有恢复 init 服务的启用关系和原运行状态。

    回退应包含内容恢复、必要的服务加载、读回和业务验证。不能仅凭文件恢复宣告生效。

    出处：[正向 cron 操作](/F:/vps/review/round-2/方案.md:65)、[回退承诺](/F:/vps/review/round-2/方案.md:83)。

14. **【高优先级】文件替换缺少“先验证、后原子替换”的步骤。**

    方案要求推送后才做 `sh -n`，没有规定先上传到同目录临时文件、校验内容和语法、保留权限，再原子替换正式文件。直接覆盖时，如果连接中断，会留下半截 rc.local 或 crontab。其影响可能到下次开机才暴露。

    base64 和 md5 可以检查传输内容，但不能自动提供替换原子性。

    出处：[方案文件修改原则](/F:/vps/review/round-2/方案.md:44)、[方案 rc.local 操作顺序](/F:/vps/review/round-2/方案.md:67)、[现有 push 直接覆盖目标](/F:/vps/scripts/flash-snr.py:118)。

15. **【流程缺口】缺少并发保护、失败闸门和明确检查点。**

    快照取得后，agent 的策略任务仍可能改 crontab；随后用旧快照整文件覆盖，会丢掉并发变更。方案没有规定比对修改前哈希、检查待执行任务，也没有给每个阶段定义退出码、停止条件及续跑位置。

    此外，“单台失败不影响其余”与“全绿才下一台”之间需要明确裁决：是停整批，还是隔离故障后继续。不能留给执行者临场猜测。

    出处：[方案逐台原则](/F:/vps/review/round-2/方案.md:48)、[整文件改写](/F:/vps/review/round-2/方案.md:65)、[全绿要求](/F:/vps/review/round-2/方案.md:77)、[agent 也会改写 cron](/F:/vps/mgmt/agent/handlers/switch_node.sh:544)。

16. **【核心验收不足】路由器自身 HTTP 成功不能证明用户使用无影响。**

    路由器执行一次代理出口查询，只证明该次请求能走代理；无法证明 LAN 转发、WiFi、既有长连接、直连业务和视频体验正常。仓库已有明确教训：路由器自身测试正常，终端 WiFi 段却严重劣化。

    应有独立用户侧探针覆盖实际使用路径，并比较升级前、期间、之后的丢包、延迟和连接连续性。出口 IP 不变与 QUIC 规则不变，只是部分验收项。

    出处：[方案“不影响”六项](/F:/vps/review/round-2/方案.md:79)、[用户侧无感知判定](/F:/vps/review/round-2/方案.md:104)、[历史测量盲区](/F:/vps/docs/current/当前状态.md:68)。

17. **【核心验收不足】前后两次心跳和实例数一致，不能证明远程控制全程连续。**

    控制链可能中间断开后恢复；相同数量的 SSH 进程也可能包含失效连接。方案没有建立独立持续监测，没有记录关键进程 PID、启动时间，也没有明确“全程可入”是怎样测得的。

    心跳“30 秒内两连拍”还应核对实际设备间隔：仓库 agent 默认心跳间隔为 60 秒，在线配置是否覆盖该值没有提供证据。

    出处：[方案基线](/F:/vps/review/round-2/方案.md:52)、[连续性承诺](/F:/vps/review/round-2/方案.md:104)、[默认心跳间隔](/F:/vps/mgmt/agent/routermgmt-agent.sh:19)。

18. **【证据缺口】四台设备的具体残留及 R2 死代码结论，缺少可追溯原始输出。**

    方案写了“上午实测”、行号、进程和分区内容，但没有链接对应命令、完整输出、采集时间、设备身份及哈希。当前状态文件支持“曾清表层、深层仍待处理”，却没有独立提供本方案这张逐台残留表的全部证据。

    特别是 R2“因死代码导致三天未重启”，还需核对 rc.local 全文、钩子调用位置、当前 cron、平台策略和启动记录；uptime 本身不能证明这个因果链。

    出处：[方案现状表](/F:/vps/review/round-2/方案.md:12)、[R2 因果判断](/F:/vps/review/round-2/方案.md:32)、[历史深层待办](/F:/vps/docs/current/当前状态.md:508)、[开机 cron 恢复实现](/F:/vps/mgmt/agent/onboot-hooks.sh:8)。

19. **【状态冲突需核对】R5/R7/R8 是否离线，关系到处理范围。**

    方案把 R5/R6/R7/R8 列为离线；当前状态的 R9 完成条目则记载 R1–R5、R7–R9 在线，仅 R6 离线。两者可能是不同采样时点，不能直接判谁错；但方案应给出准确采集时间，并在执行前刷新范围。

    若 R5 已回线，继续只登记待办，会漏掉本轮需要核查的设备。

    出处：[方案设备状态](/F:/vps/review/round-2/方案.md:10)、[当前状态另一口径](/F:/vps/docs/current/当前状态.md:535)、[方案 R5/R6 待办](/F:/vps/review/round-2/方案.md:115)。

20. **【重要遗漏】在线终验没有覆盖完整的 PCDN 运行面和持久化面。**

    Phase 6 未列明确的异常监听端口、rc.d 自启链接、被删二进制读回，也没有完整进程匹配规则。现有刷机脚本至少检查了多个异常 TCP 端口和 rc.d 链接；在线版反而更弱。

    应定义共同的逐项检查清单，包括安装器及子进程、收益进程、异常 TCP/UDP 监听、自启入口、脚本与二进制、数据盘载荷。检查命令失败要判为未知或失败，不能判干净。

    出处：[方案终验](/F:/vps/review/round-2/方案.md:78)、[现有运行面检查](/F:/vps/scripts/flash-snr.py:653)。

21. **【高优先级】现有批量刷机重启复验失败不会影响最终成功结果。**

    `flash-batch.py` 的 `good=False` 或复验异常只打印 `FAIL`；最终失败计数仍来自刷机阶段的 `results`。而设备在重启复验前就已标记为 `done`。因此可能出现“重启后失联/PCDN 复活，但批量总结仍为成功、退出码为 0”。

    这必须作为后续刷机流程的阻断项修复，不能只增加三条检查。

    出处：[提前标记 done](/F:/vps/scripts/flash-batch.py:239)、[复验仅打印](/F:/vps/scripts/flash-batch.py:270)、[最终失败计数](/F:/vps/scripts/flash-batch.py:278)、[方案刷机增量](/F:/vps/review/round-2/方案.md:94)。

22. **【高优先级】批量重启复验的连接命令存在确定的实现缺陷。**

    发往 DMIT 的复验 SSH 参数缺少 `-p 28722`，与项目规定入口不一致；本机 SSH 配置没有为该 IP 补充此端口。构造的远端命令又把整个设备检查包在单引号中，内部 `grep -E '…|…|…'` 再使用单引号，导致引用边界被破坏，管道可能在 DMIT 外层解释。

    `bash -n` 对重建命令通过，但语法通过不能证明命令会在正确设备执行。需要检查实际参数边界，并使用结构化文件或可靠传输方式消除多层拼接。

    出处：[复验命令构造](/F:/vps/scripts/flash-batch.py:258)、[缺少端口参数](/F:/vps/scripts/flash-batch.py:266)、[规定入口](/F:/vps/docs/INDEX.md:77)。

23. **【确定缺陷】刷机终验首轮解析会漏掉 P2/P3/P4/P5，造成必然误失败和额外等待。**

    首轮合并扩展检查结果使用 `^(\w)=(.*)$`，只接收单字符键，接收不到 P2–P5。随后这四项都不能通过，触发固定 60 秒等待；复测才换为 `^(\w+)=(.*)$`。

    本次用同样正则做只读复现，输入 P、P2、P3、P4、P5、Q，结果只取得 P 和 Q。因此至少一部分所谓“瞬态消抖”其实来自解析错误，不能继续用固件瞬态解释。

    出处：[首轮解析](/F:/vps/scripts/flash-snr.py:661)、[固定等待](/F:/vps/scripts/flash-snr.py:680)、[复测解析](/F:/vps/scripts/flash-snr.py:702)。

24. **【刷机覆盖不足】新增三关卡仍无法把深层清洁终态完整固化。**

    现有 P5 只检查 rathole、zcon-ng、cgi-exec 三个文件；未完整验证安装器目录、zcon-edge、数据盘载荷、checkMem 等。P 进程项也不含本方案重点强调的休眠安装器。

    新增 exit、重启标记和 CGI 检查后，这些缺口仍存在。在线工具与刷机工具应共享一份完整检查清单，而不是只写“共用口径”。

    出处：[方案新增三项](/F:/vps/review/round-2/方案.md:94)、[现有进程与文件检查](/F:/vps/scripts/flash-snr.py:653)、[拟共用口径](/F:/vps/review/round-2/方案.md:99)。

25. **【可靠性缺口】TX/BWG 公钥校验只检查编号注释，不能证明正确公钥及权限落地。**

    `grep "snR{N}"` 会把 `snR1` 与 `snR10` 等匹配混淆；同编号旧钥也会被当成成功，并触发跳过追加。当前校验没有比较完整公钥或指纹、限制选项，也没有用新设备实际验证备用隧道。

    SOP 提供的 R9 测试是在手工救过的钥上重复运行，证明了该场景的幂等行为，尚未证明新编号首次分发、错误旧钥和失败重试路径。

    出处：[方案“硬校验”描述](/F:/vps/review/round-2/方案.md:96)、[注释匹配实现](/F:/vps/scripts/flash-snr.py:437)、[已提供实测范围](/F:/vps/docs/operations/新SN-R1刷机录入SOP-自动化-20260928.md:275)。

26. **【可靠性缺口】failover SQL 的结果校验不足以确认成功，也不阻断出厂。**

    两处实现只判断 stdout 是否包含 `UPDATE`。即使返回 `UPDATE 0`，也会被视作成功；失败只打印告警，没有进入终验失败条件。没有核对返回码、三条更新是否均命中、最终优先级以及设备配置是否与数据库一致。

    后续刷机应读回预期绑定和优先级，失败不得交付。

    出处：[方案已落地描述](/F:/vps/review/round-2/方案.md:96)、[第一次 SQL 判断](/F:/vps/scripts/flash-snr.py:553)、[恢复 SQL 判断](/F:/vps/scripts/flash-snr.py:737)、[最终通过条件](/F:/vps/scripts/flash-snr.py:752)。

27. **【刷机风险遗漏】抹分区仍依赖固定设备名及卸载检查，没有完整的破坏性操作闸门。**

    当前刷机代码固定写 `/dev/mmcblk0p6`、768MB；方案延续它，但没有要求核验机型、分区用途、容量及全部挂载引用。代码还允许 `umount -l`，之后只用 `mount` 字符串判断是否可以写块设备；这并不能覆盖所有活动引用。

    SOP 已把 dd 降级为辅助步骤。后续流程应明确是否仍需要它；若保留，应补足设备身份、分区和活动依赖验证，以及失败后的停止条件。

    出处：[现有卸载与 dd](/F:/vps/scripts/flash-snr.py:210)、[SOP 已降级为辅助](/F:/vps/docs/operations/新SN-R1刷机录入SOP-自动化-20260928.md:254)、[方案保留刷机 dd](/F:/vps/review/round-2/方案.md:75)。

28. **【文档一致性问题】验收数量与实际实现对不上。**

    Phase 6 的“残留六项”实际列出七项，再加“不影响六项”共十三项；R2 又列三项加验，却在方案级写十四项。批量复验写“12→14”，同时说增加三项；当前代码实际只判断六个字段。单台脚本最终成功提示仍写“11关”。

    这会让“全绿”无法对应到稳定的验收范围。应给每项固定编号、条件、证据路径和失败处置，不再以漂移的总数证明完整性。

    出处：[在线验收计数](/F:/vps/review/round-2/方案.md:77)、[批量计数](/F:/vps/review/round-2/方案.md:95)、[方案级计数](/F:/vps/review/round-2/方案.md:103)、[批量实际判断](/F:/vps/scripts/flash-batch.py:270)、[单台成功提示](/F:/vps/scripts/flash-snr.py:755)。

29. **【流程完整性不足】单台刷机入口和批量入口的重启验收标准没有统一。**

    `flash-snr.py` 可以直接报告完成，但受控重启及重启后复验在 `flash-batch.py` 中。方案没有规定直接运行单台脚本后，必须走怎样的收尾才能交付。历史上恰恰是重启后才暴露了 QUIC、数据盘和死代码问题。

    应明确区分“配置完成”和“重启后验收完成”，所有入口共享同一交付闸门。

    出处：[单台完成出口](/F:/vps/scripts/flash-snr.py:755)、[批量重启入口](/F:/vps/scripts/flash-batch.py:244)、[SOP 重启验证要求](/F:/vps/docs/operations/新SN-R1刷机录入SOP-自动化-20260928.md:230)。

30. **【范围与结论应更准确】现有材料支持“潜伏残留待清”，不能直接升级为“正在跑 PCDN”或“已经全面干净”。**

    方案自己记载收益进程为零。安装器存活、启动入口和磁盘载荷代表复活风险，不能直接证明当前存在收益流量。反过来，现有检查也不足以证明不存在未知启动入口、外联或替代载荷。

    应分别报告运行进程、安装器、持久化入口、磁盘载荷、监听端口和流量证据。若没有流量侧核查，应明确“未验证当前 PCDN 外联/流量”，避免“重度”“无”“根除”超出证据范围。

    出处：[方案收益进程为零](/F:/vps/review/round-2/方案.md:34)、[逐台“重/无”判断](/F:/vps/review/round-2/方案.md:16)、[现有有限匹配清单](/F:/vps/scripts/flash-snr.py:653)。

建议修订时先完成五个具体交付：**逐台可追溯证据表、完整清理与验收清单、带停止条件和可验证备份的在线流程、独立的控制与用户侧连续监测、失败必阻断交付的统一刷机收尾流程**。R2 恢复定时重启应单独注明影响；未经历后续重启的在线设备，应标为“在线清理通过，持久化终验待完成”。在这些缺口闭环前，这份方案适合作为讨论稿，尚不适合直接按文执行并承诺零影响。
