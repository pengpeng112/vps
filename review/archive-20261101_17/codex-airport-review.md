**结论：先修平台覆盖风险、冷启动兜底和空组行为，再完成主链全断验收后铺开。CPU 瞬时 138% 和未经证实的“10 台限制”，都不能单独判为阻断。**

以下依据你提供的实测及 **v1.19.31 源码**，未重新连接设备验证。

1. **阻断：手工配置会被平台覆盖。**  
   优先先模板化，并验证一次平台重发后配置仍完整。若暂时手工铺开，至少落实相关发布冻结、配置备份和恢复流程；“之后会模板化”尚未解决覆盖风险。

2. **阻断：备用链的冷启动能力尚未证明。**  
   `proxy: NODE-PICK` 合法，但它指定的是**订阅下载通道**：主链全断后，订阅无法经此通道刷新；机场节点自身并不因此经过主链。已有有效缓存仍可使用，所以应确保缓存位于持久目录、发布不会清除，并验证主链不可用时重新加载仍能使用机场。无缓存启动还需要经验证的独立获取路径或预置有效节点；订阅及节点域名的 DNS 也要能独立解析。[下载通道说明](https://wiki.metacubex.one/config/proxy-providers/#proxy)、[缓存加载源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/component/resource/fetcher.go)

3. **铺开前修正空组行为，并补故障验收。**  
   `AIRPORT` 首次加载失败且无有效缓存时，默认空组回退为 `COMPATIBLE`，等效直连，可能让未配置 `DIRECT` 的 `US-MEDIA` 也直连。若媒体流量不允许这种行为，在 **AIRPORT 组内**显式设置：

   ```yaml
   empty-fallback: REJECT
   ```

   这只处理“组为空”，不处理“有节点但全部失效”。目前“加载成功、选中日本、主链正常”还未证明自动兜底：应验证**主链全断→自动切机场→真实业务通→主链恢复回切**，并覆盖订阅下载失败、有缓存重载。核对外层 `AUTO`、`US-MEDIA` 的探测已启用，探测 URL 与状态码要求对齐。[空组默认值](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/outboundgroup/parser.go)、[COMPATIBLE 定义](https://wiki.metacubex.one/config/proxies/built-in/#compatible)

4. **非阻断：CPU 先观察，不必立即放宽周期。**  
   若监控按核累计，138% 约为占用 1.38 个核心；重点看持续时间、转发延迟、心跳、内存及 OOM。还需纠正一个常见判断：**此版本同一 provider 的相同探测 URL 会去重，不能认定两处 300 秒就把 38 节点测速翻倍**；外层组仍可能另测组成员。provider 定时检查内部并发上限为 10。[健康检查源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/provider/healthcheck.go)

   `300→600 秒`能降低探测频率，**不能直接降低单次峰值**，也会延长部分故障发现时间。若确有业务抖动，优先在 provider 层保留一批经过验证的节点。兜底用途建议先保留 `lazy: false`。

5. **非阻断：补过滤词，避免泛化误杀。**  
   provider 中可改为：

   ```yaml
   exclude-filter: '(剩余流量|套餐到期|到期时间|官网|公告|重置时间|节点超时.*更新订阅)'
   ```

   能覆盖已知提示节点；不要简单加入所有“超时”“更新”字样。此版本 provider 先按原始名称过滤，再添加 `AP | ` 前缀，无需把前缀写入表达式。过滤后检查真实节点数量及名单。[解析源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/provider/provider.go)

6. **设备限制：错开 interval 只能缓解并发，不能解决额度。**  
   必须先确认机场限制的是设备数、来源公网 IP、连接数，还是某个时间窗内的活跃数。六台路由器之外，还要考虑其他客户端；`lazy: false` 即使没有业务也会建立探测连接，是否计入在线取决于机场。

   错开订阅更新、测速启动时间有助于削峰，但**不能保证不触发设备上限**。先逐台增加并观察认证失败、限流；确有限额则使用允许多设备的授权或拆分账号。不要把健康检查“并发 10”与机场“设备限 10”混为一谈。

7. **其他需要明确的行为。**
   - `US-MEDIA → AIRPORT` 当前可能选日本；若要求美国出口或特定流媒体解锁，应另设符合条件的机场组。gstatic 204 只证明该探测可达，不能证明解锁、带宽或 UDP 可用。
   - `fallback` 按成员顺序选择健康项，因此机场 56ms 不会仅因更快抢占主链；但**全员不健康时会返回首成员，末尾 `DIRECT` 不是无条件兜底**。[fallback 源码](https://github.com/MetaCubeX/mihomo/blob/v1.19.31/adapter/outboundgroup/fallback.go)
   - 贴出的片段缺少顶层 `proxy-groups:`。若只是展示时省略，无需处理；若实际文件也是如此，则层级错误。平台最终渲染结果应使用同版本 `mihomo -t` 校验，再按单台、剩余设备分批验收。
